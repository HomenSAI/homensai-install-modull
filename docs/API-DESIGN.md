# Публичный API установочного модуля: проект v1

02.11.2026 · HomenS.AI · Serhii Khomenko

Проектный контракт. Ниже описаны требуемые операции, а не утверждение об их
реализации. Действующий `shared.ctl` поддерживает только подмножество локальных
действий и не соответствует этому API полностью. Исполняемая спецификация и
тестовый клиент создаются на шагах 110–113. Ранний ограниченный интерфейс
`shared.api` уже предоставляет `capabilities`, `validate`, частичную проверку
`preflight-fresh`, `check-target` и, при доступной криптографической зависимости,
`verify-package`, `inspect-fresh-package`, `inspect-native-fresh-package` и
`fresh-status`. API 1.8 добавляет ограниченную изменяющую операцию
`prepare-native-release`; API 1.9 добавляет чтение `update-plan-status`,
API 1.10 — проверку файлов подготовленного выпуска `verify-native-release`,
API 1.11 — нижнюю оценку места для подготовки подписанного нативного выпуска,
API 1.12 — локальную проверку ответа продукта `check-local-health`,
API 1.13 — предварительный просмотр подписанных Linux user-units
`plan-systemd-user-units`, API 1.14 — их ограниченную публикацию
`publish-systemd-user-units`, API 1.15 — загрузку опубликованных units
`load-systemd-user-units`, API 1.16 — необязательную проверку сгенерированных
unit-файлов при публикации, API 1.17 — планирование, публикацию и загрузку
units из подписанного переносимого рецепта. API 1.18 добавляет планирование,
подготовку и проверку подписанного Linux runtime. API 1.19 добавляет совместную
проверку готовности runtime и переносимых user-служб к первому запуску.
API 1.20 добавляет ограниченный первый запуск этих служб, API 1.21 — их
остановку с отдельным журналом, API 1.22 — подтверждение остановленных units
после неопределённого результата остановки, API 1.23 — подтверждение активных
units после неопределённого результата запуска. API 1.24 добавляет ограниченные
повторные циклы запуска и остановки для того же подготовленного выпуска.
API 1.25 добавляет предварительный просмотр фаз обновления `plan-update`.
API 1.26 добавляет наблюдение за прерванным обновлением `inspect-update-recovery`.
API 1.27 добавляет локальный импорт копии в checkpoint отката `import-update-archive`.
API 1.28 добавляет ограниченную проверку Docker `check-docker-engine`.
API 1.29 добавляет подготовку подписанного Linux-выпуска `prepare-signed-linux-update`.
API 1.30 добавляет проверку начатого подписанного обновления `inspect-signed-linux-update`.
API 1.31 добавляет `install-portable-linux`: ограниченный сценарий первой
Linux-установки с журналом шагов, описанный в [FRESH-CONTROLLER.md](FRESH-CONTROLLER.md).
API 1.32 добавляет чтение привязанного журнала `inspect-portable-linux-install`.
API 1.33 добавляет план `plan-signed-compose` для нескольких компонентов Docker.
API 1.34 добавляет ограниченную подготовку этого плана `prepare-signed-compose`.
API 1.35 добавляет проверку локальных ссылок образов `inspect-signed-compose-images`.
API 1.36 добавляет ограниченное управление `control-signed-compose`.
API 1.37 добавляет чтение связанного журнала `compose-control-status`.
API 1.38 сверяет идентификатор образа контейнера с разрешённой digest-ссылкой.
API 1.39 добавляет ограниченное согласование неопределённого start/stop.
API 1.40 проверяет хэши конфигураций и при обычных start/stop и их повторах.
API 1.41 дополнительно сверяет выбранные фактические параметры контейнеров.
API 1.42 сверяет окружение контейнеров с окружением закреплённого образа.
API 1.43 добавляет проверку ответа здоровья подписанного Compose-продукта.
Полная установка и обновление через API пока недоступны.

`start-portable-linux` принимает поля `check-portable-linux-start` и отдельный
`idempotency_key` запуска. Три ключа загрузки, подготовки runtime и запуска
должны различаться; ключ публикации также не должен совпадать с ключом запуска.
Перед действием проверяются выпуск, runtime и остановленные загруженные units.
После создания устойчивой отметки `pending` отправляются команды start, затем
после подтверждения активного состояния сохраняется `done`. Совпадающий повтор
`done` повторно проверяет runtime и активные units, не отправляя start. При
`pending`, повреждённой или конфликтующей отметке повтор запрещён; ошибка не
доказывает, что службы не запустились. Автоматической очистки отметки пока нет.
Вызов может выполнить код из
подписанного продукта; подпись не гарантирует его безопасность. Проверка не
защищает от изменения файлов после неё или прямого управления systemd. Ответ
означает активность units, но не здоровье приложения и не готовую установку.

`reconcile-portable-linux-start` принимает тот же запрос и ключ запуска. Под
блокировкой он требует точную отметку `pending` или `done` и отсутствие отметки
остановки, проверяет подпись, runtime и активное состояние всех выбранных
units. При `pending` он сохраняет `done` и заново проверяет runtime и units,
не отправляя команды start или stop. Поле `prior_start_command_confirmed` со
значением `false` означает, что проверка не устанавливает причину активности. Здоровье
продукта не проверяется. При ошибке после записи `done` запись могла сохраниться;
неактивные либо неподтверждённые units блокируют подтверждение.

`stop-portable-linux` принимает те же поля и дополнительно `start_key` — ключ
уже записанного запуска; `idempotency_key` задаёт отдельный ключ остановки.
Ключи запуска, остановки, загрузки и runtime должны различаться. Допустима
остановка после `pending` запуска, если units имеют устойчивые состояния.
Проверяются подписанный выпуск и идентичность units, но не подготовленный
runtime, чтобы его повреждение не препятствовало остановке. После `pending`
отправляются stop и проверяется неактивное состояние; повтор `done` только
проверяет состояние, повтор `pending` запрещён. Ошибка может означать частичную
или полную остановку. Ответ не гарантирует, что все внешние писатели остановлены.
Общая блокировка не допускает одновременные API start/stop одной установки, но
не охватывает прямые вызовы systemd и все прочие действия установщика. После
отметки остановки для следующих циклов используется `cycle-portable-linux`.

`cycle-portable-linux` принимает поля выпуска и runtime, ключи `load_key`,
`runtime_key`, `initial_start_key`, `initial_stop_key`, новый `idempotency_key`,
`action` (`start` или `stop`) и обязательный boolean `reconcile`. Первая пара
ключей первого запуска и остановки привязывает журнал к уже остановленному
выпуску. Под общей блокировкой операция хранит последовательность до 512 новых
действий с уникальными ключами и отметками `pending/done`; старые отметки не
удаляются. Повтор `done` проверяет текущее состояние без отправки команды.
`reconcile: true` подтверждает только точный последний `pending/done` по
состоянию units без новой команды; оно не доказывает причину состояния.
После неопределённого start допускается отдельный stop стабильной группы;
запуск сохраняется как `interrupted`, а не как успешный. Неопределённый stop
требует подтверждения состояния, повторять действие автоматически нельзя.
После начала нового журнала старый API остановки блокируется. Следующий start
требует проверенного runtime; stop не требует исправного runtime. API не
подтверждает здоровье продукта или остановку внешних писателей, не исключает
прямое управление systemd и изменение состояния после проверок. Обновление,
ротация журнала и переход между выпусками ещё не реализованы.

`reconcile-portable-linux-stop` принимает точно тот же запрос и ключ остановки,
что предыдущий `stop-portable-linux`. Под общей блокировкой он требует точную
отметку `pending` или `done`, проверяет подписанный выпуск и неактивность всех
выбранных units. При `pending` он переводит её в `done` и перепроверяет units;
ни start, ни stop он не отправляет. Ответ `prior_stop_command_confirmed: false`
означает, что наблюдаемое состояние не устанавливает причину остановки.
Активная или недоступная служба блокирует подтверждение. Внешние писатели и
изменения после проверки не исключаются; состояние может измениться и после
сохранения отметки, поэтому ошибка после записи не означает отсутствие записи.

`check-portable-linux-start` принимает `package_path`, `envelope`,
`trusted_public_key`, `expected_product_id`, `expected_version`, `install_root`,
`modes`, `unit_dir`, `load_key`, `runtime_key` и `reserve_bytes`. Последние три
значения должны совпадать с отдельными завершёнными загрузкой units и
подготовкой runtime, а два ключа — различаться. Вызов сверяет подпись, выпуск,
отметки, файлы runtime и состояние остановленных units. Команды запуска,
остановки и daemon-reload не отправляются. Опрашивание systemd может загрузить
unit в менеджер, поэтому операция объявлена изменяющей; файлы установщика она
не создаёт. Успех не гарантирует будущий запуск: после проверки данные и
состояние могут измениться, а код и совместимость Python не проверяются.
Операция не подтверждает здоровье приложения или завершённость установки.

`plan-linux-runtime`, `prepare-linux-runtime`, `verify-linux-runtime` принимают
`package_path`, `envelope`, `trusted_public_key`, `expected_product_id`,
`expected_version`, `install_root` и целое `reserve_bytes`. Для подготовки и
проверки дополнительно требуется `idempotency_key`; проверка использует тот же
ключ и параметры, что и завершённая подготовка. План и проверка не создают
файлы; подготовка является изменяющей операцией. Проверка подтверждает состав,
байты и права уже подготовленного runtime, не исполняя его. Ошибка подготовки
может оставить частичные файлы и журнал `pending`. Операции не доказывают
совместимость, происхождение, отсутствие вредоносного кода или готовность
установки; запуск служб не зависит автоматически от проверки runtime. Подробнее:
[RUNTIME-LINUX.md](RUNTIME-LINUX.md).

`plan-systemd-user-units` принимает `package_path`, `envelope`,
`trusted_public_key`, `expected_product_id`, `expected_version`, `install_root`
и непустой массив `modes`. Пакет и подготовленный выпуск проверяются; ответ
содержит имена и SHA-256 выбранных unit-файлов, `state: planned`, а также
`services_started: false`, `manager_checked: false` и
`publication_readiness_verified: false`.
Запрос не обращается к systemd и не публикует, не загружает и не запускает
службы. Он не проверяет каталог назначения или доступность менеджера и не
является разрешением на запуск. Возможность объявляется на нативном Linux
x86-64 при наличии криптографической зависимости. Ошибка проверки возвращает
`systemd_plan_failed`; сообщения доступны на русском, английском и немецком.

`publish-systemd-user-units` принимает те же параметры и дополнительно
`unit_dir` и `idempotency_key` из 32 строчных шестнадцатеричных знаков. Это
изменяющая операция: она создаёт подписанные файлы в каталоге текущего user
systemd, не перезаписывая существующие. Каталог, права, менеджер, выпуск и
состав проверяются; журнал привязывает ключ к запросу. Повтор подтверждённой
операции сверяет файлы, а неопределённое состояние или конфликт приводят к
`systemd_publish_failed` и требуют отдельного разбора. Нельзя считать любую
ошибку доказательством отсутствия изменений. Ответ с `state: published`
означает публикацию файлов, `services_started: false` — отсутствие запуска
данным вызовом, а `installation_complete: false` — незавершённую установку.
API не выполняет reload, enable или start; публикация позволяет менеджеру
позже обнаружить файлы. Подпись не доказывает безопасность их содержимого.
Необязательный `verify_generated_units: true` требует точного совпадения с
генератором для подписанного манифеста и указанного корня до записи. Это
политика фиксированного корня, а не переносимая генерация после подписи;
сервисные секреты в этом варианте пока не поддерживаются. Политика входит в
привязку ключа операции. Если поле отсутствует, действует прежнее поведение.

`load-systemd-user-units` принимает те же поля, что и публикация, с отдельным
`idempotency_key`. Это изменяющая операция: она выполняет настоящий
`systemctl --user daemon-reload`, относящийся ко всему пользовательскому
менеджеру и способный применить и другие ожидающие изменения его конфигурации.
Вызывать её следует только при управлении этим менеджером. Загрузка не делает
enable или start. Перед reload записывается `pending`, после подтверждения —
`done`; повтор `done` проверяет состояния без нового reload. После потери
ответа или ошибки, оставившей `pending`, операция отказывает без повторного
reload, пока неопределённое состояние не будет разобрано. Ошибка
`systemd_load_failed` не доказывает, что reload не произошёл. Ответ `loaded`
не означает, что продукт установлен или работоспособен.
Клиент обязан выделять новый ключ для каждой операции: общий реестр,
проверяющий уникальность ключей между всеми видами операций, пока не реализован.
Повторное использование ключа из отметки публикации для загрузки отклоняется.

`plan-portable-systemd-user-units`, `publish-portable-systemd-user-units` и
`load-portable-systemd-user-units` используют поля и ограничения соответствующих
непереносимых операций. Пакет должен содержать подписанный рецепт v1; пути
подставляются для указанного подготовленного корня после проверки подписи.
План возвращает имена и хэши, без текстов команд, обращения к менеджеру или
записи. Публикация и загрузка требуют разные ключи повтора. Загрузка выполняет
глобальный user-manager `daemon-reload`; при неопределённом результате повтор
блокируется. Никакая из этих операций не запускает службы, не поставляет
runtime и не подтверждает безопасность приложения. Рецепт и генератор пока
экспериментальны; одинаковые `product_id` в одном менеджере конфликтуют.

## Границы и транспорт

Первая версия — локальный API с интерфейсом вызова в Python и отдельным CLI,
передающим JSON через stdin/stdout. Их семантика, проверка и форматы совпадают;
CLI запускается без shell, не принимает секреты в argv и не выводит их в JSON.
Пример клиента с согласованием возможностей и обработкой ошибок находится в
`examples/demo_product/installer_client.py`; это локальный пример, а не
опубликованный SDK или интеграция с существующими проектами.
Интегратор использует опубликованную клиентскую библиотеку или документированный
CLI, а не импортирует внутренние модули, state-файлы или исключения реализации.
Обе стороны устанавливаются на одном хосте. Никакого сетевого сервера, облака
или ИИ для работы API не требуется. HTTP/удалённый доступ не входит в v1.

Доверенное приложение вызывает API в контексте пользователя/службы ОС; права
операционной системы ограничивают доступ к файлам, секретам и управлению
службами. Дополнительное повышение привилегий только через явную платформенную
процедуру с проверкой владельца установки; произвольный путь к исполняемому
файлу, shell-команда или произвольный compose-файл из API не принимаются как
доверенное действие. Установщик отдельно проверяет пакет, идентичность и
совместимость продукта. Локальный API не является песочницей для злоумышленного
кода, уже работающего с равными правами.

## Совместимость и согласование возможностей

До действий клиент вызывает `capabilities` и проверяет целое `api_major: 1`,
минимально необходимую `api_minor`, перечисленные `operations`, версии
манифестов, доступные способы запуска и ограничения текущего хоста. Клиент
отказывает при неизвестной major-версии или отсутствии требуемой возможности.
Minor-версия допускает обратно совместимые дополнительные операции/поля;
новые обязательные поля или изменение смысла требуют новой major-версии.
Клиент игнорирует неизвестные поля ответа, сервер отвергает неизвестные поля
запроса. Поле возможностей означает реализованную и проверенную возможность,
а не намерение будущей версии. До реализации нельзя считать какие-либо
проектные операции доступными.

## Общий конверт

Каждый запрос — JSON-объект с `api_major`, `operation`, `request_id` и
`params`. `request_id` — безопасный идентификатор клиента для сопоставления,
не секрет и не доказательство авторизации. Операции изменения дополнительно
передают устойчивый `idempotency_key`, уникальный для установки и неизменного
запроса. Один ключ с другим запросом отклоняется. Сервер ограничивает размер,
глубину и число объектов, запрещает дубликаты ключей JSON и недопустимые типы;
точные пределы фиксируются в исполняемой спецификации до выпуска.

Успех: `{api_major, request_id, ok: true, result}`. Ошибка:
`{api_major, request_id, ok: false, error: {code, message, retryable}}`.
Коды стабильны в пределах major и включают `invalid_request`,
`unsupported_version`, `unsupported_operation`, `unsupported_platform`,
`not_found`, `conflict`, `permission_denied`, `verification_failed`,
`operation_failed` и `recovery_required`. `message` безопасен для пользователя;
не содержит секретов, произвольных исключений или вывода процессов. CLI отдаёт
один JSON на stdout; код 0 — успешный ответ, 2 — ошибка контракта/совместимости,
1 — операционная ошибка; диагностика не дублирует секреты в stderr.

Начиная с API 1.4 запрос может содержать необязательное поле `language`,
например `"de"`. `capabilities.result.languages` перечисляет полные доступные
словари. При указанном языке переводятся сообщения ошибок API; коды ошибок и
машинные поля не зависят от языка. Старый запрос без поля сохраняет русский
текст. Недоступный или некорректный язык приводит к `invalid_request`; если
словарь стал недоступен после проверки, сохраняется исходный русский текст,
чтобы не скрыть фактическую ошибку. Если JSON невозможно разобрать, выбрать
язык невозможно, и возвращается исходная ошибка на русском языке. Перевод
прочих интерфейсов и пользовательских текстов ещё не завершён.

## Операции

| Операция | Основные параметры | Результат и действие |
|---|---|---|
| `capabilities` | нет | Версии API и манифестов, список реально доступных операций и возможностей. |
| `validate` | объект публичного манифеста в `params.manifest` | Проверка декларации без эффектов; не подтверждает содержимое payload. |
| `preflight-fresh` | манифест v2, корень, расчёт места и резерв | Частичная проверка путей и места без записи; не подтверждает право установки. |
| `check-target` | манифест, объект `target` с `os`, `architecture`, `execution` | Сравнение только с декларацией продукта; не проверяет реальную машину. |
| `verify-package` | локальный путь, конверт подписи, доверенный ключ, ожидаемые продукт и версия | Проверка подписи и содержимого ZIP без извлечения и запуска. Требует `cryptography`. |
| `inspect-fresh-package` | данные проверки подписи, цель, корень и оценка места | Проверка подписанного манифеста, заявленной цели и путей без извлечения и записи. Требует `cryptography`. |
| `inspect-native-fresh-package` | данные проверки подписи, корень и оценка места | То же с определением ОС и архитектуры текущего процесса для `native`; не проверяет Docker. |
| `fresh-status` | данные проверки подписи и корень подготовки | Прочитать журнал конкретного проверенного выпуска без записи; готовность установки отдельно не подтверждается. |
| `check-local-health` | порт, публичные ID и версия, путь, timeout | Однократно проверить JSON-ответ на 127.0.0.1; личность процесса не подтверждается. |
| `check-docker-engine` | абсолютный путь CLI, независимый SHA-256, локальный socket и timeout | Выполнить проверки версий и справки без запуска контейнеров; доверие к CLI/plugin и готовность установки не подтверждаются. |
| `verify-native-release` | те же параметры, что у `fresh-status` | Сверить подписанный состав с файлами выпуска, указателем и журналом; не подтверждает готовность установки. |
| `update-plan-status` | исходный манифест v2, корень, выпуск, режимы, миграции и `guard_effects` | Прочитать проверенный checkpoint обновления, включая признак неизвестного исхода, без записи или выполнения. |
| `plan-update` | те же шесть полей, что у `update-plan-status` | Получить порядок компонентов, фаз обновления и отката и идентификатор плана без выполнения. |
| `prepare-signed-linux-update` | старый и новый подписанные пакеты, доверенные ключи, продукт/версии, установка, work-dir, режимы, миграции и ключ операции | Проверить текущий выпуск и подготовить новый payload, не запуская обновление или службы. |
| `plan-signed-compose` | подписанный пакет, доверенный ключ, цель Docker и режимы | Проверить рецепт и вернуть детерминированный план нескольких компонентов без запуска контейнеров. |
| `prepare-signed-compose` | те же параметры, защищённый каталог и ключ операции | Создать проверенный Compose-файл и устойчивую отметку без запуска контейнеров. |
| `inspect-signed-compose-images` | те же параметры, закреплённый Docker CLI, локальный socket и таймаут | Сверить ссылки по ответам daemon, не запуская и не скачивая образы. |
| `control-signed-compose` | параметры проверки образов, действие `start`/`stop` и отдельный ключ действия | Однократно запустить или остановить выбранные контейнеры с журналом состояния. |
| `compose-control-status` | параметры проверки образов, использованные при запуске | Прочитать связанный журнал без обращения к daemon и без разрешения восстановления. |
| `check-signed-compose-health` | параметры проверки образов, ключ подтверждённого запуска и таймаут health | Проверить подписанный loopback endpoint между двумя проверками контейнеров. |
| `install-portable-linux` | подписанный пакет и ключ, пути, режимы, оценка места и шесть сохранённых ключей операций | Подготовить выпуск и runtime, опубликовать и загрузить user-units, запустить службы и проверить loopback health. |
| `inspect-portable-linux-install` | тот же запрос и ключи, что для установки | Прочитать связанный checkpoint без выполнения шагов. |
| `inspect-signed-linux-update` | те же параметры, что использовались для подготовки | Проверить привязку и checkpoint начатого обновления, не продолжая его. |
| `inspect-update-recovery` | те же шесть полей, что у `update-plan-status` | Прочитать фазу и ключ текущей операции для диагностики, без выполнения или разрешения продолжения. |
| `import-update-archive` | манифест, установка, выпуск, режимы, миграции, work-dir, архив, доверенный SHA-256 и имя env пароля | Импортировать проверенный шифрованный архив в приостановленный guarded-откат; изменяет рабочий каталог, не запускает восстановление. |
| `prepare-native-release` | данные подписи, новый корень, оценка места и `idempotency_key` | Подготовить файлы и указатель первого нативного выпуска, не запуская продукт; запись в новый корень. |
| `plan` | идентификатор пакета, установка, вариант запуска | Проверенный план без записи в установку и запуска продукта. |
| `install` | идентификатор проверенного пакета, установка, вариант и ключ | Начать свежую установку; вернуть идентификатор операции. |
| `update` | установка, проверенный выпуск и ключ | Начать обновление с резервными копиями и откатом по контракту. |
| `status` | установка и идентификатор операции | Текущее состояние и результат без запуска новой операции. |
| `archive` | установка, назначение и ключ | Создать и проверить полный архив через защищённый канал пароля. |
| `restore` | установка, проверенный архив и ключ | Восстановить по проверяемому плану при остановленных писателях. |
| `resume` | установка и идентификатор операции | Возобновить только совместимую незавершённую операцию. |
| `uninstall` | установка, политика данных и ключ | Удалить принадлежащие установке ресурсы; данные сохраняются по умолчанию. |

`update-plan-status` принимает в `params` шесть обязательных полей: объект
`manifest`, абсолютный `install_root`, строку `release`, массив `modes`, массив
`migration_ids` (может быть пустым) и булево `guard_effects`. Все значения
должны соответствовать исходному плану, иначе возвращается
`update_status_failed`. Результат — `{"state": null}` либо проверенный
checkpoint; `indeterminate: true` требует проверки эффекта до повторного
исполнения. Эта операция не читает содержимое пакета, не доказывает здоровье
служб и не возобновляет транзакцию. Чтение без блокировки может увидеть
предыдущий или следующий атомарный checkpoint. Файл ограничен 16 КиБ и должен
быть обычным файлом; проверка инвариантов не является криптографической
аутентификацией состояния и не защищает от изменения тем же пользователем ОС.

`plan-update` принимает те же поля и возвращает `plan_sha256`, `components`,
`forward`, `rollback`, `guard_effects`, `execution_supported: false` и
`readiness_verified: false`. Идентификатор совпадает с полем `plan` checkpoint
при одинаковых параметрах плана; сам корень установки в него не входит. Фазы
`backup:N` и `migrate:N` относятся к индексам массива `migration_ids`. Операция
не читает checkpoint, не проверяет подписанный выпуск, остановку писателей,
совместимость, место или права и не выполняет обновление. Идентификатор не
является подписью или разрешением на выполнение; все проверки потребуются
непосредственно перед реальной операцией.

`inspect-update-recovery` принимает те же параметры. Для отсутствующего
checkpoint возвращаются `outcome`, `direction`, `phase`, `operation_key` со
значением `null`; для выполняющейся операции возвращаются направление, текущая
фаза и её устойчивый ключ. У завершённой операции фаза и ключ равны `null`.
`indeterminate` отражает только сохранённую отметку неопределённости.
`archive_binding_review_candidate: true` означает, что включён guarded-план,
его неопределённая фаза относится к копированию и может потребовать проверки
отметки архива. Это не подтверждение наличия, целостности, происхождения или
согласованности копии и не обещание, что восстановление возможно. Поля
`effects_verified` и `resume_authorized` всегда `false`. Результат —
наблюдение без блокировки, способное устареть; операции должны повторно
проверять состояние и получать блокировку. Метод не читает архивы и журналы
портов, не принимает пароли и не изменяет файлы. Ошибки используют существующий
локализованный код `update_status_failed`.

`import-update-archive` принимает `manifest`, абсолютные `install_root`,
`work_dir` и `archive`, `release`, `modes`, `migration_ids`, независимый
`expected_sha256` и `password_env` — имя переменной окружения процесса API,
не значение пароля. Нужен существующий guarded-checkpoint `restore` и
подтверждённая отдельная копия перед откатом. Операция записывает архив и отметку
в рабочий каталог; возвращает `archive_imported: true` и
`resume_authorized: false`, не возобновляет откат. При ошибке результат может
быть неопределённым и оставаться `pending`; произвольный повтор без анализа
не разрешён. Ошибка `update_archive_import_failed` локализована, содержимое
путей, пароль и причины из адаптеров не возвращаются. В `capabilities` операция
присутствует среди изменяющих только при доступной закреплённой криптобиблиотеке.

Пример клиента передаёт в дочерний процесс только явно указанный секрет с именем
`HOMENSAI_SECRET_*` через `secret_env_name`; в обычных вызовах окружение
очищено. Переменные окружения могут быть видны процессам с соответствующими
правами и не являются универсально защищённым каналом. API локальный, не имеет
сетевого транспорта или встроенной сетевой авторизации: его вызывающая сторона
отвечает за доступ, секрет, доверие к SHA-256 и остановку писателей.

```python
from examples.demo_product.installer_client import InstallerClient

result = InstallerClient().call('import-update-archive', {
    'manifest': manifest, 'install_root': '/absolute/install', 'release': '2',
    'modes': ['autonomous'], 'migration_ids': [], 'work_dir': '/absolute/work',
    'archive': '/absolute/backup.hsac', 'expected_sha256': trusted_sha256,
    'password_env': 'HOMENSAI_SECRET_BACKUP',
}, min_minor=27, language='en', secret_env_name='HOMENSAI_SECRET_BACKUP')
```

Перед вызовом интегратор отдельно предоставляет переменную
`HOMENSAI_SECRET_BACKUP` процессу клиента; её значение не включается в запрос.
Флаг `secret_env_name` разрешён только для этой операции и только при совпадении
с полем `password_env`. Клиент не повторяет изменяющие запросы автоматически.

Пример клиента с заранее загруженным манифестом:

```python
from examples.demo_product.installer_client import InstallerClient

status = InstallerClient().call('inspect-update-recovery', {
    'manifest': manifest, 'install_root': '/absolute/install/path',
    'release': '2', 'modes': ['autonomous'], 'migration_ids': ['schema-2'],
    'guard_effects': True,
}, min_minor=26, language='en')
```

`prepare-signed-linux-update` принимает `new_package`, `new_envelope`,
`new_key`, `old_package`, `old_envelope`, `old_key`, `product_id`,
`old_version`, `new_version`, `install_root`, `work_dir`, `modes`,
`migration_ids` и `idempotency_key`. Пути абсолютные; подписи и открытые ключи
передаются в каноническом base64. Ключи должны быть доверены независимо от
пакетов. На Linux x86-64 операция сверяет подписанный текущий выпуск,
совместимость манифестов и цели, затем под блокировками подготавливает отдельный
payload. Рабочий каталог заранее создан с правами 0700 и находится вне установки.
Успех не означает запуск обновления, проверку runtime или служб. Идентичный
повтор проверяет ранее созданные файлы; `pending` требует разбора, а не слепого
повтора. В `capabilities` операция объявлена изменяющей при доступной проверке
подписи и поддерживаемой среде. Ошибка `update_prepare_failed` не содержит
входные пути или детали исключения. См. ограничения в `UPDATE.md`.

`inspect-signed-linux-update` принимает те же параметры и доступен с API 1.30.
Он проверяет подписи, привязку к исходной установке и подготовке, checkpoint,
старый и подготовленный новый выпуск, а также новый выпуск, если он уже
размещён. Ответ содержит `state`, `payload_name`, `plan_sha256`,
`effects_verified: false` и `resume_authorized: false`. Отсутствие начатой
транзакции, неподтверждённые данные или занятая блокировка возвращают
обобщённую ошибку `update_inspect_failed`. Службы, миграции и восстановление
не запускаются. Поскольку проверка берёт и записывает служебные блокировки,
она указана в `mutating_operations`; результат не подтверждает состояние
служб, успешность неопределённых эффектов или разрешение на продолжение.

```python
from examples.demo_product.installer_client import InstallerClient

# prepare_params — тот же словарь с путями, подписями, ключами и idempotency_key,
# который использовался при подготовке данного обновления.
inspection = InstallerClient().call('inspect-signed-linux-update', prepare_params,
                                    min_minor=30, language='ru')
checkpoint = inspection['state']
```

`install-portable-linux` доступен с API 1.31 на Linux x86-64 и объявлен
изменяющей операцией: он создаёт файлы, загружает и запускает службы. Поля:
`package_path`, `envelope`, `trusted_public_key`, `expected_product_id`,
`expected_version`, `install_root`, `unit_dir`, `work_dir`, `modes`,
`required_bytes`, `reserve_bytes`, `workflow_key`, `keys`. Объект `keys`
содержит пять разных ключей `release`, `runtime`, `publish`, `load`, `start`;
шестой ключ `workflow_key` также должен отличаться. Подпись и открытый ключ —
канонический base64; ключ издателя должен быть доверен независимо от пакета.
Пути и защищённый рабочий каталог описаны в FRESH-CONTROLLER.md.

Вызов синхронный и может занять продолжительное время. При ошибке, таймауте
клиента или прерывании изменения могли произойти; точный запрос и ключи нужно
сохранить и проверить журнал перед повтором. Незавершённый шаг обращается к
своему порту с тем же ключом, но неопределённый эффект может требовать ручной
проверки. `fresh_controller_failed` не включает входные данные. Ответ не
подтверждает текущее состояние после предыдущего успешного вызова, подлинность
процесса или завершённость установки. Это не установка Windows или Docker.

`inspect-portable-linux-install` принимает точно те же параметры, что и
`install-portable-linux`. Он проверяет подпись пакета и привязку checkpoint,
но не запускает шаги и не проверяет их фактические последствия. Ответ содержит
`state` (`no_checkpoint`, `pending`, `recorded_complete`), `completed_steps`,
`total_steps`, `current_step`, `step_may_have_executed` и явно ложные
`effects_verified`, `current_health_verified`, `resume_authorized`,
`installation_complete`. При `no_checkpoint` число выполненных шагов и признак
возможного выполнения неизвестны (`null`): отсутствие журнала не доказывает
отсутствие изменений. При `pending` текущий шаг мог начать или завершить эффект.
Операция объявлена изменяющей из-за записи служебной блокировки. Возобновление
остаётся отдельным вызовом и может требовать разбора неопределённого состояния.

`plan-signed-compose` принимает `package_path`, `envelope`, `trusted_public_key`,
`expected_product_id`, `expected_version`, `target`, `modes` и `instance_id`
(32 строчных hex символа для конкретной установки). Подпись и ключ
передаются в каноническом base64; доверие к ключу устанавливается отдельно.
Ответ включает `compose_json`, `compose_sha256`, выбранные `components` и цель.
Ошибки подписанного рецепта возвращают `docker_plan_failed` без входных путей.
Хост, образы и запуск не подтверждаются; процесс ничего не пишет и не запускает.
Формат рецепта и ограничения описаны в [DOCKER-ADAPTER.md](DOCKER-ADAPTER.md).

`prepare-signed-compose` принимает те же поля и дополнительно `work_dir` и
`idempotency_key`. На Linux x86-64 операция записывает файл и durable отметку
в защищённом каталоге; она объявлена изменяющей. Повтор с тем же ключом
перепроверяет данные, незавершённое `pending` требует разбора, существующие
чужие файлы не заменяются. Ответ включает `compose_name`, `compose_sha256` и
`instance_id`, но не подтверждает Docker, образы и запуск. Ошибка
`docker_prepare_failed` не включает исходные пути или детали исключений.

`inspect-signed-compose-images` принимает параметры подготовки и дополнительно
`executable`, `executable_sha256`, `socket_path`, `timeout_seconds` (1–30).
Поддерживается Linux x86-64 с целью Linux Docker. Ответ сообщает лишь, что
доверенный daemon вернул ожидаемые ссылки: `daemon_reported_matches: true`;
байты и издатель образов не проверяются. Из-за временной конфигурации, файловой
блокировки и вызова CLI операция считается изменяющей. Ошибка
`docker_images_failed` не содержит входных путей. Условия и ограничения — в
[DOCKER-ADAPTER.md](DOCKER-ADAPTER.md).

`compose-control-status` принимает те же поля, что `inspect-signed-compose-images`,
включая `timeout_seconds` (1–120) для совместимости формы; таймаут не используется,
поскольку внешние команды не выполняются. Пакет, подготовка и привязка журнала
проверяются заново; socket и CLI могут отсутствовать. Ответ содержит `state`:
`not_recorded`, `start_pending`, `running`, `stop_pending` или `stopped`, а также
`receipt_present`, `daemon_state_verified: false`, `recovery_authorized: false`.
Это запись о ранее подтверждённом состоянии, а не текущая проверка daemon;
отсутствие журнала не доказывает отсутствие контейнеров. Ручное изменение файла
не аутентифицируется; каталог и его владелец должны быть доверенными. Операция
создаёт или обновляет служебные файлы блокировок и поэтому объявлена изменяющей.
Она не восстанавливает состояние и не разрешает повтор.

`control-signed-compose` принимает те же параметры, что проверка образов, и
поля `action` (`start`, `stop`, `reconcile-start` или `reconcile-stop`) и
`action_id` (32 строчных hex символа).
`idempotency_key` указывает ключ подготовки Compose, а каждый `action_id`
должен быть другим и сохранён вызывающей стороной. Таймаут команды — 1–120
секунд; общая граница ожидания команд составляет до 300 секунд, плюс время
проверки файлов. API выполняет действия, не скачивая и не собирая образы.
Для каждого контейнера API сравнивает идентификатор его образа с идентификатором,
полученным по подписанной digest-ссылке, повторяя проверку ссылки и идентификатора.
Тег из `Config.Image` не используется как доказательство. Эти проверки зависят
от доверенного daemon и не являются атомарными относительно внешних изменений.
При всех подтверждениях состояния также сверяются хэши модели Compose с метками
контейнеров и повторно проверяется состав. Метка может быть подделана и не
доказывает всех фактических настроек контейнера.
API 1.41 отдельно сверяет ответ daemon о команде и entrypoint, пользователе,
read-only корне, привилегиях, devices, отдельных пространствах имён, security
options, именованном томе, сети и портах. При проверке CapDrop принимается
`ALL` или явно перечисленные базовые capabilities; это не доказывает отсутствие
всех возможных capabilities у процесса. Не проверяются все параметры движка,
содержимое образов или работающие внутри контейнера процессы. Ответ daemon
остаётся доверенным, а изменения во время нескольких запросов не исключены.
Контейнер не должен содержать неожиданные переменные относительно окружения
образа: допускаются ограниченные системные значения PATH, TERM и container,
а дополнительный HOSTNAME — только соответствующий идентификатору контейнера. Повторяющиеся
имена и изменённые значения образа отклоняются. Безопасность самого окружения
образа таким сравнением не подтверждается.
Ошибка `docker_control_failed` может означать частично выполненную операцию.
Неопределённое `pending` блокирует автоматический повтор. Для согласования
передаётся прежний ключ соответствующего start/stop и действие
`reconcile-start` или `reconcile-stop`: проверяются все ожидаемые контейнеры,
их состояние и образы, хэши `compose config --hash '*'`, соответствующие метки
контейнеров и неизменность состава. Если всё совпало, обновляется только журнал;
команды `up` и `stop` не повторяются. Частичный состав, отсутствующие ресурсы
или несовпадения оставляют операцию в `pending`. Это не доказывает здоровье
приложений, подлинность меток, отсутствие внешних писателей или безопасность
образа. Daemon, CLI, каталог и все управляющие процессы должны быть доверенными;
несколько проверок не атомарны. Повторные циклы,
удаление и восстановление данных не поддерживаются. Подробные условия и
ограничения описаны в [DOCKER-ADAPTER.md](DOCKER-ADAPTER.md).

`check-signed-compose-health` принимает поля `inspect-signed-compose-images`,
`action_id` подтверждённого запуска и `health_timeout_seconds` (1–30). Порт,
путь, продукт и версия берутся из проверенного подписанного пакета; клиент не
может подставить другой адрес. До и после HTTP-запроса состояние контейнеров
проверяется через CLI. Отсутствующий или остановленный запуск не запускается
автоматически. Возвращаются `health_response_matches: true` и
`daemon_state_verified: true`, но `process_identity_verified`,
`all_components_healthy` и `installation_complete` остаются `false`: другой
локальный процесс может имитировать ответ, а HTTP-проверка не подтверждает все
компоненты. При любой ошибке возвращается `health_check_failed` без подробностей.
Проверки не атомарны; операция создаёт временные файлы и блокировки и выполняет
доверенный CLI, поэтому объявлена изменяющей.

`check-docker-engine` принимает `executable`, `executable_sha256`,
`socket_path` и `timeout_seconds` (1–10 на команду). Для Linux нужен
абсолютный путь Unix socket, для Windows — `null` и фиксированный именованный
канал. Процесс API использует временную пустую Docker-конфигурацию и выполняет
только запросы версий и справки. В результате `client_version`, `compose_version`
и `server_version` содержат проверенные версии или `null`,
`compose_flags_present` указывает наличие названий двух флагов в справке;
`installation_ready` и `images_verified` всегда `false`. CLI и plugin должны
быть доверенными, хэш CLI предоставляется независимой стороной. Это запуск
внешних процессов, поэтому операция указана в `mutating_operations`; доступ к
ней должен ограничиваться доверенным локальным вызывающим. Несовпадение хэша
даёт локализованную ошибку `docker_preflight_failed`. Подробности и границы —
в `DOCKER-ADAPTER.md`.

Конкретные поля и ограничения параметров будут формализованы в схеме и
проверены до предоставления API. Пароль/значения секретов передаются отдельным
каналом полномочий вызывающей стороны, а не в публичном JSON; реализация этого
канала зависит от платформы. Прямой пароль в переменной окружения не считается
универсально защищённым решением. `plan` не даёт разрешения на последующее
изменение состояния: перед действием нужно повторно проверить актуальные факты.

Ранняя схема запросов — `shared/api-v1-request.schema.json`; манифест внутри
`validate` отдельно проверяется существующим валидатором v1/v2. В Python:
`from shared.api import handle`, затем `handle(request)`. CLI: передать один
JSON в stdin `python -m shared.api`, прочитать один JSON из stdout; аргументы
командной строки отклоняются. Например:

```json
{"api_major":1,"operation":"capabilities","request_id":"example-1","params":{}}
```

Ограничение stdin — 1 МиБ, вложенности — 64, узлов — 50 000, длины строки —
8192 символа. Python API проверяет структуру и циклы, но байтовый лимит stdin
к нему не применяется; общие ссылки на один контейнер также отклоняются. Поля
`request_id` и `product_id` считаются публичными и могут вернуться вызывающему;
они не должны содержать секретов. Продуктовый код интерфейс не запускает.
Эти операции ещё не составляют готовый установщик. Поле
`capabilities.mutating_operations` отдельно перечисляет операции с записью;
при недоступной криптографии список подготовки пуст.

`check-target` (API 1.3) принимает `manifest` и `target`, например
`{"os":"windows","architecture":"x86_64","execution":"native"}`.
Результат `status` — `supported`, `unsupported` или `unknown`, если декларации
нет. Утверждение `supported` означает только совпадение с декларацией: проверка
фактической ОС, Docker, зависимостей и безопасности пакета не выполняется.
До выбора способа установки эти проверки должны выполняться отдельно.

`preflight-fresh` (API 1.2) принимает `manifest`, абсолютный `install_root`,
`required_bytes` со всеми семью ключами путей и `reserve_bytes`. Все оценки
места — целые неотрицательные байты, предоставленные клиентом. Результат
включает обязательный список непроверенных факторов `not_checked`; поля путей
являются публичными и возвращаются клиенту. Ошибка состояния путей/места —
`preflight_failed` с кодом CLI 1. Проверка не создаёт блокировок и ничего не
устанавливает; см. `PREFLIGHT.md`.

`inspect-fresh-package` (API 1.5) объединяет параметры `verify-package` с
`target`, `install_root`, `required_bytes` и `reserve_bytes` из соответствующих
проверок. Манифест берётся только из проверенного подписанного пакета; отдельный
манифест запроса отвергается. Неподтверждённая или отсутствующая декларация
цели даёт `target_not_supported`. При успехе возвращаются `declared_target` и
результат частичной проверки путей. Подпись подтверждается перед проверкой
декларации, однако клиент сам выбирает доверенный ключ и оценку места.
Вложенный `preflight.not_checked` описывает только проверку путей, поэтому в
нём остаётся `package_authenticity`, хотя внешняя операция проверяет подпись.
Проверка хоста, среды, прав, зависимостей и соответствия выбранной цели
реальной машине остаётся за вызывающим кодом. Проверка действует только на
момент вызова: повторная проверка пакета и состояния до установки обязательна.
Этот вызов не извлекает пакет и не разрешает выполнение кода.

`inspect-native-fresh-package` (API 1.6) принимает те же данные, кроме `target`:
цель формируется из ОС и архитектуры текущего Python-процесса, а способ запуска
задаётся как `native`. Поддерживаются обнаруженные Linux x86_64 и Windows x64
при 64-битном процессе; прочие или неопределённые платформы дают
`unsupported_platform`. Подписанный манифест по-прежнему должен явно включать
полученную цель. Ответ содержит `process_target`. ОС и архитектура определяются
изнутри текущей среды: контейнер, эмуляция или совместимый слой могут отличаться
от физического компьютера. API 1.11 также требует новый корень с существующим
родительским каталогом, проверяет расположение путей и возвращает
`storage_estimate` с `minimum_bytes`, `reserve_bytes` и
`free_bytes` для его устройства. Нижняя оценка учитывает временную копию ZIP,
две копии payload и внутренний резерв архиватора; при недостатке места
возвращается `preflight_failed`.
Это не полная оценка будущих данных, зависимостей и служб. Доступность Docker,
режим контейнеров, версии ОС,
фактические права, зависимости и безопасность содержимого не проверяются.
Эта операция остаётся предварительной и не запускает установку.

`fresh-status` (API 1.7) принимает те же `package_path`, `envelope`,
`trusted_public_key`, `expected_product_id`, `expected_version`, что и
`verify-package`, и абсолютный `install_root`. Он проверяет подпись и сверяет
продукт, версию, корень, ключ и текущую цель с журналом подготовки формата 3 или 4.
Ответ содержит публичные `transaction`, `product_id`, `version`,
`reported_status` (`preparing` или `prepared`) и всегда
`completion_verified: false`. Это состояние журнала на момент чтения, а не
подтверждение целостности размещённого выпуска, наличия служб или работоспособной
установки. Во время работы записи статуса могут измениться; перед действием
необходимы отдельные повторные проверки и блокировка. Если пакет или журнал
недоступен, не совпал или повреждён, возвращается общий `fresh_status_failed`
с кодом CLI 1; входные пути и содержимое не выводятся. При отсутствии
криптографии операция не объявляется в `capabilities`. Она ничего не записывает,
не возобновляет подготовку и не выполняет продуктовый код.

`verify-native-release` (API 1.10) принимает ровно те же параметры, что
`fresh-status`. Он проверяет подпись и платформу, подготовленный журнал,
указатель и точные пути, размеры и SHA-256 файлов размещённого выпуска,
отклоняет лишние файлы и каталоги. Успех возвращает `release_files_match: true`
и `installation_complete: false`; ошибка — `fresh_verify_failed`. Операция
только читает файлы и не запускает продукт. Она не проверяет зависимости в
активном окружении, миграции, службы, здоровье приложения и данные пользователя.
Проверка не блокирует одновременные изменения и не защищает от процесса с теми
же правами; её результат описывает наблюдение во время вызова, а не разрешение
на последующее исполнение. Перед действием потребуются блокировка, защита
каталога и повторная проверка. Ожидаемый ключ и версия должны приходить из
независимого доверенного канала. Сверка использует перечень подписанного
выпуска и не применяет к старому выпуску текущий lock-файл сборщика.

`check-local-health` (API 1.12) принимает ровно `port` (1–65535),
`product_id`, `version`, `path` и `timeout_seconds` (целое 1–30). Операция
делает один HTTP-запрос только к `127.0.0.1`, без прокси и перенаправлений;
контракт JSON и ограничения ответа описаны в `HEALTH.md`. При совпадении
возвращаются `health_response_matches: true` и
`process_identity_verified: false`, при ошибке — `health_check_failed`.
Она не проверяет подпись запущенного процесса: другой локальный процесс может
подделать ответ. Таймаут относится к операциям сокета, а не гарантированному
суммарному времени; вызывающий клиент должен предусмотреть собственный срок.
Операция не запускает приложение и не подтверждает полную установку.

`prepare-native-release` (API 1.8) принимает параметры
`inspect-native-fresh-package` и обязательный `idempotency_key`: ровно 32
строчные шестнадцатеричные цифры. Клиент генерирует случайный ключ для одной
операции и сохраняет его вместе с исходным запросом. Первый вызов создаёт
новый корень и записывает проверенный выпуск и указатель; `installation_complete`
всегда `false`: миграции, службы и запуск не выполняются. Ответ включает
`transaction`, `product_id`, `version`, `status` и `process_target`.

Повтор с тем же ключом, путём пакета, конвертом подписи, оценками места,
ожидаемыми продуктом/версией, ключом издателя и корнем возвращает прежний
результат или пытается продолжить частичную подготовку. `request_id` и язык
не входят в идентичность действия. Изменённая оценка, другой ключ операции
или иное действие на уже связанном корне отклоняются; часть конфликтов
возвращается как `conflict`, прочие непроверенные/ошибочные состояния — как
`fresh_prepare_failed`. Содержимое другого пакета, подпись и журнал повторно
проверяются; совпадение одного пути или одного ID недостаточно. Для уже
подготовленного выпуска повторный запрос под блокировкой также сверяет указатель
и полное дерево выпуска с подписанным перечнем. При изменениях повтор не
заявляет успех и не восстанавливает и не удаляет изменённые файлы; пользовательские
данные не затрагиваются. Проверка не защищает от изменения процессом с теми же
правами и не удостоверяет работу приложения.

При параллельном вызове или прерывании клиент получает ошибку и может позже
повторить тот же запрос; `fresh-status` позволяет прочитать доступный журнал.
Авария до создания журнала, неполный `prepared` и посторонние данные не
восстанавливаются автоматически. Ожидаемые ключ и версия предоставляются из
доверенного канала; защита от подмены ключа вызывающей стороной и отката версии
ещё не реализована. Это локальный вызов с правами вызывающего процесса, не
сетевая служба и не песочница. Каталог родителя и права должны быть защищены.

`verify-package` (API 1.1) принимает ровно `package_path` (абсолютный путь на
текущей ОС), `envelope` (base64 байтов подписанного JSON), `trusted_public_key`
(base64 32 байтов Ed25519), `expected_product_id`, `expected_version`.
Проверка требует ключ и ожидания из доверенного независимого источника.
Конверт и ключ — публичные данные; закрытый ключ никогда не передаётся в API.
Клиент должен проверить `capabilities.operations`, прежде чем вызывать этот
метод: при недоступной зависимости операция не объявляется и явно отказывает.
Ответ содержит product ID, версию и число файлов, но не содержимое пакета;
ошибки не раскрывают путь или входной конверт. Ошибка проверки возвращает
`verification_failed` и код CLI 1, неправильный запрос — `invalid_request`
и код 2. Вызов не извлекает и не исполняет файлы. Результат относится к моменту
проверки; если файл позже заменят, его нужно проверять снова. Эта операция не
является хранилищем доверенных ключей и не выдаёт разрешение на установку.

## Операции, повторы и отказ

Изменяющая операция получает идентификатор, сохраняет состояние и блокировку
установки до эффектов и сообщает `running`, `succeeded`, `rolled_back` или
`recovery_required`. Вызовы `status`/`resume` возвращают проверенное состояние
по идентификатору. Повтор с тем же ключом и тем же каноническим запросом
возвращает существующую операцию; другая нагрузка с тем же ключом — `conflict`.
Ключи, подтверждения и состояние переживают перезапуск. Если результат внешнего
эффекта после сбоя нельзя достоверно определить, автоматического повтора нет:
возвращается `recovery_required`. Повторяемость и exactly-once на внешних
командах не гарантируются одним только API; адаптер обязан предоставить
надёжный механизм подтверждения. Статус `rolled_back` не равен успеху update.

## Передача другим продуктам

После реализации и приёмки публикуются версия контракта, схема, инструкция,
минимальный клиент и независимый тестовый пример. Для каждого продукта отдельно
проверяются его адаптер, версии, зависимости, секреты и сценарии отказа.
Копирование одной инструкции в репозиторий не подключает продукт автоматически.
Список репозиториев и фактическое распространение определяются на следующем
этапе после принятия контракта.
