# Экспериментальная подготовка Linux runtime

## Сборка кандидата блока

`python -m shared.runtime_block --source /absolute/input --lock /absolute/runtime-lock.json
--destination /absolute/payload/runtime-linux` подготавливает блок из заранее
полученных локальных файлов. Сеть не используется, код не запускается.
Назначение должно быть новым, а перечень находиться вне источника и назначения.
Файл перечня содержит, например:

```json
{"format":1,"target":{"os":"linux","architecture":"x86_64"},"python_version":"3.14.10","origin":"https://example.org/runtime/release","license":"PSF-2.0","license_files":["licenses/LICENSE"],"executables":["bin/python"],"files":[{"path":"bin/python","size":123,"sha256":"0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"},{"path":"licenses/LICENSE","size":42,"sha256":"0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"}]}
```

Числа и хэши примера условны. Адрес источника — HTTPS без данных пользователя,
параметров запроса и фрагмента. В реальном перечне должны быть точные размеры и
SHA-256 каждого файла; списки файлов и имён сортируются. Файлы лицензии должны
быть непустыми, находиться под `licenses/` и входить в перечень. Блок включает исходный перечень как
`runtime-provenance-v1.json`, файлы и сгенерированный `runtime-v1.json`.
Необязательный `artifact_sha256` в перечне фиксирует хэш исходного архива;
обычная проверка блока проверяет формат этого поля, но не имеет самого архива
для его повторного сравнения.
Сборщик ZIP повторно проверяет согласованность распознанного блока до упаковки.
Отдельная `verify_runtime_block` проверяет его без сборки; проверка готового ZIP
повторно сверяет описание, рецепт и состав распознанного блока. Эти проверки
не подтверждают подлинность источника или отсутствие вредоносного кода.

Источник, SPDX-идентификатор, версия Python и лицензии являются заявлениями
автора перечня. Хэши не устанавливают доверие к источнику, отсутствие вредоносного
кода, ABI, полный состав зависимостей и право распространения. Перед выпуском
нужны независимая проверка источника, ключей, лицензий всех компонентов, целевой
ОС и воспроизводимости. Конкретный сторонний runtime этой операцией не выбран и
не включён в репозиторий.

При ошибке после создания назначения может остаться маркер
`.homensai-runtime-incomplete`; ZIP-сборщик отклоняет такой маркер на любом
уровне payload. Авария между созданием каталога и маркера возможна, поэтому
отсутствие маркера само по себе не доказывает успех. Подготовка не защищает от
подмены файлов процессом с теми же правами; исходные файлы, сборочную среду и
закрытый ключ подписания необходимо защищать отдельно.

## Кандидат Python Build Standalone

[Выпуск 20261026](https://github.com/astral-sh/python-build-standalone/releases/tag/20261026)
содержит `cpython-3.14.10+20261026-x86_64-unknown-linux-gnu-install_only_stripped.tar.gz`;
GitHub указывает SHA-256
`4d3c16c59ed0802a3d1d34d8bce504b15ceeaff39d62dadecc6a9fa803412aed`.
Локально скачанный архив размером 36 776 589 байт с этим хэшем исследован
02.11.2026. Это предварительный кандидат, а не принятый компонент выпуска.

```sh
python -m shared.runtime_pbs --archive /absolute/python.tar.gz \
  --destination /absolute/payload/runtime-linux \
  --sha256 4d3c16c59ed0802a3d1d34d8bce504b15ceeaff39d62dadecc6a9fa803412aed \
  --origin https://github.com/astral-sh/python-build-standalone/releases/download/20261026/cpython-3.14.10%2B20261026-x86_64-unknown-linux-gnu-install_only_stripped.tar.gz \
  --python-version 3.14.10
```

Команда работает офлайн, требует внешний хэш, проверяет ограниченный поток TAR,
отклоняет расширенные заголовки, специальные файлы, неоднозначные имена,
опасные и циклические ссылки. Ссылки на файлы внутри архива материализуются в
обычные файлы, `share/terminfo` исключается из-за регистрозависимых конфликтов.
Утилита сохраняет обнаруженные файлы с лицензиями и уведомлениями в `licenses/`,
а исходный хэш архива — в подписываемом описании блока. Она не исполняет код.
Пока состав лицензий не проверен, блок помечается
`LicenseRef-Composite-Unreviewed`, а не одной лицензией всего runtime.
Исключение terminfo может повлиять на терминальные приложения; лицензирование
встроенных компонентов и совместимость конкретных ОС требуют отдельной проверки.
Утилита не является песочницей для недоверенного архива; хэш должен поступать из
доверенного независимого источника. Образ Python, сборочная среда и файлы
временного каталога также должны быть доверены.

Авторы указывают на [различные лицензии Python и его зависимостей](https://github.com/astral-sh/python-build-standalone/blob/main/docs/running.rst#licensing).
`install_only` [не содержит полного `PYTHON.json`](https://github.com/astral-sh/python-build-standalone/blob/main/docs/distributions.rst#install-only-archive),
поэтому автоматический сбор заметок не доказывает полноту лицензионной ведомости.
Совпадение хэша с данными того же GitHub не является независимой проверкой
происхождения, а наличие текстов лицензий само по себе не разрешает выпуск.

При наличии полного архива того же выпуска `pgo+lto-full.tar.zst` можно добавить
`--full-archive /absolute/full.tar.zst --full-sha256 HASH`. Для исследованного
архива SHA-256: `4a2823d5deacb631e21b3c8387a1ec9be57e1b0ed37b7770e2e71cfe7b94eb94`.
Утилита проверяет размер, TAR-заголовки, хэш и основные поля `PYTHON.json`, а
также совпадение лицензии CPython из каталога установки в обоих архивах.
Для полного архива требуется доступный модуль `compression.zstd` Python 3.14;
окно распаковки ограничено 128 МиБ, а суммарный распакованный размер — 1 ГиБ.
Она сохраняет `PYTHON.json` и найденные лицензионные тексты полного архива в
`licenses/upstream-full/`, а хэш полного архива — как `evidence_sha256`.
Это сопоставление не доказывает криптографически, что два архива являются
парой сборок, и не является полным SBOM или юридической проверкой. Метаданные
для этого выпуска указывают 109 расширений, разные лицензии зависимостей и
динамическую glibc; конкретные обязательства и источники нужно проверить.

Для сквозного теста с заранее загруженными архивом и wheels используется
`python3 tests/run_isolated_pbs_test.py --run --archive /absolute/python.tar.gz
--wheelhouse /absolute/wheels`: отдельный rootless Podman без сети, исходники и
входы только для чтения. Для теста с полным архивом дополнительно передают
`--full-archive /absolute/full.tar.zst`. Тест выполняет интерпретатор **внутри контейнера**;
это не замена приёмке на целевых системах. Wheels pytest нужны только для теста.

## Подготовка на целевой системе

`shared.runtime_native.prepare_signed_linux_runtime` формирует план или
копирует файлы runtime из уже подготовленного подписанного выпуска в пустой
каталог `runtime` установки. Это ограниченный Python-интерфейс, не законченный
механизм поставки и не проверка безопасности программы.

В подписанном payload находится `runtime-linux/runtime-v1.json`:

```json
{"format":1,"target":{"os":"linux","architecture":"x86_64"},"python_version":"3.14.10","executables":["bin/python"]}
```

Все остальные файлы под `runtime-linux/` входят в подписанный состав и
копируются в `runtime/` без префикса. Список `executables` должен быть
отсортирован, содержать `bin/python` и ссылаться только на файлы состава.
Исполняемым назначается режим 0700, остальным файлам 0600, каталогам 0700.
Ссылки, посторонние файлы и неожиданные права при проверке результата
запрещены. Версия и целевая платформа — декларации подписанного рецепта;
установщик не исполняет бинарный файл и не проверяет его фактическую версию,
ABI, зависимости ОС, лицензию, происхождение или отсутствие вредоносного кода.

Вызов по умолчанию возвращает план. Запись требует `execute=True` и отдельного
`operation_id` из 32 строчных шестнадцатеричных символов. Она выполняется под
блокировками, после проверки места и подписи, с созданием файлов без
перезаписи. При ошибке или прерывании отметка `pending` и частичные файлы
сохраняются; автоматический повтор запрещён. Подтверждённый `done` при повторе
проверяет точный состав, байты и права без перезаписи. До ручного разбора
частичные файлы не следует запускать. Автоматическое восстановление, обновление
runtime и защита от кода с теми же правами пользователя ещё не реализованы.

Локальный API версии 1.18 предоставляет операции `plan-linux-runtime`,
`prepare-linux-runtime` и `verify-linux-runtime`. Все они принимают путь к
пакету, envelope и доверенный ключ в base64, ожидаемые идентификатор продукта и
версию, корень установки и `reserve_bytes`. Для подготовки и проверки нужен
`idempotency_key`: проверка требует тот же ключ и параметры, что у завершённой
подготовки. Она сверяет подпись, состав, содержимое и права без создания или
изменения файлов и не запускает интерпретатор. При отсутствии завершённой
записи или несовпадении проверка отказывает. Подготовка может оставить
частичные файлы при ошибке; не следует считать ошибку отсутствием изменений.

Отдельная экспериментальная Python-функция
`portable_signed_runtime_user_group` связывает подтверждённую переносимую
группу служб с параметрами уже выполненной подготовки runtime. При каждом
явном `start` группы она проверяет runtime до отправки команд службам;
ошибка проверки блокирует запуск. Планирование и остановка не требуют такой
проверки. Эта обёртка не является портом обновления и не подключена к запуску
напрямую через API; другие способы запуска служб её не используют. API 1.19 отдельно
предоставляет `check-portable-linux-start` для проверки runtime и загруженных
остановленных служб без запуска; подробности и влияние опроса менеджера —
в `API-DESIGN.md`. API 1.20 предоставляет ограниченный первый запуск через
`start-portable-linux` с отметкой результата и отказом повторять `pending`.
API 1.21 добавляет остановку через `stop-portable-linux` без проверки runtime;
остановка и запуск через эти операции используют общую блокировку.
Проверка не исключает
изменение файлов после проверки или обход со стороны кода с теми же правами.
Планировщик systemd отдельно не гарантирует, что runtime подготовлен. Для
реальной поставки необходимо закрепить происхождение, точные версии, хэши,
лицензии и зависимости целевой ОС и проверить запуск и восстановление на ней.
Тест с CPython использует файлы из одноразового образа только в контейнере;
это не утверждение о лицензировании или пригодности готового дистрибутива.
В этом тесте после отдельной подготовки runtime и публикации переносимых units
тестовый код запускает web и worker через Python-группу и проверяет ответ и
heartbeat. Сам runtime использует также системные библиотеки контейнера;
происхождение и готовность автономной поставки этим не подтверждаются.
