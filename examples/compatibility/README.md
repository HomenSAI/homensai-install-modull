# Примеры декларации совместимости

Все четыре манифеста описывают **вымышленные** продукты и используют один и
тот же каталог `payload`. Декларация перечисляет допустимые сочетания в
манифесте; отдельные пакеты для каждой системы не требуются.

| Манифест | Заявленные цели x86-64 |
|---|---|
| `windows-native.json` | Windows, нативный запуск |
| `linux-native.json` | Linux, нативный запуск |
| `windows-native-docker.json` | Windows, нативный запуск и Docker |
| `all-targets.json` | Windows и Linux, нативный запуск и Docker |

`payload` содержит только текстовые тестовые заглушки. Файл с расширением
`.whl` намеренно **не является wheel**, lock-файлы не описывают реальные
зависимости, а команды компонентов ссылаются на несуществующий продукт.
Эти файлы предназначены для проверки инвентаря, а не установки или исполнения.
Хэши в манифестах соответствуют этим точным тестовым байтам.

Пример проверки манифеста и выбора цели через Python API:

```python
from shared.manifest import check_target, load_manifest

manifest = load_manifest('examples/compatibility/windows-native-docker.json')
target = {'os': 'windows', 'architecture': 'x86_64', 'execution': 'docker'}
assert check_target(manifest, target) == {'status': 'supported'}
```

Аналогичный локальный JSON API: операция `check-target`, параметры `manifest`
и `target`; пример транспортного клиента — в `examples/demo_product/README.md`.
Ответ означает только совпадение с декларацией, а не проверку реальной ОС,
Docker, runtime, лицензий или безопасности. Архитектуры кроме x86-64 текущая
схема не принимает. Нативная подготовка может использовать эти декларации при
проверке подписанного пакета; реализация полного Docker-сценария ещё не готова.
