## 1. Итог

**Готовность не 100 %.** Модуль умеет собирать подписанный установочный
комплект и ставить, обновлять, откатывать и удалять продукт на Linux
(user-systemd) и Windows (службы) без Docker. Это проверено сквозными
сценариями на демо-продукте. Принятого выпуска нет, реальный продукт (Rent)
ещё не подключён, Docker-комплекта нет, а криптоаудит нашёл пробел, из-за
которого «строгий» режим обновления не даёт обещанной защиты.

  откат при ошибке, проверка здоровья, удаление с сохранением данных и

- Секреты продукта (шаги 73, 76): объявление в подписанном выпуске, файл
  владельца вне корня установки, команда `setup secrets`.
- Полный архив данных с шифрованием, копии перед миграцией и откатом.
- Публичный локальный API (JSON/CLI), локализация ru/en/de.
- Находки прошлого аудита A-01 — A-10 исправлены
  ([AUDIT-REPORT](AUDIT-REPORT.md#статус-исправлений-добавлено-после-аудита)).

## 4. Криптоаудит: подпись и цепочка поставки

### К-1. Высоко — неподписанный код установщика становится «доверенным»

- **Где:** `shared/kit_setup.py:281-309` (`store_installer`), вызовы из
  `install`, `_consolidate` и `kit_windows.py:601, 732`;
  `finish_installer` (`kit_setup.py:317-331`) выполняется в `locked()` до
  `check_key`. Код установщика (`installer/app`, встроенный Python) и
  `SHA256SUMS` лежат вне подписанного пакета (`shared/kit.py:567, 590-594`).
- **Суть:** подпись покрывает только `package/*.zip`. После успешного
  обновления установщик копирует неподписанный код из нового комплекта в
  сохранённую «доверенную» копию `<state>/installer`. Поэтому
  рекомендованный в [KIT.md](../KIT.md) «строгий» режим (обновлять
  сохранённым установщиком) защищает только одно обновление.
- **Атака:** злоумышленник с доступом к каналу доставки берёт подлинный
  подписанный комплект и меняет только `installer/app/shared/*.py` или
  встроенный Python. Подпись пакета верна, ключ совпадает с закреплённым,
  подменённый код попадает в доверенную копию и исполняется следующей
  командой (`status`, `update`, `secrets`, `uninstall`). На Windows — с
  правами администратора.
- **Подтверждено** воспроизведением (тест-PoC) и чтением кода.
- **Исправление:** подписывать перечень файлов установщика тем же ключом с
  отдельным доменом и привязкой к `product_id`/версии (или включить
  `installer/` в подписанный payload); в `store_installer` сверять дерево
  с подписью закреплённым ключом до `os.replace` и копировать из
  проверенного снимка; `finish_installer` выполнять только после
  `check_key`. До исправления — убрать обещание «строгого» режима из KIT.md.

### К-2. Средне (условно) — Windows: предки нестандартного `--root` не проверяются

- **Где:** `shared/kit_windows.py:529-530, 574-576` — `parent.mkdir(...)`,
  `secure_owned` только для самого корня; на Linux предки проверяет
  `_root_parents` (`kit_setup.py:87-116`).
- **Атака:** администратор выбрал `--root` вне `ProgramData\HomenSAI`
  (например, пример из документации `C:\Program Data\Acme`); созданный
  предок наследует ACL `C:\`, где обычный пользователь может
  переименовывать подкаталоги. Пока службы остановлены, он подменяет
  исполняемый файл службы, который затем запускается от LocalSystem.
- **Подтверждено** только чтением кода; на Windows не воспроизводилось.
- **Исправление:** требовать, чтобы все существующие предки принадлежали
  SYSTEM/Administrators/TrustedInstaller и не давали прочим DELETE,
  WRITE_DAC, FILE_DELETE_CHILD; иначе отказ. Либо разрешить `--root` только
  внутри `%ProgramData%\HomenSAI` или `%ProgramFiles%`.

### К-3. Низко — нет защиты от понижения версии

- **Где:** `kit_setup.py:617-621`, `kit_windows.py:623-627`,
  `update_prepare.py:119, 218` — отклоняется только равная версия.
- **Атака:** пользователя уговаривают «обновиться» на старый подлинный
  комплект с известной уязвимостью (на экране видно «3 → 2»).
- **Подтверждено** воспроизведением: обновление 3 → 2 проходит.
- **Исправление:** монотонный `release_seq` в подписанном
  `homensai-release.json`; отказ при `seq <= сохранённого`, кроме явного
  `--allow-downgrade`.

### К-4. Инфо — ротация и отзыв ключа

Первый ключ принимается при первой установке (TOFU); смена ключа — ручным
`--accept-key-sha256`, без подтверждения старым ключом; отзыва нет. Это
задокументировано. При исправлении К-1 стоит добавить заявление о ротации,
подписанное старым ключом.

### Что сделано правильно

- Ed25519 над доменно-разделённым каноническим JSON (продукт, версия,
  SHA-256 всего ZIP); строгий разбор конверта; один примитив подписи;
  закрытый ключ с правами 0600 и необязательным паролем.
- Проверка пакета: хэш до и после разбора на одном дескрипторе, только
  `ZIP_STORED` и обычные файлы (симлинки и hardlinks невозможны), список
  файлов совпадает с подписанным, защита путей, учёт регистра.
- Распаковка: снимок → проверка → извлечение с `O_EXCL` → повторный хэш и
  подпись → публикация; TOCTOU закрыт.
- История миграций и секреты берутся из подписанного выпуска.
- Зависимости: `--require-hashes`, `--only-binary`, wheels по SHA-256 lock;
  runtime закреплён по SHA-256; запуск везде с `python -I -B`.
- Криптографические находки прошлого аудита (A-07, A-08) действительно
  закрыты.

## 5. Криптоаудит: шифрование, пароли и секреты

Сама криптография архивов ошибок не содержит: все попытки подделки при
воспроизведении отвергнуты. Главная проблема — подготовка каталогов
Windows в ProgramData.

### Ш-1. Высоко (нужна проверка на Windows) — junction вместо `ProgramData\HomenSAI`

- **Где:** `shared/kit_windows.py:131-151` (`secure_owned`), `:434-442`
  (`prepare_state_dir`, `prepare_secrets_dir`); `kit_setup.py:404-425,
  446-476`; `kit_secrets.py:106-122`.
- **Суть:** `secure_owned` проверяет только последний компонент пути и
  распознаёт ссылку через `is_symlink()`, который для junction (точки
  подключения) возвращает False. `GetNamedSecurityInfoW` и `icacls` без
  `/L` работают с целью junction, а не с ним самим. Проверка reparse points
  (`checked_path`) для путей состояния и секретов не вызывается.
- **Атака:** обычный пользователь до первой установки создаёт
  `C:\ProgramData\HomenSAI` как junction на каталог, принадлежащий
  администраторам. Проверка владельца проходит, а junction остаётся под
  контролем атакующего. Во время скрытого ввода секрета он перенаправляет
  junction в своё дерево — файл секретов создаётся там, значения
  раскрываются. При `--root` вне `HomenSAI` сохранённый установщик лежит в
  `HomenSAI\.state\<id>\installer`, и администратор, запустив его по
  подсказке, исполняет код атакующего — без всякой гонки.
- **Подтверждено** только чтением кода и документацией Windows/Python; на
  ВМ не воспроизводилось. Проверка: под обычным пользователем
  `mkdir C:\ProgramData\HomenSAI` → `mklink /J` на каталог администратора
  → `setup.cmd install`.
- **Исправление:** от `ProgramData\HomenSAI` вниз отклонять каждый
  компонент с атрибутом reparse point (`lstat().st_file_attributes &
  0x400`, `Path.is_junction()`); владельца брать у самого объекта
  (`FILE_FLAG_OPEN_REPARSE_POINT` + `GetSecurityInfo`); создавать
  `HomenSAI` сразу с закрытым DACL (`CreateDirectoryW` с
  `SECURITY_ATTRIBUTES`); пропускать пути состояния и секретов через
  `checked_path`.

### Ш-2. Низко — Windows: пароль архива наследуется дочерними процессами

`kit_setup.py:605` кладёт пароль в `os.environ`, а `kit_windows.py:48-49`
(`_run`) запускает WinSW и `icacls` без `env=`. На Linux окружение уже
минимальное. **Исправление:** минимальное `env` в `_run`, как в
`WindowsEffects.migrate`; убирать `HOMENSAI_ARCHIVE_PASSWORD` из окружения
после чтения.

### Ш-3. Низко — открытый SHA-256 всего ZIP в заголовке архива

`archive_crypto.py:35, 217`. ZIP детерминирован, поэтому хэш позволяет
проверять догадки о малых данных и связывать архивы с одинаковым
содержимым; для целостности поле не нужно (GCM). Ограничение
задокументировано. **Исправление:** в формате v2 убрать поле или хранить
HMAC под производным ключом.

### Ш-4. Низко — запас стойкости KDF

scrypt N=2^15, r=8, p=1 (~0,35 с, 32 MiB) — уровень «interactive»;
комплект требует пароль ≥ 8 символов, `ctl` и API — любой непустой.
**Исправление:** формат v2 с N=2^17 или Argon2id; проверка длины/сложности
пароля в CLI и API.

### Ш-5. Низко — секреты молча берутся из одноимённых переменных окружения

`kit_setup.py:389-402` (`ask_value`): если издатель объявил секрет с
ходовым именем (`GITHUB_TOKEN`, `DATABASE_URL`), значение из оболочки
администратора без вопроса уходит в файл и службам. **Исправление:**
отдельный префикс (`HOMENSAI_SECRET_VALUE_<ИМЯ>`) или сообщение
«значение взято из окружения» с подтверждением в интерактивном режиме.

### Ш-6. Инфо

- `kit_setup.py:195`: `getpass` без защиты от ввода с эхом (в
  `archive_crypto.password_provider` она есть) — использовать ту же
  обёртку.
- Временный открытый ZIP на Windows наследует ACL каталога архива и
  остаётся при сбое; в комплекте недостижимо (каталог состояния закрыт),
  опасно для `ctl archive-verify/restore` в общей папке.
- Пример `KIT.md:281` (`ACME_API_TOKEN=… ./setup.sh`) оставляет секрет в
  истории оболочки — показать `read -s`.
- `homensai_entry.py` учитывает `HOMENSAI_SECRETS_FILE` и в рабочем режиме;
  можно ограничить режимом разработки.

### Что сделано правильно

- AES-256-GCM по блокам, nonce = 4 случайных байта + счётчик, ключ на
  каждый архив (соль 16 байт `os.urandom`), в AAD — весь заголовок, номер
  и длина блока.
- Воспроизведено: отвергаются изменение любого из 86 байт заголовка,
  перестановка/повтор/удаление блоков, лишний хвост, блоки чужого архива с
  тем же паролем, неверный пароль, обычный ZIP при обязательном
  шифровании.
- Параметры KDF зашиты в код (нет DoS через заголовок); открытый текст
  выдаётся только после проверки всех тегов и SHA-256; ошибки без
  оракулов; пароль не передаётся через argv.
- Секретов нет в XML WinSW, состоянии, манифесте и сообщениях; запись файла
  секретов атомарная (`O_EXCL|O_NOFOLLOW`, fsync, `os.replace`), 0600/0700
  с проверкой uid; CR/LF/NUL в значениях запрещены.
- Модуль `random` нигде не используется.

## 6. Рекомендуемый порядок работ

1. **К-1** — подписывать код установщика и проверять его перед сохранением;
   до исправления убрать обещание «строгого» режима из KIT.md.
2. **Ш-1 и К-2** — единая проверка цепочки каталогов на Windows (reparse
   points, владелец самого объекта, атомарное создание с DACL, предки
   `--root`), затем воспроизведение на тестовой ВМ.
3. **К-3** — монотонный номер выпуска против понижения версии.
4. **Ш-2, Ш-5, Ш-6** — мелкие правки окружения и ввода.
5. **Ш-3, Ш-4** — формат архива v2 (сильнее KDF, без открытого хэша) с
   чтением старого формата.
6. Подключение Rent (Н-8) и приёмка на реальном ПК (Н-3).
7. Лицензии и состав пакета, защищённая сборка, кандидат в выпуск
   (Н-4 — Н-6); Docker-комплект (Н-1) — отдельным этапом, если нужен.

После пунктов 1–4: полная регрессия, сквозные проверки Linux и Windows
(install/update/restore/rollback), повторный выборочный криптоаудит.
