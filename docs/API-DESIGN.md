# Публичный API установочного модуля: проект v1

02.11.2026 · HomenS.AI · Serhii Khomenko

Проектный контракт. Ниже описаны требуемые операции, а не утверждение об их
реализации. Действующий `shared.ctl` поддерживает только подмножество локальных
действий и не соответствует этому API полностью. Исполняемая спецификация и
тестовый клиент создаются на шагах 110–113; до этого интеграция невозможна.

## Границы и транспорт

Первая версия — локальный API с интерфейсом вызова в Python и отдельным CLI,
передающим JSON через stdin/stdout. Их семантика, проверка и форматы совпадают;
CLI запускается без shell, не принимает секреты в argv и не выводит их в JSON.
Интегратор использует опубликованную клиентскую библиотеку или документированный
CLI, а не импортирует внутренние модули, state-файлы или исключения реализации.
Обе стороны устанавливаются на одном хосте. Никакого сетевого сервера, облака
или ИИ для работы API не требуется. HTTP/удалённый доступ не входит в v1.

Доверенное приложение вызывает API в контексте пользователя/службы ОС; права
операционной системы ограничивают доступ к файлам, секретам и управлению
службами. Дополнительное повышение привилегий только через явную платформенную
процедуру с проверкой владельца установки; произвольный путь к исполняемому
файлу, shell-команда или произвольный compose-файл из API не принимаются как
доверенное действие. Установщик отдельно проверяет пакет, идентичность и
совместимость продукта. Локальный API не является песочницей для злоумышленного
кода, уже работающего с равными правами.

## Совместимость и согласование возможностей

До действий клиент вызывает `capabilities` и проверяет целое `api_major: 1`,
минимально необходимую `api_minor`, перечисленные `operations`, версии
манифестов, доступные способы запуска и ограничения текущего хоста. Клиент
отказывает при неизвестной major-версии или отсутствии требуемой возможности.
Minor-версия допускает обратно совместимые дополнительные операции/поля;
новые обязательные поля или изменение смысла требуют новой major-версии.
Клиент игнорирует неизвестные поля ответа, сервер отвергает неизвестные поля
запроса. Поле возможностей означает реализованную и проверенную возможность,
а не намерение будущей версии. До реализации нельзя считать какие-либо
проектные операции доступными.

## Общий конверт

Каждый запрос — JSON-объект с `api_major`, `operation`, `request_id` и
`params`. `request_id` — безопасный идентификатор клиента для сопоставления,
не секрет и не доказательство авторизации. Операции изменения дополнительно
передают устойчивый `idempotency_key`, уникальный для установки и неизменного
запроса. Один ключ с другим запросом отклоняется. Сервер ограничивает размер,
глубину и число объектов, запрещает дубликаты ключей JSON и недопустимые типы;
точные пределы фиксируются в исполняемой спецификации до выпуска.

Успех: `{api_major, request_id, ok: true, result}`. Ошибка:
`{api_major, request_id, ok: false, error: {code, message, retryable}}`.
Коды стабильны в пределах major и включают `invalid_request`,
`unsupported_version`, `unsupported_operation`, `unsupported_platform`,
`not_found`, `conflict`, `permission_denied`, `verification_failed`,
`operation_failed` и `recovery_required`. `message` безопасен для пользователя;
не содержит секретов, произвольных исключений или вывода процессов. CLI отдаёт
один JSON на stdout; код 0 — успешный ответ, 2 — ошибка контракта/совместимости,
1 — операционная ошибка; диагностика не дублирует секреты в stderr.

## Операции

| Операция | Основные параметры | Результат и действие |
|---|---|---|
| `capabilities` | нет | Версии API и манифестов, список реально доступных операций и возможностей. |
| `validate` | путь к локальному манифесту | Проверка декларации без эффектов; не подтверждает содержимое payload. |
| `plan` | идентификатор пакета, установка, вариант запуска | Проверенный план без записи в установку и запуска продукта. |
| `install` | идентификатор проверенного пакета, установка, вариант и ключ | Начать свежую установку; вернуть идентификатор операции. |
| `update` | установка, проверенный выпуск и ключ | Начать обновление с резервными копиями и откатом по контракту. |
| `status` | установка и идентификатор операции | Текущее состояние и результат без запуска новой операции. |
| `archive` | установка, назначение и ключ | Создать и проверить полный архив через защищённый канал пароля. |
| `restore` | установка, проверенный архив и ключ | Восстановить по проверяемому плану при остановленных писателях. |
| `resume` | установка и идентификатор операции | Возобновить только совместимую незавершённую операцию. |
| `uninstall` | установка, политика данных и ключ | Удалить принадлежащие установке ресурсы; данные сохраняются по умолчанию. |

Конкретные поля и ограничения параметров будут формализованы в схеме и
проверены до предоставления API. Пароль/значения секретов передаются отдельным
каналом полномочий вызывающей стороны, а не в публичном JSON; реализация этого
канала зависит от платформы. Прямой пароль в переменной окружения не считается
универсально защищённым решением. `plan` не даёт разрешения на последующее
изменение состояния: перед действием нужно повторно проверить актуальные факты.

## Операции, повторы и отказ

Изменяющая операция получает идентификатор, сохраняет состояние и блокировку
установки до эффектов и сообщает `running`, `succeeded`, `rolled_back` или
`recovery_required`. Вызовы `status`/`resume` возвращают проверенное состояние
по идентификатору. Повтор с тем же ключом и тем же каноническим запросом
возвращает существующую операцию; другая нагрузка с тем же ключом — `conflict`.
Ключи, подтверждения и состояние переживают перезапуск. Если результат внешнего
эффекта после сбоя нельзя достоверно определить, автоматического повтора нет:
возвращается `recovery_required`. Повторяемость и exactly-once на внешних
командах не гарантируются одним только API; адаптер обязан предоставить
надёжный механизм подтверждения. Статус `rolled_back` не равен успеху update.

## Передача другим продуктам

После реализации и приёмки публикуются версия контракта, схема, инструкция,
минимальный клиент и независимый тестовый пример. Для каждого продукта отдельно
проверяются его адаптер, версии, зависимости, секреты и сценарии отказа.
Копирование одной инструкции в репозиторий не подключает продукт автоматически.
Список репозиториев и фактическое распространение определяются на следующем
этапе после принятия контракта.
