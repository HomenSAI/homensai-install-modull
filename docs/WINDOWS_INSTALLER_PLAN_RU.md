## Этап 1 и состав результата

**Сначала Windows native, затем Windows Docker.** Целевая ОС — Windows 11 x64.
Первая поставка проверяется на Reference с SQLite. Установщик работает из-под
обычного пользователя, содержит мастер и app-local runtime. У конечного
пользователя могут отсутствовать Python, pip, Git и инструменты сборки.

Результат этапа — один Windows x64 `Setup.exe` и соответствующие пакеты для
выбора **«Установить в Windows»** или **«Установить в Docker»**. Docker-путь
разворачивает Linux-контейнеры в Docker Desktop с WSL 2. Сначала выпускается
DEV-кандидат только с Windows native. Docker появляется в том же мастере
после проверки второй очереди. У двух режимов отдельные идентификаторы
установок и каталоги данных.

Linux frozen DEV и зарегистрированный Linux-адаптер дают проверенные примеры
журнала, миграции, backup и восстановления. `NativeEngine.capabilities()` сейчас
ограничен Linux. В репозитории Windows PowerShell/WinSW — генератор сценариев,
а Docker backend работает с узким Linux-профилем и заранее доступными
образами. Windows portable CI проверяет код. Установленный Windows artifact
предстоит собрать и принять отдельно.

## Шаг 0. Зафиксировать входы и среду

1. Проверить Git, фактическую ветку, состояние локальных изменений и записать SHA,
   от которого начинается разработка. Взять текущие схемы API, манифест
   Reference, существующие профили v1/v2/v3 и проверки Linux как образец
   поведения. Публичные методы и форматы сохранённых планов менять только
   при необходимости, с проверкой совместимости.
2. Подготовить Windows 11 x64 VM или отдельный тестовый компьютер. Нужны
   обычный пользователь, отдельная админская учётная запись для UAC,
   возможность перезагрузки и чистый снимок для повтора. Для Docker-пути
   отдельно подтвердить, что выбранная среда поддерживает WSL 2 и
   виртуализацию. Среда сборки и машина приёмки могут быть разными.
3. Зафиксировать выбранную версию Windows, архитектуру, версии runtime и
   средств сборки в lock/квитанции. Для каждой новой бинарной зависимости
   проверить точный источник, SHA-256 и условия использования по политике проекта.
4. На доступной машине снять исходный portable baseline средствами существующего
   Windows CI. Отдельно отметить доступность реальной Windows 11 и Docker Desktop.
   Если целевая машина недоступна, подготовку кода и fixtures продолжать, а
   соответствующей приёмке оставить `BLOCKED`.

Команды для первичной сверки доступны в PowerShell. Вызовы Docker и WSL
выполнять только при наличии соответствующих команд.

```powershell
git status --short --branch
git rev-parse HEAD
git ls-remote origin refs/heads/codex/universal-installer-20261025
Get-CimInstance Win32_OperatingSystem | Select-Object Caption, Version, BuildNumber, OSArchitecture
Get-Command docker,wsl -ErrorAction SilentlyContinue
wsl.exe --status
wsl.exe --version
docker context ls
docker version
```

**Готово, когда** записаны baseline и целевая конфигурация, а статус отдельно
отражает наличие среды сборки, чистой Win11 для тестов и WSL 2 для Docker.

## Очередь A. Установка напрямую в Windows

### A1. Подключить Windows к общему ядру

1. Разобрать Linux-зависимые действия в `homensai_install/engine.py` и
   `adapters.py`: запуск, идентификация и остановка процессов, блокировки,
   проверка владения каталогом, закрытие писателей и безопасная замена файлов.
2. Выделить только нужные Windows-реализации этих действий и подключить их через
   `BackendRouter` для `windows/x64/native/user`. Повторно использовать
   `InstallerAPI`, reviewed plan, согласия, журнал, блокировку установки и
   существующую логику архива. Windows-ветки подключать по мере проверки
   конкретных действий в `capabilities()`.
3. Первым срезом сделать Windows-команду `discover → plan → submit → status`
   на подписанной fixture. Проверить запуск встроенного runtime и чтение
   результата новым экземпляром SDK. Пробелы и кириллица в путях входят
   в первый тест.

**Готово, когда** файл плана привязан к Windows target и точным входам,
повтор submit сохраняет ID операции, а Linux-регрессии продолжают проходить.

### A2. Реализовать права, процессы и готовность на Windows

1. Создавать управляемые каталоги от имени исходного пользователя. Разделить
   app/releases, DataHome и API state. Привязать владение к SID и identity
   установки. Проверить ACL и файловую идентичность до замены или удаления,
   включая reparse points, junctions и спорные ссылки.
2. Запускать компоненты из проверенного релиза с фиксированными executable и
   аргументами. Для управления деревом процессов проверить применимость Job
   Objects и сохранение требуемого поведения при закрытии мастера. Записывать
   PID, время создания процесса, релиз и подтверждённую принадлежность. При
   повторном открытии мастера сверять живой процесс перед stop.
3. Для штатной остановки добавить проверяемый протокол Reference и дождаться
   завершения его писателей. Readiness проверяет собственный loopback listener,
   идентификатор установки, релиз, SQLite и открытие веб-страницы. Чужой
   процесс или порт дают отказ с объяснением.
4. Секреты передавать через доверенный provider. Если требуется хранение
   между запусками, реализовать защиту под профилем пользователя с ACL и
   проверить восстановление из резервной копии. Машинную привязку DPAPI
   учитывать отдельно от переносимого зашифрованного архива.

**Готово, когда** обычный пользователь выполняет start/stop, повторный start
использует собственный процесс, второй пользователь получает предусмотренный
отказ, а чужой процесс и пользовательские файлы остаются целыми.

[Windows-контракт](WINDOWS.md) · [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) · [Windows DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)

### A3. Довести установку, обновление и восстановление

1. Подготовить подписанные Windows-пакеты Reference v1/v2/v3 с собственным
   runtime, нужными wheel и ресурсами. Провести доверенную регистрацию
   продуктового адаптера через bootstrap. Адаптировать исполнение hooks и
   durable ledger для Windows, сохранив публичный контракт.
2. Fresh-путь проверяет пустое назначение, загружает релиз в staging,
   создаёт схему SQLite и подтверждает запуск. Существующая установка идёт
   по явному update/reinstall, с проверкой её identity.
3. Перед обновлением остановить писателей и получить проверенный зашифрованный
   архив. После миграции подтвердить новую схему и готовность. Потерю
   подтверждения разбирать по журналу и `operation_status` исходной операции.
   `UNKNOWN` и отсутствие authoritative ledger сохраняют `RECOVERY_REQUIRED`.
4. Подключить restore и rollback с отдельным safety archive текущего состояния.
   Repair/reinstall повторно устанавливают проверенный код той же версии с
   сохранением данных. Uninstall удаляет только управляемые файлы и сохраняет
   данные, настройки и квитанции для последующего восстановления.

**Готово, когда** через Windows SDK пройдены fresh → v2 → v3, backup → restore,
rollback, repair и uninstall → reinstall. После сбоя повтор запроса
не дублирует миграцию. Копия действительно расшифрована и восстановлена,
версия схемы и контрольные пользовательские файлы сверены.

[API восстановления](../INSTALLER_API.md#явные-restore-и-rollback-productadapter) · [Контракт адаптера](PRODUCT_ADAPTER_EXECUTION.md)

### A4. Собрать Setup.exe и принять native-режим

1. Добавить воспроизводимую x64 сборку в `windows/` и запись в CI. По текущему
   проектному решению собрать frozen onedir launcher и NSIS-оболочку. Мастер,
   валидация и upgrade остаются в общем SDK. Упаковщик передаёт управление
   launcher и подключает системную точку удаления к той же операции SDK.
2. Вложить офлайн runtime, payload, схемы, ru/en/de, условия, signed inventory и
   trust для конкретного профиля. Installer и uninstaller повседневного
   пользовательского режима стартуют с обычными правами. Если выбранный
   prerequisite требует повышения, доверенный helper получает ограниченное
   действие из утверждённого плана и возвращает проверяемый результат.
3. Выпустить DEV-кандидат, установить его вне checkout на чистой Windows 11.
   Повторить проверку без сети, отказ UAC для требующего его шага, запуск под
   обычным пользователем и сценарий ввода другого администратора. Проверить,
   что исходный SID остаётся владельцем пользовательской установки.
4. Приложить квитанцию с SHA-256 `Setup.exe`, ревизией, версиями компонентов
   и результатами реальных запусков. Проверить три языка, включая условия,
   ход операции и читаемое сообщение об ошибке.

**Готово, когда** с чистого снимка работает нативный DEV-кандидат без
инструментов разработки. Архив и восстановление проходят через тот же
установленный мастер, штатное удаление сохраняет данные. После этого
переходить к очереди B.

## Очередь B. Установка в Docker Desktop на Windows

### B1. Подключить проверенный Windows-путь к Docker

1. В Windows-мастере сначала выполнять read-only проверку Docker Desktop,
   WSL 2, режима Linux containers, совместимости и доступности daemon.
   Различать отсутствие Docker, закрытый Desktop, режим Windows containers
   и ошибку доступа. Сохранять фактическую причину.
2. Добавить Windows-исполнение для доверенного `DockerCLI` или узкий
   Windows-адаптер с тем же контрактом. Выбирать локальный endpoint из
   проверенной bootstrap-конфигурации. Проверять executable, контекст и
   identity daemon перед изменениями и resume. Не менять глобальный контекст
   пользователя. Удалённый daemon не входит в этот профиль.
3. Отдельно реализовать подтверждение пути Windows ↔ Linux VM. Сначала проверить
   отображение путей в отдельном тестовом контейнере. Созданный приложением
   контрольный файл виден через выбранное хранилище, соседний путь недоступен.
   Описать выбранный вариант томов и проверяемый способ копирования данных.
   Сохранить Linux-проверки текущего профиля.

**Готово, когда** Windows-клиент выполняет read-only discovery и plan на
реальном Desktop, а неверный daemon, недоступный endpoint или неразрешённый
путь завершаются контролируемым отказом.

[Docker CLI](../homensai_install/docker_cli.py) · [Контексты Docker](https://docs.docker.com/engine/manage-resources/contexts/) · [Хранилища Docker Desktop](https://docs.docker.com/engine/storage/bind-mounts/)

### B2. Подготовить prerequisites и образы

1. Начать с совместимого Docker Desktop, который пользователь уже установил.
   Затем подключить manual/recheck. Автоматическое действие подключать после
   проверки точного пакета и условий использования, отдельного согласия и
   привязки разрешённого действия к подписанному каталогу prerequisites.
2. При необходимости reboot/relogin сохранить исходную попытку. После
   пользовательского перезапуска заново выполнить discovery. Когда daemon
   готов, выполнить свежий product preflight и получить подтверждение плана.
3. Собрать Linux amd64 образ Reference с закреплёнными базовым образом и
   runtime. Подписать контракт. Онлайн-пакет закрепляет digest, офлайн-пакет содержит локальный
   архив образа с SHA-256. После `docker image load` независимо сверять
   платформу и image ID с подписанным контрактом: тег служит для поиска,
   содержимое подтверждают проверенные идентификаторы. Проверить отдельно,
   какие сведения о RepoDigest реально сохраняет выбранный формат архива.
4. Различать офлайн-установку продукта на готовом Docker и офлайн-подготовку
   самого Docker Desktop/WSL. Вторую проверять отдельно при наличии допустимых
   локальных компонентов.

**Готово, когда** мастер предлагает понятный путь при отсутствующем Docker,
обнаруживает подготовленную среду и разворачивает корректный локальный образ
без сети. Подменённый образ и неверная архитектура дают отказ до старта.

[Установка Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/) · [WSL 2](https://docs.docker.com/desktop/features/wsl/) · [Загрузка образа из архива](https://docs.docker.com/reference/cli/docker/image/load/)

### B3. Довести установку и обслуживание контейнеров

1. Связать сетевые настройки, конфигурацию контейнеров и хранилище с
   installation ID и проверенным daemon. Операции работают с точными ID и
   квитанциями владения. Согласованный план закрепляет порты и публикацию
   на loopback. Проверить занятый порт и соседнюю установку.
2. Адаптировать существующий Docker lifecycle: создание собственных ресурсов,
   запуск, остановка, readiness, backup и uninstall с сохранением данных.
   Если понадобится Compose, определить его роль в provisioning в рамках
   того же журнала и проверок владения.
3. Добавить update, restore, rollback, repair и reinstall. Перед заменой образа
   остановить писателей, сделать архив с проверкой восстановления и сохранить
   привязку старого и нового образов. Restore проверяет доступ к данным внутри
   выбранного хранилища. После потерянного ответа сначала сверяется
   фактическое состояние контейнеров, томов и release.
4. При удалении подтвердить, что затронуты только собственные контейнеры и
   сети, а пользовательские данные, архивы, Docker Desktop и соседние
   ресурсы сохранены. Проверить восстановление сохранённой установки.

**Готово, когда** на реальном Windows Docker Desktop прошли fresh, start/stop,
v1→v2→v3, backup/restore, rollback, repair и uninstall/reinstall. Отдельные
прогоны проверяют перезапуск Docker Desktop, потерю подтверждения операции,
занятый порт и сохранность соседнего контейнера.

[Контракт Docker](DOCKER_ENGINE.md) · [HIM-039 и HIM-044](../HomenSAI_Universal_Installer_TODO_RU.txt)

### B4. Включить Docker в общий Windows Setup

1. Подключить Docker-пакет через доверенный bootstrap. Мастер показывает
   доступность каждого пути и причину отказа. Выбранный режим закрепляется
   в плане и сохраняется при повторном открытии мастера.
2. Собрать один Windows-кандидат с native и Docker. Проверить разные roots,
   state, installation ID и порты для двух установок. В обеих ветках
   проверить ru/en/de и сохранение исходного operation ID после перезапуска.
3. На чистых снимках отдельно прогнать native и Docker. Для Docker выполнить
   как минимум варианты с готовым Desktop и с доступным ручным путём
   подготовки. Отдельно повторить офлайн установку продукта на готовом Desktop.

**Готово, когда** тот же `Setup.exe` работает в обоих режимах, а квитанции
привязаны к его SHA-256 и фактическим пакетам native и Docker.

## Приёмка этапа 1

| Проверка | Windows native | Windows Docker |
| --- | --- | --- |
| Чистая Windows 11 x64, без dev tools | Setup, веб-готовность, start/stop | Тот же Setup, реальный Desktop/WSL 2, веб-готовность |
| Цикл данных | v1→v2→v3, backup/restore, rollback, repair, uninstall/reinstall | Тот же цикл с заменой контейнеров и сохранением хранилища |
| Офлайн | Runtime и приложение из пакета | Локальный проверенный образ на готовом Desktop |
| Отказы и продолжение | Чужой PID/порт, права, сбой после миграции, защита данных | Чужой контейнер/порт, недоступный daemon, прерванная операция, защита данных |
| Мастер и журнал | ru/en/de, согласия, операции после повторного открытия | ru/en/de, preflight, ручная подготовка, корректный recheck |

У каждой строки нужны source SHA, SHA-256 установщика и payload, целевая среда,
команда или шаги мастера, фактический результат и файл квитанции. Приёмка этапа
закрывает указанный Windows-профиль. Production-выпуск идёт отдельной задачей
в этапе №2.

## Этап 2. Отложенные работы

Этап №2 на паузе. Порядок возобновления определяется после Windows-результата.

| Работа | Как продолжить |
| --- | --- |
| **Linux native** | Подключить зарегистрированный ProductAdapter к собранному Linux-мастеру, довести выпускной пакет и повторить полный цикл на чистом Ubuntu 24.04 Desktop. Использовать Linux DEV квитанции как исходную точку. |
| **Linux Docker** | Подключить профиль нативного Linux Engine к Linux-мастеру. Повторно использовать проверенную доставку образов и общее ядро Docker lifecycle, отдельно принять права, сеть, тома и восстановление на Linux. |
| **Системные службы** | Подключить существующий systemd user port к общему жизненному циклу. Для Windows добавить SCM/WinSW там, где продукт заявляет службу. Отдельно принять учётные записи, секреты, автозапуск, logout и reboot. |
| **JobPilot и Rent** | Подключить проверенные манифесты и отдельные adapters к установленному SDK. Проверить миграции, реальные данные и сборки каждого продукта в его заявленных режимах. |

## Как продолжать и сохранять работу

Первое действие при возобновлении — выполнить шаг 0 и перейти к A1. Опорные
карточки Windows native — HIM-036, HIM-037, HIM-040–042, HIM-072. Для Docker —
HIM-031, HIM-039, HIM-044, HIM-072. Требования к загружаемым компонентам и
перезапуску — HIM-028–034.

После каждого проверенного среза обновить соответствующий HIM/ACC, RESUME и
work-state. Сохранить исходный отказ и итоговую квитанцию, затем сделать
checkpoint через `tools/checkpoint.py` с явным списком файлов. Публикация этапа
идёт в feature-ветку с независимой сверкой GitHub ref/tree. Ключи, секреты,
личные БД и каталоги сборок остаются вне Git.
