# Сохранённый прогресс загрузки prerequisites

Автор: Serhii Khomenko.

`durable_byte_progress=true` в discovery/`InstallerAPI.describe()` обозначает
поддержку сохранённых измерений загрузки. Configured SDK/HTTP capabilities
подтверждают её для явно зарегистрированного coordinator. Отсутствие capability
у старого сервера означает отсутствие этой гарантии. Capability не объявляет
операцию, зависимости или продукт готовыми к эксплуатации.

Публичный `operation.download_progress` содержит последнее измерение одного
артефакта. Поле необязательно: его нет до первой загрузки, у прежних сохранённых
операций и у ручной подготовки/отмены до загрузки. Это не сумма байтов всех
зависимостей и не процент выполнения installer. Raw plan v1, его digest и
consent refs сохраняют прежний формат.

## Публичная запись

OpenAPI `PrerequisiteDownloadProgress` описывает ровно 17 обязательных полей;
дополнительные поля запрещены. `PrerequisiteSnapshot.download_progress` остаётся
необязательным. Схемы подключены к HTTP `status` и `events`; SDK и CLI возвращают
ту же запись внутри соответствующего результата.

| Поле | Смысл и ограничение |
|---|---|
| `schema_version` | Целое `1`. |
| `plan_digest` | 64 строчных hex-символа; digest принятого плана. |
| `component_id`, `artifact_id` | Идентификаторы из signed plan, длина 1–128; буквы ASCII, цифры, `_`, `.`, `+`, `-`, первый символ — буква или цифра. |
| `artifact_sha256` | 64 строчных hex-символа; ожидаемый SHA-256 из signed plan. |
| `transfer_id` | 32 строчных hex-символа; корреляция одного прохода загрузки, не секрет авторизации и не execution lease token. |
| `attempt` | Целое 0–7. `0` используется до сетевой попытки и для локальных путей; сетевые попытки начинаются с `1`. |
| `state` | `preparing`, `transferring`, `verifying`, `retrying`, `verified`, `failed`, `canceled`. |
| `completed` | Измеренное целое число байтов: `0 <= completed <= total`. |
| `total` | Подписанный размер: целое от 1 до 68 719 476 736 байтов, то есть 64 GiB. |
| `unit` | Всегда `bytes`. |
| `source` | `unknown`, `network`, `cache`, `partial`, `local`. |
| `resumed` | Boolean; отражает восстановление фактического partial-файла. |
| `verified` | Boolean; `true` только у состояния `verified`. |
| `percent` | Целое либо `null`; правила приведены ниже. |
| `sequence` | Положительное целое; номер общей ревизии операции, в которой сохранено измерение. Публичная схема ограничивает его безопасным диапазоном JavaScript: до `2^53 - 1`. |
| `updated_at` | Время сохранения в UTC, строка RFC 3339 с окончанием `Z`. |

Числовые счётчики не принимают boolean, дробные, отрицательные или бесконечные
значения. Размер, hash и идентификаторы берутся из подписанного плана: callback
не может подставить другой artifact или total. Проекция не содержит URL,
query string, локальный путь, команду или диагностический текст transport.

## Когда допустим процент

| Состояние | `percent` | Проверка |
|---|---|---|
| `transferring` | `floor(completed * 100 / total)`, от 0 до 99 | `completed < total`, `verified=false`. |
| `verified` | `100` | `completed == total`, `verified=true`; проверен SHA-256 подготовленного staged-файла. |
| `preparing`, `verifying`, `retrying`, `failed`, `canceled` | `null` | Числовой процент не отображается. |

Получение всех байтов само по себе приводит к `verifying`. Затем проверяются
hash исходного файла и hash копии, подготовленной для installer. Только после
успешной проверки staged-файла сохраняется `verified/100`, а затем coordinator
может перейти к запуску installer. В этот момент операция ещё `RUNNING`;
успешность installer и последующие probes остаются отдельными условиями READY.

Verified cache, полный восстановленный `.part` и local artifact имеют явные
измерения и проходят проверку. Полный файл неверного hash не получает 100%.
`partial` обозначает путь проверки уже полного partial-файла; сетевая дозагрузка
использует `source=network` и признак `resumed`. Отсутствие новой записи после
обрыва соединения показывает последнее сохранённое наблюдение, а не продолжающуюся
загрузку; клиент должен отдельно отображать потерю связи.

## Сохранённое измерение и offset восстановления

`completed` — число байтов, которое загрузчик наблюдал после записи в файловый
буфер. Commit прогресса может завершиться раньше `flush/fsync` самого `.part`.
Поэтому после остановки процесса в журнале может остаться больше байтов, чем
реально сохранилось в файле. Эта разница допустима и не исправляется выдуманным
увеличением файла или запросом Range по snapshot.

Resume заново проверяет фактическую длину `.part` и HTTP validator. Сброс файла,
полный ответ на Range или новая попытка могут уменьшить `completed`; номер
попытки и состояние отражают этот переход. Обработчик не сохраняет устаревшие
callbacks прежнего transfer, плана или попытки. Новый артефакт/проход получает
новый `transfer_id` и собственные счётчики.

Явный `replace_plan` очищает текущую `download_progress`, в том числе при
неизменившемся digest плана. Следующая загрузка начинает новую проекцию.
Исторические события остаются в журнале и не должны восстанавливать старую
полосу прогресса поверх нового snapshot. Обычный save той же операции переносит
самое свежее измерение и sticky cancellation из хранилища, поэтому устаревший
объект controller не затирает их и не возвращает очищенную проекцию.

## Частота сохранения

Промежуточные `download.bytes` распределены по 256 диапазонам подписанного
размера: `bucket = floor(completed * 256 / total)`. Первый прочитанный chunk
сохраняется сразу; последующие — при переходе в следующий диапазон. На одну
сетевую попытку приходится не более 256 промежуточных byte-записей. Завершение
передачи и состояния подготовки, retry, проверки, ошибки и отмены сохраняются
отдельно; это не общий предел событий операции.

Ширина диапазона не превышает `ceil(total / 256)`; при предельном размере 64 GiB
это 256 MiB. Пропущенные диапазоны не создают искусственных измерений: сохраняется
действительное последнее число прочитанных байтов. Таймер не расходует лимит
записей в начале медленной большой загрузки. Обратная сторона — отсутствие
гарантии обновления каждую секунду: при медленной передаче до следующего
диапазона запись может долго не меняться. Размер диапазона также не является
гарантией времени commit или сохранности buffered bytes после crash.

## Транзакция и курсор событий

Обязательный writer в одной SQLite-транзакции сохраняет snapshot, событие
`type=prerequisite_download` и новую ревизию. У события:

- `phase=prerequisites`, `message_code=prerequisite_download_progress`;
- `operation_id` и `component_id` относятся к этой операции/артефакту;
- `sequence` равен `download_progress.sequence`;
- `timestamp` равен `download_progress.updated_at`;
- вложенная `download_progress` совпадает с сохранённой проекцией этой ревизии.

События состояния и загрузки используют единый возрастающий `sequence`.
Текущий snapshot может иметь более новую ревизию, чем последняя запись прогресса
или полученная страница events. Запрос `events(after_sequence, limit)` ограничен
1000 событиями; значение по умолчанию — 100. Клиент продвигает курсор только до
`sequence` последнего реально полученного события. Нельзя заменить его на
`snapshot.revision`: это пропустит невычитанные страницы.

После завершения controller журнал также нужно дочитать. Для стабильной
завершённой операции курсор достигает её revision; повтор запроса после этого
возвращает пустую страницу. Status и чтение событий не вызывают resume и не
запускают installer. Встроенный короткий список `snapshot.events` не заменяет
постраничное чтение полного журнала.

## Обязательная запись и наблюдатели

`DownloadManager.fetch(..., persist_progress=...)` отделён от прежнего
best-effort `progress` observer. Coordinator передаёт обязательный writer.
Его ошибка возвращается как `STATE_STORAGE_UNAVAILABLE` и запрещает дальнейший
запуск installer. Она не превращается в обычную transport retry и сохраняет
приоритет, даже если cleanup ответа, файла или cache lock тоже завершился
ошибкой. Невозможность сохранить событие откатывает и snapshot той же транзакции.

Ошибка необязательного observer не делает уже проверенные байты неверными.
Она также не заменяет обязательное сохранение и не является источником
публичного durable progress.

В CP018 чтение состояния также учитывает нормальное удаление SQLite временных
`-journal`, `-wal`, `-shm` во время commit. Отсутствие такого sidecar допустимо;
неверные права, владелец, ссылки и другие ошибки сохраняют отказ. Соединение
уже созданного prerequisite store использует `mode=rw`: пропавшая основная БД
не создаётся заново при status/save. Первоначальный constructor отдельно создаёт
новую БД; это не восстановление прежнего журнала или его неизвестных эффектов.

## Проверки и границы доказательства

`tests/test_prerequisites_progress.py` проверяет сохранение между чтениями SDK
и процессами, actual partial offset после остановки собственного controller,
retry/Range, cache/local/full-part пути, hash/staging failure, stale callbacks,
cancel/save merge, transaction rollback и обязательный writer перед installer.
`tests/test_prerequisites_progress_contract.py` и
`integration_tests/test_prerequisites_http.py` проверяют реальные SDK и
аутентифицированные loopback HTTP ответы по опубликованной схеме, signed binding,
страницы events, отсутствие URL/путей и совместимость snapshot без нового поля.
Installed client отдельно проверяет публичный SDK/CLI из установленного wheel.

Эти fixtures используют синтетические installer и артефакты. Они не подтверждают
реальную установку пакетов ОС, Windows ACL/UAC, browser acceptance или устойчивость
к потере питания. PASS относится только к конкретным выполненным командам и
исходным байтам в соответствующем receipt; `production_ready=false` сохраняется.
