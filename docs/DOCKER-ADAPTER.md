## Проверка Docker

`shared.docker_preflight.check_docker` и локальные интерфейсы `docker-check` и
API 1.28 `check-docker-engine` выполняют ограниченную проверку версии CLI,
версии Compose, наличия в справке `--no-build` и `--pull`, а также версии
локального демона. Используются команды из документации Docker:
[`docker --version` и `docker version --format`](https://docs.docker.com/reference/cli/docker/version/),
[`docker compose version --short`](https://docs.docker.com/reference/cli/docker/compose/version/)
и справка `docker compose up --help`. Контейнеры и образы эти запросы не
запускают. Неопознанный вывод, включая обнаруженный на тестовом хосте интерфейс
совместимости Podman, не выдаётся за подтверждённый Docker.

Интегратор передаёт абсолютный путь CLI и его SHA-256 из независимого
доверенного источника, а на Linux — абсолютный путь локального Unix socket;
Windows использует фиксированный локальный именованный канал. Для каждого
вызова CLI проверяются байты программы до и после исполнения. Создаётся
временная пустая конфигурация Docker; параметры контекста и подключения из
окружения пользователя не наследуются. Ошибки, stdout и stderr не выводятся;
возвращаются только проверенные строки версий или `null`. Команды выполняются
как внешние процессы, поэтому API перечисляет проверку среди операций с
эффектами. Указанный CLI и установленный Compose plugin должны быть доверенными;
хэш CLI сам по себе не проверяет plugin, демон или защиту от вредоносного кода.
Выводы `installation_ready` и `images_verified` всегда `false`: наличие флагов
не подтверждает конкретную версию их поведения, образы или работоспособность
установки. Происхождение, подписи, права, сетевые действия plugin и полноценный
Docker/Windows-профиль требуют отдельной приёмки. На этой машине настоящий
Docker Engine положительно не проверялся.

```sh
python -m shared.ctl docker-check --executable /absolute/path/docker \
  --executable-sha256 TRUSTED_SHA256 --socket-path /absolute/local/docker.sock --json
```

`TRUSTED_SHA256` заменяют настоящим доверенным хэшем. На Windows `--socket-path`
не задаётся. Таймаут выполнения каждой команды — до 10 секунд, завершение и
очистка могут занять ещё несколько секунд; проверка не использует shell.
При штатном исполнителе stdout ограничен 8192 байтами во время чтения, stderr
отбрасывается. На POSIX каждая команда запускается в отдельной группе процессов:
при таймауте или переполнении группе отправляется SIGKILL, а оставшиеся после
выхода CLI процессы той же группы не считаются успешной проверкой. Завершение
каждого потомка отдельно не подтверждается. На Windows
останавливается непосредственный процесс; завершение всех его потомков этим
механизмом не подтверждается. Процессы, покинувшие группу, и вредоносные
действия программы не изолируются. Внедрённый тестовый/сторонний `runner`
отвечает за собственные ограничения ресурсов и остановку процессов.

`shared/adapters_docker.py` реализует низкоуровневые порты управления сервисом
и HTTP health для Compose, сформированного `shared/render_docker.py` из
публичного манифеста **v1**. По умолчанию каждый вызов возвращает план без
процессов, сети и записи. **Реальный Docker в этом шаге не запускался;
install/update/restore/rollback и Docker/native-приёмка не выполнены.**

## Подписанный план нескольких компонентов v2

`shared.docker_recipe.plan_signed_compose` и API 1.33 `plan-signed-compose`
строят план из подписанного пакета с манифестом v2. Для выбранной цели
`{os: linux|windows, architecture: x86_64, execution: docker}` требуется явное
совпадение с `compatibility.targets`. Это проверка декларации, а не хоста,
архитектуры образа или установленного Docker.

В пакет включается `homensai/docker/recipe-v1.json` размером не более 64 КиБ:

```json
{
  "format": 1,
  "images": {
    "web": "registry.example/product/web@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "worker": "registry.example/product/worker@sha256:bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"
  },
  "web_component": "web",
  "container_port": 8080
}
```

`images` должен содержать ровно все имена компонентов подписанного манифеста;
ссылки ограничены поддерживаемым подмножеством имён и обязательным SHA-256
digest. Выбранные режимы должны включать `web_component`. Этот формат не
поддерживает разные web-компоненты для разных режимов, сервисные секреты и
hooks `pre_start`, `health_checks`, `post_update`: такие запросы отклоняются.
Команды берутся из подписанного манифеста; символ `$` экранируется для Compose.
План возвращается как детерминированный `compose_json` и его SHA-256; файлы
не создаются, процессы, образы и контейнеры не запускаются.
Интегратор передаёт и сохраняет отдельный `instance_id` — 32 строчных hex
символа. Имя Compose-проекта состоит из `product_id` и `instance_id`, поэтому
разные значения дают разные имена проектов и именованных томов. Повторное
использование одного ID не обеспечивает изоляцию и должно контролироваться
интегратором; само планирование ничего не резервирует в Docker.
Разные ID не устраняют конфликт одного и того же порта: одновременно
работающим установкам нужны разные порты в подписанных манифестах.

План использует независимые сервисы в порядке зависимостей, `pull_policy: never`,
пустой entrypoint, аргументы без неявного shell, UID 10001, read-only корень,
общий именованный том `/data`, удаление capabilities и `no-new-privileges`.
Порт из манифеста публикуется на `127.0.0.1` и направляется на `container_port`.
Внутри контейнера программа должна слушать доступный сетевой интерфейс, а том
должен быть подготовлен для нужных прав. Внешняя сеть контейнеров не отключена.
Зависимости задают порядок старта, но не подтверждают готовность сервисов.
Подпись пакета не доказывает безопасность кода или наличие, происхождение и
платформенную совместимость образов; `host_verified`, `images_verified`,
`containers_started` и `installation_complete` остаются `false`.

Семантика [Compose JSON](https://docs.docker.com/compose/support-and-feedback/faq/),
[`pull_policy`, entrypoint и command](https://docs.docker.com/reference/compose-file/services/),
[экранирования `$`](https://docs.docker.com/reference/compose-file/interpolation/)
и [публикации на loopback](https://docs.docker.com/engine/network/port-publishing/)
опирается на документацию Docker. Реальный Docker Compose v2 и этот план ещё
нужно проверить в целевых средах; запуск, обновление и резервное копирование
нескольких контейнеров здесь не реализованы.

## Подготовка Compose-файла

`shared.docker_prepare.prepare_signed_compose` и API 1.34
`prepare-signed-compose` повторно проверяют подписанный план и создают
`compose-<instance_id>.json` в существующем рабочем каталоге владельца с
правами 0700. Родительские каталоги и вызывающая сторона должны быть
доверенными. API доступен на Linux x86-64; цель в подписанном плане может
быть Linux или Windows, но это не проверка соответствующей системы.

Для операции нужен отдельный `idempotency_key`: 32 строчных hex символа,
которые интегратор сохраняет с исходным запросом и `instance_id`. Перед
созданием файла записывается устойчивая отметка `pending`, затем файл
создаётся эксклюзивно с правами 0600, синхронизируется и проверяется по
подписанному плану. Чужой существующий файл не заменяется. Повтор успешной
операции сверяет пакет, отметку, состав и права файла; незавершённый `pending`
требует ручной проверки и не запускается повторно. Возможный сбой после записи
не означает, что файл отсутствует. Каталог не очищается автоматически.

Ответ содержит имя файла и SHA-256; он не проверяет локальные образы, daemon,
платформенную совместимость или запущенные сервисы. Планирование и подготовка
не являются запуском и не доказывают безопасность подписанного кода.

## Проверка локальных ссылок образов

`shared.docker_images.inspect_signed_compose_images` и API 1.35
`inspect-signed-compose-images` работают на Linux x86-64. Они требуют ту же
подписанную подготовку и ключ, абсолютный путь к Docker CLI и его SHA-256 из
независимого доверенного источника, а также путь локального Unix socket. Сначала
проверяются отметка и подготовленный файл без их создания. Затем для каждой
уникальной ссылки из подписанного плана выполняется только
`docker image inspect --format '{{json .RepoDigests}}'`; CLI работает без shell
и с временной пустой конфигурацией, а его байты проверяются до и после вызова.

Ответ daemon должен содержать точную ссылку с digest; отсутствующие, неверные
или непонятные ответы дают ошибку. Запросы не содержат pull, build, up или stop.
На каждую команду задаётся таймаут 1–30 секунд, суммарный лимит ожидания
команд — до 300 секунд; проверка подписей и хэшей занимает дополнительное время.
stdout ограничен, stderr отбрасывается. Создание временной конфигурации и
блокировки делает операцию изменяющей в API. Результат
`daemon_reported_matches: true` отражает ответы конкретного daemon на момент
проверки; `image_contents_verified`, `publisher_verified`, `host_verified` и
`containers_started` остаются `false`. CLI, plugin, daemon, socket и рабочие
каталоги должны быть доверенными. Нет независимой проверки байтов, происхождения,
архитектуры или отсутствия вредоносного кода в образе. После проверки состояние
может измениться. Команда основана на официальной документации
[`docker image inspect`](https://docs.docker.com/reference/cli/docker/image/inspect/)
и [JSON-форматирования Docker](https://docs.docker.com/engine/cli/formatting/).
Пока проверялись только фиктивный CLI и сокет, не настоящий Docker Engine.

## Ограниченный запуск и остановка нескольких сервисов

`shared.docker_lifecycle.control_signed_compose` и API 1.39
`control-signed-compose` поддерживают один `start` и один последующий `stop`
подписанного плана на Linux x86-64. Для подготовки используется прежний
`idempotency_key`; для каждого действия нужен отдельный `action_id`, отличный
от ключа подготовки и ключа другого действия. Ключи и запрос сохраняет
интегратор. Операция запускает внешний Docker CLI и изменяет состояние daemon.

Перед первым запуском проверяются подпись, подготовленный файл, локальные
ссылки образов, версия Compose v2 и нужные флаги. Существующие контейнеры с
меткой проекта Compose и одноимённые том или сеть блокируют запуск. Затем команда
использует `up --detach --no-build --no-recreate --pull never`; после неё
проверяются ответы daemon о составе, состоянии и ссылках образов контейнеров.
Для каждого контейнера подписанная digest-ссылка разрешается в идентификатор
образа; он сравнивается с `.Image` контейнера. Ссылка и идентификатор повторно
проверяются после сравнения. Содержимое `.Config.Image` с тегом не используется
как доказательство. Совпадение зависит от достоверности ответов daemon и не
делает несколько запросов атомарными.
Для остановки нужна подтверждённая отметка первого запуска; `stop` не удаляет
контейнеры, тома или сеть. Повтор подтверждённого действия сверяет состояние,
но не отправляет команду снова.

До каждой изменяющей команды сохраняется `start_pending` или `stop_pending`.
При таймауте, потере процесса или ошибке после начала действия результат может
быть неопределённым: автоматический повтор блокируется и требуется ручная
проверка. API 1.39 поддерживает ограниченное согласование pending по уже
наблюдаемому состоянию, без повторного действия; подробности ниже. Повторных
циклов, обновления, резервного копирования или удаления здесь нет. Если подписанный Compose-файл
повреждён, операция остановки также отклоняется; для аварийного управления
нужна отдельная доверенная процедура. После аварийного завершения во время
проверки могут остаться временные каталоги конфигурации в рабочем каталоге.

Проверки конфликтов не атомарны относительно посторонних процессов и не
защищают от изменения daemon между запросами. CLI, Compose plugin, daemon,
socket, рабочий каталог и образы должны быть доверенными; ни их подлинность,
ни безопасность, ни готовность приложений не подтверждаются. В ответе
`health_verified`, `image_contents_verified`, `all_writers_verified` и
`installation_complete` равны `false`. Проверка проводилась с фиктивным CLI,
не с реальным Docker Engine. Описание команд — в документации Docker:
[`compose up`](https://docs.docker.com/reference/cli/docker/compose/up/),
[`compose ps`](https://docs.docker.com/reference/cli/docker/compose/ps/) и
[`compose stop`](https://docs.docker.com/reference/cli/docker/compose/stop/).

## API v1 для прежнего Docker-адаптера

```python
from shared.adapters_docker import DockerComposeAdapter

adapter = DockerComposeAdapter(manifest, absolute_compose_path,
                               runner=fake_runner, fetcher=fake_fetcher,
                               timeout=30, health_timeout=3)
argv = adapter.start()       # list[str], только план
adapter.stop()              # list[str], только план
adapter.ps()                # list[str], только план
adapter.logs()              # list[str], только план
health_plan = adapter.health()  # {"url": ..., "timeout": 3}

# Разрешение задаётся отдельно для каждого вызова. В тестах только фейки.
result = adapter.start(execute=True)  # результат runner, CompletedProcess
healthy = adapter.health(execute=True)  # True только при HTTP 200
```

| Метод | Запланированный argv после общего префикса |
|---|---|
| `start()` / `command("up")` | `up`, `-d`, `--no-build`, `--pull`, `never` |
| `stop()` / `command("stop")` | `stop` |
| `ps()` / `command("ps")` | `ps` |
| `logs()` / `command("logs")` | `logs` |

Общий префикс: `["docker", "compose", "-p", product_id, "-f", absolute_compose_path]`.
Произвольные действия/опции, build, down, hooks и миграции API не принимает.
Флаги `--no-build --pull never` запрещают Compose автоматически собирать или
скачивать образы при `up`; нужные образы должны быть заранее подготовлены и
находиться локально. Источник, подпись и digest локального образа эта команда
не проверяет. Требуется версия Docker Compose, поддерживающая эти флаги; на
реальном Docker изменение пока не проверено. [Описание флагов Docker Compose](https://docs.docker.com/reference/cli/docker/compose/up/).
`execute` принимает только bool; разрешение одного вызова не сохраняется.
Планирование допускает отсутствующий Compose и не создаёт его каталог.
Перед каждым исполнением адаптер читает обычный файл и требует точного
совпадения с Compose, сформированным из переданного манифеста; допустимы LF и
CRLF. Ссылки, hard links, слишком большой и изменившийся при чтении файл
отклоняются. Ручные правки требуют обновить поддерживаемый генератор; изменение
файла блокирует и остановку через этот адаптер, поэтому для аварийного управления
нужна отдельная проверенная процедура. Dry-run файл не читает.

`runner(argv, **kwargs)` — единственная точка исполнения процессов. По умолчанию
это `subprocess.run`; внедрённый runner получает ровно тот же контракт:

```python
runner(argv, shell=False, timeout=30, check=False,
       stdin=subprocess.DEVNULL, capture_output=True, text=True,
       cwd=str(compose_path.parent), env={"COMPOSE_DISABLE_ENV_FILE": "1"})
```

Окружение родительского процесса не читается и не передаётся. Единственная
фиксированная переменная отключает автоматический Compose `.env`. Настройки
DOCKER_HOST/CONTEXT/CONFIG, proxy, HOME и секреты из окружения не наследуются.
Реальная доступность Docker executable/daemon с таким минимальным окружением
не проверялась. Если нужен иной runner, вызывающая сторона отвечает за его
безопасность, конечный timeout и отсутствие чтения секретов. Программа Docker
и доверенный Compose при явном исполнении имеют собственные эффекты; адаптер
не является песочницей и не проверяет Docker config, образ и payload. Сравнение
с локальным генератором не подтверждает его происхождение или безопасность;
подмена файла между проверкой и чтением Docker не исключена. Эти флаги не
отключают сеть контейнеров и не ограничивают эффекты Compose, если генератор или
окружение были изменены.

Ненулевой returncode, TimeoutExpired и ошибки runner дают `DockerAdapterError`
с фиксированным текстом без stdout/stderr/argv/исходного исключения. Успешный
результат runner возвращается вызывающему коду; вывод ps/logs может содержать
продуктовые данные, поэтому адаптер его сам не печатает и не журналирует.

## Пути и health

Манифест проверяется существующим валидатором; product_id соответствует
`[a-z0-9][a-z0-9_-]{0,62}`. Compose — абсолютный путь текущей ОС к `.yml`/`.yaml`,
проверяемый `checked_path` при создании адаптера и перед каждой командой.
Запрещены обход `..`, UNC, drive-relative/ADS, управляющие символы,
зарезервированные имена Windows, ссылки/reparse points, каталоги вместо файлов
и shell-метасимволы `; | & $` и другие подстановки/кавычки. Пробелы и кириллица
допускаются и сохраняются отдельным аргументом. Shell-строки не строятся.
Гонки злонамеренной смены пути между проверкой и внешним чтением не исключены.

Health URL берётся только из проверенного v1: `http://127.0.0.1:<port>/<path>`,
порт совпадает с манифестом; localhost/DNS, IPv6, другие адреса, credentials,
query и fragment отвергаются. Путь соответствует контракту манифеста, например
`/healthz` или `/health/ready`. Fetcher имеет контракт
`fetcher(url, timeout=health_timeout) -> int`. По умолчанию используется stdlib
urllib с `ProxyHandler({})` и запретом redirect; тело ответа не читается, ответ
закрывается. Успех — только целое `200`; другие статусы, ошибки соединения и
таймауты дают обобщённый `DockerAdapterError`. Оба timeout конечны, больше 0
и не больше 600 секунд. Выполняется один запрос, без polling/retry.

Эти методы не реализуют полный Protocol `UpdatePorts`: v2-компоненты,
durable key/receipts, pre_start/health hooks, остановка всех внешних писателей,
архив, migration и rollback требуют отдельного адаптера. Прямого подключения
к `FilesystemPorts` или `UpdatePlan` нет; v2 явно отвергается, как и рендером.
HTTP 200 и нулевой код Compose не доказывают принадлежность установки,
идентичность выпуска, фактическую остановку всех писателей или готовность
install/update/restore/rollback. Разные установки с одинаковым product_id
не изолированы по Compose project; владение и сериализацию обеспечивает
вызывающая сторона. Сборка образа и проверка digest также не реализованы.

## CLI: только план

```powershell
py -3.14 -B -m shared.ctl --manifest examples/jobpilot.manifest.json docker-plan --compose-file build/jobpilot/compose.yml --action up
py -3.14 -B -m shared.ctl --manifest examples/jobpilot.manifest.json docker-plan --compose-file build/jobpilot/compose.yml --action logs --json
```

`--action` обязателен: `up`, `stop`, `ps` или `logs`. JSON сохраняет существующий
конверт CLI, `data` содержит ровно `dry_run: true` и `argv: list[str]`. Текст
содержит русский статус и JSON-массив argv для сохранения границ аргументов.
Относительный `--compose-file` разрешается относительно cwd; файл может ещё
не существовать. Ничего не записывается, runner/fetcher не вызываются.
Флага `--execute` и команд исполнения в CLI нет. Общие коды: 0 — план построен,
2 — неверный ввод, 1 — ошибка локального I/O. V2 не поддерживается.

### Эксперимент Compose с изолированным Podman (02.11.2026)

На Linux x86_64 отдельно от штатного хранилища был запущен rootless Podman
4.3.1 с драйвером vfs и собственным Unix-сокетом. Standalone Compose v2.39.4
создал, запустил, показал через `ps --format json`, остановил и удалил один
тестовый контейнер Alpine с запретом сети, `read_only`, `cap_drop: ALL` и
непривилегированным UID. Использована локальная ссылка образа
`docker.io/library/alpine@sha256:2e0b81d60597f449baa56dc25d355367869d2dca4cd57e866f1e2b52af3eb55f`;
проверка издателя и содержимого образа в этом эксперименте не проводилась.
Созданный контейнер удалён; штатное хранилище Podman не использовалось.
После десятисекундного ожидания завершения по SIGTERM Podman сообщил о
принудительном SIGKILL; штатное мягкое завершение этим опытом не подтверждено.

Этот эксперимент не запускал подписанный план через API и не подтверждает
Docker Engine, установку или жизненный цикл приложения. Подтверждена важная
несовместимость: Podman вернул в `.Config.Image` тег `docker.io/library/alpine:3.22`
вместо запрошенной digest-ссылки. Управление в версии API 1.36 отклонило такой
ответ и оставило состояние неопределённым; автоматический повтор недопустим.
Проверка идентичности по идентификаторам добавлена позднее в API 1.38. Проверен также
формат 12-символьного идентификатора контейнера, который может вернуть Compose.

### Управление API через экспериментальный Podman-переходник (02.11.2026)

Отдельно выполнены два запуска `control-signed-compose` с настоящим подписанным
пакетом, подготовленным через API, официальным Compose v2.39.4 и rootless Podman
4.3.1 в собственном хранилище. Использовался локальный тестовый переходник CLI,
который передавал команды Compose и Podman в отдельный Unix-сокет; это не
официальный Docker CLI и не поддерживаемый адаптер продукта.

В обоих опытах команда запуска создала три контейнера, после чего API вернул
`docker_control_failed` и сохранил `start_pending`. В одном из опытов локальный
HTTP health ответил успешно; повтор того же запроса не вызвал ни одной команды
CLI и не изменил `start_pending`. В повторном опыте отдельно подтверждено,
что `.Config.Image` контейнера, созданного через Compose по digest-ссылке,
содержал локальный тег; это не соответствует закреплённому значению. API 1.36
не мог подтвердить такой запуск. Экспериментальные контейнеры,
сеть и тома затем удалены вручную в отдельном хранилище.

Запись `start_pending` сама по себе не определяет фактическое состояние daemon.
API 1.37 `compose-control-status` читает привязанный журнал без запуска CLI и
работает при отсутствующем socket. На журнале первого опыта получено
`start_pending`, при этом `daemon_state_verified` и `recovery_authorized` равны
`false`. На момент этого эксперимента операции согласования ещё не было;
ограниченное согласование добавлено в API 1.39. Автоматический повтор запрещён.
Docker Engine и приёмка настоящего установщика этими экспериментами не подтверждены.

### Сверка идентификаторов и start/stop через API (03.11.2026)

В API 1.38 проверка больше не отклоняет контейнер только потому, что daemon
вернул тег в `.Config.Image`: вместо него сравниваются проверенная digest-ссылка
и полные идентификаторы образа. Контрольные проверки отклоняют отсутствующую
digest-ссылку, некорректный идентификатор, несовпадение и наблюдаемое изменение
идентификатора. Изменения между запросами по-прежнему возможны; движок должен
быть доверенным и не должен параллельно изменяться другим управляющим процессом.

В отдельном rootless Podman 4.3.1 через тестовый CLI-переходник и Compose
v2.39.4 API успешно запустил и остановил три сервиса подписанного тестового
плана. Проверены loopback health и сохранение SQLite, настроек и двух heartbeat
на томе после остановки; тестовые ресурсы затем удалены вручную. Это не проверка
официального Docker CLI, Docker Engine, обновления, отката или Windows. Ранее
оставленные записи `start_pending` этим изменением не разрешаются автоматически.

### Согласование неопределённого результата (03.11.2026)

API 1.39 допускает `reconcile-start` и `reconcile-stop` с прежним ключом
действия. Проверяются состав и состояния контейнеров, идентификаторы образов,
хэши конфигурации, полученные через `compose config --hash '*'`, метки
контейнеров и повторное состояние состава. Только после этого журнал переводится
в `running` или `stopped`; `up`/`stop` повторно не вызываются. Несовпадение,
неполный состав или недоступный движок оставляют `pending`. Метки можно
подделать, проверки не атомарны и не подтверждают всех настроек, здоровья,
безопасности образов или отсутствия внешних писателей: необходимы доверенные
CLI, daemon и отсутствие параллельного управления этими ресурсами.

На изолированном Podman/Compose с тестовым переходником в отдельных опытах
намеренно терялся ответ после фактически выполненных `up` и `stop` трёх
сервисов. `reconcile-start` и `reconcile-stop` подтвердили соответствующее
состояние без повторения исходных команд; тестовые ресурсы удалены. Проверялась
потеря результата после завершения команды, а не обрыв во время её выполнения;
Docker Engine ещё не проверен. Исторические записи pending не меняются автоматически.
