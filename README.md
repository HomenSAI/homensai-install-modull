# homensai-install-modull

Общий модуль установки HomenS.AI: Docker, Windows и Linux-установщики, которые
подключаются к любой программе семейства (JobPilot Pro, Rent и др.).

**Подключение продукта — [установочный комплект](docs/KIT.md):**
`python -m shared.kit` собирает из проекта единый подписанный комплект для
Linux x86-64 и Windows x86-64 со встроенным Python, зависимостями и
установщиком `setup.sh` / `setup.cmd` (install, update с откатом, status,
uninstall, secrets). Python и сеть на целевой машине не нужны.

**Без командной строки — [веб-страницы](docs/WEB.md):** сборщик комплектов
в Docker (`docker/builder`) и страница установщика из самого комплекта
(`setup-web.cmd` на Windows, `setup.sh web` на Linux), только на 127.0.0.1.

**Статус (05.11.2026): экспериментальный, не выпуск.** Полный жизненный цикл
комплекта проверен на вымышленном продукте на чистом Debian без Python в
изолированном user-systemd и на Windows 10 в тестовой ВМ (см.
[WORK-PLAN](docs/WORK-PLAN.md)), включая доставку секретов продукта службам
и миграциям. Не реализованы Docker-комплект и приёмка на физических
системах; реальный продукт (Rent) требует адаптера —
[integration/RENT.md](docs/integration/RENT.md). Ничего не
объявлять готовым без тестов.

## Структура

| Папка | Назначение |
|---|---|
| `docker/` | образ, compose, healthcheck, тома данных |
| `windows/` | PowerShell-установщик, лаунчер, DPAPI, ACL, позже Setup.exe |
| `linux/` | systemd/скрипты |
| `shared/` | общее: архив перед заменой, DataHome, миграции, откат, ключи |
| `tests/` | проверки установки/обновления/отката |
| `docs/` | требования, концепция; `docs/origin/` — материалы Rent (справочно) |

Цель интерфейса модуля: продукт задаёт манифест (имя, порт, папка данных,
команда миграций, healthcheck), модуль выполняет установку, обновление с
полным архивом, откат и удаление.

См. [docs/REQUIREMENTS.md](docs/REQUIREMENTS.md), [STATUS.md](STATUS.md); опись работы и что доделать — [HANDOFF-2026-11-05](docs/HANDOFF-2026-11-05.md).

Руководства: [администратора](docs/ADMIN-GUIDE.md) и
[разработчика адаптера продукта](docs/ADAPTER-GUIDE.md). Удаление с
сохранением данных и переустановка Linux user-systemd —
[UNINSTALL](docs/UNINSTALL.md).

Актуальное состояние и результаты проверок — в [плане работ](docs/WORK-PLAN.md).
Для ограниченной первой установки Linux user-systemd разрабатывается
[интерактивный сценарий](docs/INTERACTIVE-INSTALL.md), использующий подписанный
пакет и локальный API. Приведённые ниже описания шагов сохраняют историю ранних
прототипов; они не отражают все последующие возможности и ограничения.

Шаг 1: [контракт манифеста](docs/MANIFEST.md),
[пример JobPilot](examples/jobpilot.manifest.json),
[происхождение](docs/PROVENANCE.md). Проверка манифеста и рендер Docker-заготовок
реализованы; готовность установки и обновления этим не подтверждается.

В разработке: [сборка и проверка единого ZIP-пакета](docs/PACKAGE.md) с полным
перечнем и ожидаемым SHA-256; экспериментальные проверка Ed25519 и изолированная
подготовка payload требуют внешний доверенный ключ. Управление ключами и
установка ещё не реализованы; хэш не заменяет доверенный источник и проверку
издателя, а подготовка не является готовой процедурой установки.

Шаг 4: [генераторы служб и возобновляемая транзакция update/rollback](docs/UPDATE.md)
через внедряемые порты. Реальные службы, миграции и шифрованные копии
требуют адаптеров; готовых установщиков по-прежнему нет.

Шаг 5: [локальный CLI](docs/CLI.md), `python -m shared.ctl --manifest FILE COMMAND`:
валидация, план без записи, рендер Docker/служб, полный ZIP/проверка/восстановление
в отдельный каталог и чтение статуса UpdatePlan. Реальные адаптеры исполнения
не реализованы; ZIP не зашифрован. Готовых установщиков по-прежнему нет.

В разработке: [локальный API](docs/API-DESIGN.md) и частичная
[предварительная проверка свежей установки](docs/PREFLIGHT.md). Они не
устанавливают продукт и не подтверждают права, совместимость или готовность хоста.

Шаг 6: [локальные файловые порты и E2E](docs/E2E.md) — staged release,
атомарный pointer, ZIP/restore, crash-resume и stale detection блокировки.
Службы/миграции/health внедряются как фейки; ZIP не зашифрован, Docker/native
не приняты. Готовых установщиков по-прежнему нет.

Шаг 7: [Compose-адаптер и docker-plan](docs/DOCKER-ADAPTER.md) — argv
up/stop/ps/logs и loopback HTTP health для Docker-рендера v1. По умолчанию
только план; библиотечные эффекты требуют отдельного `execute=True` и проходят
через runner/fetcher. CLI показывает только dry-run. Реальный Docker и
install/update/restore/rollback-приёмка не выполнялись; установщик не готов.

K2: [шифрование полного архива](docs/ARCHIVE.md#шифрование) через необязательный
`cryptography`, AES-256-GCM по блокам и scrypt. CLI `archive-create --encrypt`,
verify/restore с автоопределением; FS-порты принимают внедрённый provider пароля.
Версии и хэши кандидатов для CPython 3.14 x86-64 закреплены в
[CRYPTO-LOCK](docs/CRYPTO-LOCK.md); выпуск и Windows-проверка ещё не приняты. Без пакета шифрование явно
отказывает, обычный ZIP работает. Готовность установщиков этим не подтверждается.
