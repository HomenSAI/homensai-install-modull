# Экспериментальное управление пользовательским systemd

## Публикация подписанных unit-файлов

`shared.services.render_fixed_user_services` формирует тексты user-units по
манифесту и выбранным режимам без записи и запуска. Исполняемые файлы должны
быть абсолютными путями, каталог `app` — относительным к указанному корню;
управляющие символы запрещены. Генератор отклоняет сервисные секреты, потому
что их безопасная доставка пока не реализована. Он не очищает всё окружение,
которое наследует user-manager. systemd отдельно предупреждает, что
[переменные окружения не подходят для секретов](https://freedesktop.org/software/systemd/man/latest/systemd.exec.html).
Нет секции автозапуска или команды enable.

Результат содержит конкретный абсолютный корень: файлы следует включить в
пакет до его подписи, причём будущий корень должен быть известен заранее.
Это экспериментальный путь для фиксированной установки, не решение для
переносимого единого пакета с произвольным каталогом назначения. Генератор не
проверяет безопасность команд и не поставляет runtime.

Начиная с API 1.16 публикация может явно запросить `verify_generated_units:
true`: перед записью подписанные файлы сравниваются с результатом этого
генератора для манифеста и указанного корня. Несовпадение приводит к отказу
до вызова менеджера и записи unit-файлов. По умолчанию проверка не включена,
чтобы сохранить возможность публикации других подписанных unit-файлов; ключ
повтора привязан и к выбранной политике. Сравнение не гарантирует, что каждый
аргумент команды указывает внутрь установки, и не удостоверяет безопасность
программы или состояние системы после проверки. Алгоритм генерации пока не
версионирован: изменение генератора может привести к отказу для старого пакета.

### Экспериментальный переносимый рецепт

`shared.systemd_portable.plan_portable_signed_user_units` проверяет подписанный
пакет и подготовленный выпуск и требует включённый в подписанный состав файл
`systemd-user/portable-v1.json` с точным содержимым `RECIPE_V1`. Рецепт v1
разрешает формирование unit-файлов после выбора корня. Его нельзя смешивать с
другими файлами внутри `systemd-user/`. Сам планировщик возвращает тексты и
их SHA-256; он не публикует файлы, не обращается к менеджеру и не запускает
код.

В аргументах выбранных компонентов манифеста `@app`, `@data`, `@runtime`,
`@release` и их варианты с безопасным относительным суффиксом обозначают
каталоги внутри выбранного корня. `@release` указывает на `releases/app-<версия>`.
Исполняемый файл должен использовать `@runtime/…` или `@release/…`; обходы
`..`, пустые сегменты, неизвестные обозначения и сервисные секреты запрещены.
Другая часть аргументов остаётся буквальной. Генератор v1 экспериментален и
ещё не является стабильным контрактом для распространения старых пакетов.
Рецепт не доказывает безопасность кода, отсутствие ссылок на внешние файлы в
runtime, безопасную доставку секретов или соответствие фактического процесса
подписанному содержимому. Доверие к локальному установщику тоже необходимо.

`shared.systemd_portable.publish_portable_signed_user_units` экспериментально
публикует полученные файлы в проверенный каталог user-manager. По умолчанию он
возвращает план, а запись требует `execute=True` и ключа `operation_id`.
Рецепт и выпуск повторно проверяются под блокировками; отметка публикации
связывает генератор, ключ, корень и хэши. При `pending` повтор запрещён;
повтор подтверждённого `done` сверяет файлы и не перезаписывает их. Операция
не выполняет reload, enable или start. Имена служб основаны на product_id,
поэтому две установки одного продукта в одном менеджере пока конфликтуют.
API 1.17 предоставляет `plan-portable-systemd-user-units`,
`publish-portable-systemd-user-units` и `load-portable-systemd-user-units`;
контракт приведён в `API-DESIGN.md`. Запуск переносимых units через API пока
не подключён; runtime и его возможные ссылки не проверяются этой публикацией.

`shared.systemd_user_load.load_portable_signed_user_units` экспериментально
загружает опубликованные переносимые units. Он повторно проверяет рецепт и
выпуск, требует отметку публикации, привязанную к тому же корню и составу,
и перед настоящим `daemon-reload` записывает `pending`. После `done` повтор
проверяет состояние без второго reload; `pending` блокирует повтор. Для
наблюдения без reload доступен `inspect_pending_portable_user_units`, а после
подтверждённой загрузки `portable_signed_user_group` строит группу без запуска.
Загрузка требует отдельный ключ, отличный от ключа публикации. `daemon-reload`
влияет на весь пользовательский менеджер, включая другие ожидающие изменения.
Неопределённый результат автоматически не разрешается. Состояние unit не
доказывает безопасность исполняемого кода или подлинность runtime.

`shared.systemd_user_publish.publish_signed_user_units` — отдельный
экспериментальный шаг подготовки пользовательских служб на Linux x86-64.
Проверенный подписанный v2-пакет должен содержать файл
`systemd-user/<product_id>-<component>.service` для каждого компонента выбранных
режимов. Сначала проверяются подпись, текущая цель, журнал подготовки, указатель,
полное дерево размещённого выпуска и хэши этих файлов. Значения в unit-файлах
должны быть публичными; пароли и другие секреты туда включать нельзя.

```python
from shared.systemd_user_publish import publish_signed_user_units

plan = publish_signed_user_units(
    package_path, envelope, install_root,
    trusted_public_key=publisher_key, expected_product_id=product_id,
    expected_version=version, modes=('autonomous',), unit_dir=unit_directory,
)
# После проверки плана тот же вызов с execute=True публикует файлы.
```

Вызов по умолчанию (`execute=False`) возвращает имена и хэши и не вызывает
systemd и не записывает файлы. При `execute=True` каталог задаётся явно и должен
быть существующим каталогом текущего непривилегированного пользователя в
`UnitPath` его менеджера; каталоги-родители должны быть защищены от записи
группой и другими пользователями, ссылки запрещены. Поддерживаются пути без
пробельных символов. Функция проверяет, что менеджер не знает имён служб,
и отказывает при существующих файлах, маркере или соседних `.service.d`.
Файлы создаются без перезаписи с режимом 0600 и проверяются после записи.

Публикация удерживает существующие блокировки подготовки и операции через
совместимый POSIX `flock`, не перезаписывая их содержимое. Метка прежней
незавершённой операции или занятая блокировка дают отказ: восстановление
сначала должно выполнить ответственное за неё средство. Наличие журнала
обновления также приводит к отказу: повторная публикация после обновления ещё
не реализована. До записи создаётся
`.<product_id>.homensai-units.pending`; при ошибке он и уже записанные файлы
сохраняются для ручного разбора. Повтор не перезаписывает их. Успешное удаление
маркера не доказывает, что ответ функции был получен; отсутствие маркера само
по себе не является автоматическим разрешением на очистку.

Экспериментальный вызов с `operation_id` (32 строчных шестнадцатеричных знака)
перед записью фиксирует отдельную отметку `pending` в защищённом каталоге
установки. Она связана с выпуском, установкой, ключом издателя, режимами,
каталогом и составом units. После публикации отмечается `done`; повтор того же
ключа проверяет отметку, состав файлов, отсутствие маркера и соседних drop-in,
а также принадлежность каталога менеджеру. Он не перезаписывает файлы и не
вызывает reload или start. `services_started: false` означает, что текущий
вызов не запускал службы, а не гарантирует их текущее состояние. Другой ключ,
повтор без ключа или `pending` приводят к отказу. Загрузка units также
отказывает при `pending`. Если ответ потерян до записи `done`, даже наличие
всех файлов не позволяет автоматически считать публикацию завершённой.
Автоматическое восстановление этой отметки пока не реализовано; журнал не
защищает от вредоносного кода с теми же правами пользователя.

Функция не делает `daemon-reload`, `enable`, `start` или удаление. Она доступна
через локальную операцию API 1.14 `publish-systemd-user-units` с обязательным
ключом операции; контракт и ограничения приведены в `API-DESIGN.md`.
Записанные файлы могут быть обнаружены при
последующей загрузке менеджера, поэтому публиковать следует только проверенный
выпуск. Подпись не доказывает отсутствие вредоносных директив; синтаксис и
безопасность содержимого автоматически не анализируются. Возможны более общие
systemd drop-ins вне проверенного каталога: перед запуском адаптер обязан
проверить фактическую конфигурацию менеджера. Гонки со сторонним процессом с
теми же правами, ACL и внезапная потеря питания полностью не исключены. Этот
шаг не является регистрацией, запуском или приёмкой всей установки.

## Загрузка опубликованных unit-файлов

`shared.systemd_user_load.load_signed_user_units` — следующий
экспериментальный Python-этап. Он принимает те же данные подписанного выпуска,
режимы и каталог, что публикация. По умолчанию возвращает план без systemd и
записи; при явном `execute=True` повторно проверяет выпуск, каталог, отсутствие
маркера публикации и соседних drop-in, состояние ранее не запущенных units и
выполняет `systemctl --user daemon-reload`. Затем он требует, чтобы менеджер
показывал именно ожидаемые файлы, отсутствие drop-in и состояние inactive/dead.
Он не делает `enable`, `start`, миграцию или установку продукта.
Ранее существовавшие ссылки автозапуска в других каталогах менеджера пока не
проверяются: отсутствие вызова `enable` не доказывает их отсутствия.

`daemon-reload` относится ко **всему пользовательскому менеджеру**, поэтому он
может применить и другие ожидающие изменения его конфигурации. Перед вызовом
нужны доверенный менеджер и согласование с управлением системой. Содержимое
подписанных unit-файлов автоматически не анализируется на вредоносное поведение;
подпись и проверка пути не доказывают безопасность.

Перед вызовом менеджера создаётся защищённая отметка
`.homensai-control/user-systemd-reload.json` со статусом `pending`. Она
привязана к выпуску, установке, ключу и составу units. При потере ответа или
сбое `pending` сохраняется и **автоматический повтор запрещён**. После
подтверждения записывается `done`; повтор `done` только проверяет состояние и
не вызывает `daemon-reload`. Изменённая отметка, занятая или осиротевшая
блокировка, журнал обновления, чужой путь или конфликт состояния приводят к
отказу. Автоматическое разрешение `pending`, восстановление после потери
питания ещё не реализованы.

API 1.15 предоставляет явную изменяющую операцию `load-systemd-user-units` с
ключом загрузки. Ключ связывается с отметкой и составом режимов: другой ключ
или отсутствие ключа не позволяют повторить привязанную операцию. Для прямого
Python-вызова соответствующие `inspect_pending_user_units` и
`signed_user_group` также принимают этот ключ. Устаревшие вызовы без ключа
сохраняют прежний формат привязки. Операция влияет на весь пользовательский
менеджер; опубликованный API сам по себе не означает разрешения вызывать её
на постороннем сеансе или подтверждения безопасности кода в unit-файлах.

`shared.systemd_user_load.inspect_pending_user_units` позволяет отдельно
наблюдать `pending`, используя те же подписанный пакет, ключ, корень, режимы и
каталог. Под блокировками он сверяет журнал, файлы и текущее состояние всех
units (`inactive/dead`, ожидаемый путь, без drop-in и `NeedDaemonReload=no`).
При успехе результат содержит `state: pending_observed` и
`reload_completion_verified: false`. Никакой повторный `daemon-reload` не
отправляется и отметка `pending` не изменяется; при несовпадении также следует
отказ без её изменения. Поэтому этот результат не разрешает автоматически
продолжать установку или считать глобальную перезагрузку завершённой.
Запрос `systemctl show` может привести к загрузке описания unit в память
менеджера, хотя он не запускает службу; проверка не является гарантированно
неизменяющим вызовом по отношению к состоянию самого менеджера.

Документация systemd описывает `Reloading` как [сигнал до и после операции](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.systemd1.html).
Наблюдение текущих свойств unit после потерянного ответа не является записью
получения завершающего сигнала и не удостоверяет исход глобальной операции.

Проверки `FragmentPath` и файла не доказывают, что менеджер прочитал именно
эти байты; процессы с теми же правами могут менять файлы или состояние между
проверками. До выпуска нужны защищённая среда, обработка изменений внешней
конфигурации и приёмка на целевой Linux-системе.

Отдельная экспериментальная проверка выполняет настоящий `daemon-reload` в
одноразовом rootless Podman-контейнере с собственными пользовательским
менеджером и D-Bus: `python3 tests/run_isolated_systemd_test.py --run`.
Проверены публикация подписанных синтетических unit-файлов, загрузка без
запуска служб и повторный вызов без повторной перезагрузки менеджера. В другом
варианте теста после загрузки существующие адаптеры запускают и останавливают
группу из трёх синтетических служб. Их исполняемый процесс — `sleep`, а не
реальный продукт; группа строится по подписанному выпуску.
При очистке тест вызывает ещё один reload в контейнере. Код проекта монтируется
только для чтения, пользовательский менеджер хоста не перезагружается. Для
запуска нужны Podman, доступ к сети и загрузка тестовых зависимостей; версии
образа по digest, системных пакетов и pytest не закреплены. Это не проверка
воспроизводимости сборки, полноценной установки или восстановления после сбоя.

Тот же контейнерный запуск включает `test_isolated_signed_demo.py`: локальный
пример клиента вызывает API подготовки подписанного тестового выпуска,
публикации и загрузки units; затем Python-группа отдельно запускает web и
worker из подготовленного выпуска. Проверяются локальный ответ здоровья,
heartbeat и остановка группы. Тест генерирует и подписывает unit-файлы,
использует Python контейнера и синтетические записи о runtime. Он не проверяет
поставку собственного runtime, переносимые units для произвольного продукта,
запуск через API или обновление и восстановление на чистой машине. Проверка
HTTP-ответа не подтверждает принадлежность порта процессу.

`shared.systemd_user.SystemdUserAdapter` управляет одним уже загруженным
пользовательским unit в `systemctl --user`. Имя строится из проверенного
`product_id` и выбранного компонента. Вызывающая сторона передаёт абсолютный
путь unit и SHA-256 из независимого доверенного источника; адаптер не считает
хэш, полученный вместе с непроверенным файлом, доказательством происхождения.

Конструктор и `command(..., execute=False)` не исполняют команды. Для явного
`execute=True` доступны только `start` и `stop`. Перед действием проверяются
имя и состояние unit в менеджере, точный `FragmentPath`, отсутствие drop-in,
`NeedDaemonReload=no`, тип, владелец и права родительских каталогов/файла,
отсутствие ссылок и совпадение хэша. После команды проверяется состояние
менеджера. Для временного unit допустимо подтверждение его выгрузки после stop.
Никакие команды продукта, unit-файлы или секреты не передаются через shell.
Вывод systemctl ограничен, stderr не раскрывается, timeout завершает процесс
systemctl. Конфигурация среды systemctl ограничена фиксированными переменными.

`active` — лишь статус менеджера, не health приложения. Остановка unit сама по
себе не доказывает остановку всех писателей вне его контроля. Если systemctl
превысил timeout или последующая проверка не удалась, эффект мог уже произойти;
вызывающая сторона должна проверить состояние прежде чем принимать решение о
повторе. Этот адаптер не реализует устойчивые ключи UpdatePorts, не устанавливает
и не удаляет units, не выполняет daemon-reload, не управляет системными
(root) службами и не подключён к публичному API или транзакции установки.

`shared.systemd_group.SystemdUserGroup` объединяет заранее заданные адаптеры
всех компонентов выбранных режимов: start идёт в порядке зависимостей, stop —
в обратном. Перед первым действием проверяются все units, а после — все состояния;
в переходном или ошибочном состоянии группа отказывает. При ошибке часть служб уже
может изменить состояние; автоматического отката нет. Повторная проверка
выгруженного временного unit допустима только после успешной проверки его
идентичности в рамках этого экземпляра адаптера. Группа не доказывает, что все
внешние писатели остановлены, и не заменяет устойчивые порты UpdatePlan.

`shared.systemd_user_load.signed_user_group` экспериментально создаёт такую
группу из подписанного пакета и ранее подготовленного выпуска. Функция требует
точно соответствующей отметки `done` загрузки, повторно проверяет подпись,
выпуск, имена, хэши, каталог и состояние неактивных units. Без отметки или с
`pending` она отказывает, не выполняя reload или start; саму группу нужно
запускать отдельным явным вызовом. Полученная группа проверяет файлы и состояние
перед действиями, но не перепроверяет пакет и отметку на каждом действии;
проверки не устраняют гонки и не подтверждают безопасность кода. Функция пока
не подключена к публичному API и полному жизненному циклу установки.

`shared.systemd_lifecycle_port.SystemdLifecyclePort` экспериментально связывает
уже созданную группу с конкретным `UpdatePlan(guard_effects=True)` и файловыми
портами. Допускаются только выбранные компоненты, подтверждённый checkpoint и
пустой список `pre_start` хуков. Перед вызовом пишется отдельная `pending`
отметка, после проверки состояний — `done`; повтор `done` заново читает состояние
без запуска команды, а `pending` или повреждённая отметка останавливают работу.
Журнал привязан к плану, установке и заявленным путям/хэшам unit-файлов.
Пока нет автоматического разрешения неопределённого результата и полноценного
подключения через API. Это пользовательские, заранее существующие службы;
регистрация units, хуки и гарантия остановки писателей вне группы отсутствуют.
Контекст и отметки не защищают от кода или изменения файлов с теми же правами.

Для отдельного известного ключа **остановки** можно явно создать порт с `reconcile_key` и
возобновить guarded-план с `resume_indeterminate=True`. Порт без повторной
команды проверяет все выбранные units и, только если они уже находятся в
нужном состоянии, переводит точную отметку `pending` в `done`. При несовпадении
состояния, ключа, файла или состава группы работа остаётся остановленной.
Проверка подтверждает текущее состояние менеджера, а не причину его достижения
или остановку внешних писателей. Этот режим доступен только Python-интегратору;
подтверждение запуска по одному статусу `active` не поддерживается, поскольку
этот статус не удостоверяет загруженный выпуск. API пользователя и безопасное
разрешение неопределённой миграции не реализованы.

Проверки файла и состояния не исключают гонку процесса с теми же правами, не
удостоверяют, что менеджер загрузил именно проверенные байты, и не подтверждают
безопасность исполняемого кода. Нужны защищённый канал подписи и контроль
владельца, а также приёмка на фиксированных дистрибутивах Linux. Drop-in пока
запрещены, поэтому существующий bundle `render_linux` с override ещё не может
использоваться напрямую.

На хосте с systemd 254 проверены временные user-units со случайными именами:
остановка и повторный запуск, отказ при неверном хэше и очистка; отдельно
проверена группа из трёх временных служб. Проверка также запускалась на Python
3.14, извлечённом временно из тестового контейнерного образа. Отдельный тест
запускает web и worker вымышленного продукта как временные службы, проверяет
его HTTP-ответ и heartbeat до и после остановки и запуска группы. Это не
проверка регистрации служб или полного цикла установки и обновления.

Дополнительный opt-in тест связывает `SystemdUserGroup` с `UpdatePlan` через
тестовый мост: подписанные синтетические выпуски, шифрованные архивы,
SQLite-миграция и проверка/откат демонстрационного продукта выполнялись на
реальном user systemd. В актуальном тесте запускается проверенная миграция из
подписанного выпуска; намеренный отказ миграции оставляет службы остановленными
и транзакцию в состоянии `indeterminate`, доступном для чтения через API.
Тестовый мост не является долговечным production-портом:
повтор после аварии и остановка всех внешних писателей не подтверждены, хуки
подменены. Доверие к временным unit-файлам в этом тесте создаётся самим тестом.

Такие тесты выполняются только при `HOMENSAI_TEST_REAL_SYSTEMD=1`, создают
собственные временные службы пользователя и не меняют чужие units. Это не
приёмка всей платформы Linux и не проверка root-служб.
