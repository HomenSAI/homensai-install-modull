# Вымышленный тестовый продукт

© 2026 Serhii Khomenko · HomenS.AI

`main.py` — синтетический продукт для разработки установщика. Он не является
адаптером JobPilot или поставкой для конечного пользователя. Python 3.14+;
только стандартная библиотека. Данные — только в явно заданном `--data-dir`.
При первом открытии базы создаётся `settings.json` с вымышленным именем; файл
существующих настроек при повторном запуске не перезаписывается.

Команды `migrate`, `serve` и `worker` моделируют соответственно транзакционную
миграцию SQLite, HTTP-службу на 127.0.0.1 и отдельный процесс с heartbeat.
Команда `python -B examples/demo_product/build_releases.py <пустой-каталог>`
создаёт `app-1` и `app-2` с собственным `release.json` и копией `main.py`.
Параметр `--release` при запуске выпуска не может подменить его версию; версия 1
отвергает `schema-2`. При запуске непосредственно из исходного каталога версии
можно задавать через `--release 1`/`2`. Идентификаторы миграции — `schema-1` и
`schema-2`. `--fail before/during/after` имитирует ошибки миграции; `after`
имитирует ошибку после commit: повторный запуск не добавляет запись повторно.
Для сервера `--fail start/health` имитирует отказ запуска/здоровья. Сервер
принимает `--port 0` и сообщает выбранный локальный порт через stdout.
По умолчанию сервер слушает только `127.0.0.1`. Явный параметр
`--listen 0.0.0.0` позволяет принимать соединения внутри контейнерной сети;
в обычной системе он открывает сервер на всех интерфейсах и требует отдельной
изоляции. Сам параметр не ограничивает доступ и не публикует порт.
На POSIX для `serve` и `worker` параметр `--fail stop` заставляет процесс
игнорировать SIGTERM, чтобы проверить отказ остановки и блокировку архивации.
Тест обязан принудительно завершить созданные им процессы. На Windows такое
поведение остановки отдельно не проверено.

Это модель: она не доказывает свойств произвольной продуктовой миграции,
безопасного завершения процессов или защиты данных при реальной потере питания.
Не направлять её на реальные каталоги и базы. Тестовая подготовка первого
подписанного выпуска подключена к сценарию обновления и отката; миграция в этом
сценарии запускается тестом. Дополнительные проверки используют реальные
дочерние web/worker-процессы и loopback health, но не регистрируют системные
службы и не заменяют полноценный установщик.

`Containerfile` создаёт экспериментальный образ тестового сервера для Linux
x86_64: исходник копируется в образ, запускается UID 10001, данные хранятся в
`/data`. Базовый образ Python зафиксирован по digest; перед сборкой его нужно
отдельно получить и проверить происхождение. Команда ниже не скачивает образы
во время сборки и не требует сетевых шагов:

```sh
podman build --pull=never --network=none -t localhost/homensai-demo-test \
  -f examples/demo_product/Containerfile examples/demo_product
```

2 ноября 2026 года сборка и запуск без сети проверены на rootless Podman 4.3.1
в отдельном хранилище: `/health` ответил успешно из контейнера, созданы SQLite
и синтетические настройки на именованном томе. В первом запуске потребовался
SIGKILL; после добавления обработчика SIGTERM повторный контейнер завершился
с кодом 0 в пределах четырёх секунд. Это наблюдение не заменяет проверки
остановки в других средах и при незавершённых операциях записи.
Проверка не использовала подписанный пакет или API и не подтверждает Docker
Engine, публикацию порта, Windows либо готовую установку. Образ и его базовый
образ не включены в репозиторий; перед распространением надо проверить все
лицензии и происхождение компонентов [официального Python-образа](https://github.com/docker-library/python).

Для воспроизводимой подготовки трёх сервисов соберите локальный образ, получите
его локальную digest-ссылку из `podman image inspect` и передайте её вместе со
свободным loopback-портом и новым каталогом:

```sh
python -m examples.demo_product.build_compose_demo /путь/к/новому-каталогу \
  --image 'localhost/homensai-demo-test@sha256:<digest>' --port 43817
```

Нужны Python 3.14 и `cryptography`. Скрипт создаёт синтетический пакет,
одноразовую подпись и запрос `api-request.json`, затем готовит Compose через
`prepare-signed-compose`; он не запускает контейнеры. Ключ создан только для
примера, runtime-файлы в пакете фиктивны. Digest не доказывает происхождение
или безопасность образа. Порт проверяется только на допустимый диапазон, а не
резервируется; убедитесь, что он свободен, непосредственно перед запуском.

2 ноября 2026 аналогичный подписанный план был подготовлен через API и вручную
запущен официальным Compose v2.39.4 на отдельном rootless Podman 4.3.1: три
сервиса работали, локальный `/health` отвечал, SQLite и heartbeat обоих worker
на общем томе были доступны. Сервисы, сеть и том эксперимента удалены. Запуск
выполнялся напрямую через Compose, а не операцией управления API; Podman не
заменяет Docker Engine, и проверка обновления, отката и Windows остаётся впереди.

В API 1.43 тестовый пакет использует идентичность `homensai-test-demo` и путь
`/health`, совпадающие с ответом сервера. После подтверждённого запуска можно
вызвать `check-signed-compose-health` с параметрами проверки образов, ключом
запуска `action_id` и `health_timeout_seconds`. В отдельном опыте API получил
ожидаемый ответ работающего контейнера; после остановки та же проверка была
отклонена и не запустила контейнер повторно. Это не подтверждает принадлежность
HTTP-ответа конкретному процессу или здоровье всех компонентов.

`installer_client.py` — пример подключения отдельного продукта к локальному
JSON/CLI API. Нужен доверенный Python 3.14 с доступным `shared.api` в текущем
каталоге или установленном окружении; сам установщик этот пример не поставляет.
Если продукт работает из другого каталога, параметр `api_root` задаёт абсолютный
путь к доверенному каталогу установщика, содержащему `shared`; дочерний процесс
запускается именно в нём. Это не проверка подлинности каталога или Python — их
происхождение, права и целостность должен обеспечить интегратор. Без `api_root`
сохраняется прежнее поведение и используется текущий каталог процесса.

```python
from examples.demo_product.installer_client import InstallerClient

client = InstallerClient(api_root='/absolute/path/to/trusted/installer')
info = client.capabilities()
result = client.call('validate', {'manifest': manifest}, min_minor=0, language='en')
# После того как доверенный адаптер запустил продукт и получил его порт:
health = client.call('check-local-health', {
    'port': port, 'product_id': 'homensai-test-demo', 'version': '1',
    'path': '/health', 'timeout_seconds': 3,
}, min_minor=12, language='en')
# Только предварительный порядок фаз, без проверки готовности и без запуска:
update_plan = client.call('plan-update', {
    'manifest': manifest, 'install_root': '/absolute/install/path',
    'release': '2', 'modes': ['autonomous'],
    'migration_ids': ['schema-2'], 'guard_effects': True,
}, min_minor=25, language='en')
```

Перед вызовом клиент сверяет major/minor API, доступную операцию и язык; при
ошибке выдаёт `InstallerClientError` с машиночитаемым `code`. Транспорт — JSON
через stdin/stdout, без shell и передачи произвольных переменных окружения.
При таймауте действие могло выполниться: клиент не делает автоматических
повторов и не создаёт ключ идемпотентности. Вызывающий код должен сохранить
ключ и исходный запрос, узнать состояние операции и решить, можно ли повторить.
Ответ ограничен 1 МиБ во время чтения, stderr отбрасывается. При превышении
лимита или таймауте клиент пытается остановить процесс и на POSIX его группу;
на Windows проверяется только непосредственный процесс. Доверенная программа
и окружение запуска по-прежнему обязательны; это не песочница или готовый SDK.
Никакой реальный продукт этим примером автоматически не изменяется.

Сценарий `test_independent_product_client_recovers_from_lost_prepare_response`
использует настоящий процесс CLI и подписанный вымышленный пакет с `main.py` и
`release.json`: ответ об успешной подготовке намеренно теряется, после чего
клиент читает состояние и повторяет исходный запрос с тем же ключом. Проверяется
целостность подготовленного выпуска и отказ при его подмене. Тест сам запускает
миграцию и дочерние web/worker-процессы из подготовленного выпуска; ответ web
проверяется через API на loopback, состояние worker — по heartbeat. Пакет в
тесте содержит фиктивные runtime-файлы, окружение и службы не устанавливаются.
Тестовая подпись не заменяет производственное управление ключами и не
подтверждает готовность установщика.
