# Ошибки, локализация и локальная диагностика

Реализация находится в `homensai_install/errors.py`, `diagnostics.py`,
`i18n.py`, `catalog/errors.v1.json` и `locales/{ru,en,de}.json`.
Автор проекта — Serhii Khomenko / HomenS.AI.

## Область ответственности

`DiagnosticStore` — локальная история и статистическая проекция событий.
Она не является авторитетным recovery journal и не определяет, можно ли
движку выполнить опасный переход. Движок обязан отдельно сохранять своё
обязательное состояние. Отказ этого обязательного журнала блокирует
изменения; отказ необязательной диагностики даёт явный ограниченный режим.

Модуль не делает сетевых запросов, не отправляет отчёты разработчику, не
исполняет инструкции из каталога ошибок и не устанавливает ПО. Рекомендация
`retry` означает доступный для оценки вариант, а не разрешение автоматически
повторить миграцию, запустить shell или повысить права.

## ErrorCatalog и error envelope

```python
from homensai_install.errors import ErrorCatalog, InstallerError, error_envelope

catalog = ErrorCatalog()
article = catalog.describe("PORT_IN_USE", locale="ru")
matches = catalog.search("порт", locale="ru", limit=20)

error = error_envelope(
    "PORT_IN_USE", phase="start", component_id="web",
    cause_status="confirmed",
    evidence=[{"check": "port_bind", "ok": False}],
)
```

Встроенный каталог версии `1.0.0` содержит 43 стабильных кодов на русском,
английском и немецком. Каждая статья содержит название, объяснение,
возможные причины, проверки, безопасные шаги исправления, влияние на
операцию, severity, retryable и рекомендованные идентификаторы действий.

Поиск учитывает слова и их начала; точный код и название получают приоритет.
Например, `port` не совпадает с частью слова `unsupported`.

`describe` неизвестного корректного кода сохраняет исходный код, возвращает
`known_code=false` и безопасную статью `UNKNOWN_ERROR`. Причина не выдумывается.
`cause_status` принимает `confirmed`, `suspected`, `unknown`. Для `confirmed`
обязателен непустой список структурированных результатов проверок. Их
достоверность должен обеспечивать вызывающий код; наличие JSON само по себе
не доказывает правильность диагноза.

`InstallerError(code, **context).to_dict(locale="ru")` создаёт тот же envelope.
Повторное преобразование сохраняет `error_id`. Произвольный текст исключения
не копируется в пользовательское сообщение: он может содержать пароль или
полный пользовательский путь. Технические факты передаются явно в `details`.
Связь вторичной ошибки отката с первичной задаётся через `parent_error_id`.
Внешний код возврата хранится отдельно как `external_exit_code`.

`ErrorCatalog(catalog_data=...)` принимает уже проверенные вызывающим кодом
данные. Обновляющий механизм должен проверить подпись, версию и происхождение
до передачи. Сам класс не загружает каталог и не доверяет ключам из его тела.
Встроенные JSON-файлы должны входить в inventory подписанной поставки.

## Локализация

```python
from homensai_install.i18n import translate, normalize_locale, validate_translations

translate("statistics.operations", locale="de", count=3)
normalize_locale("ru-RU")   # ru
validate_translations()
```

Поддерживаются `ru`, `en`, `de`; отсутствие выбора даёт русский язык,
неизвестный язык — английский. Все три каталога имеют одинаковые устойчивые
ключи и placeholders. Разрешены только простые именованные подстановки:
доступ к атрибутам, индексация и выражения в шаблоне запрещены.
Результат является обычным текстом; HTML-оболочка должна использовать
экранирование или `textContent`. Отсутствующий безопасный ключ возвращается
как ключ. Собственные GUI-строки можно держать отдельно без изменения
бизнес-данных и кодов ошибок.

## DiagnosticStore

```python
from homensai_install.diagnostics import DiagnosticStore

store = DiagnosticStore("/private/state/diagnostics.sqlite")
operation_id = store.start_operation(
    "install", operation_id="operation-123", product_id="reference",
    product_version="1.0.0", target="linux-native",
)
attempt_id = store.start_attempt(operation_id, attempt_id="attempt-1")
store.record_event(operation_id, {
    "event_id": "event-1", "sequence": 1, "type": "phase.completed",
    "phase": "verify", "duration_ms": 30,
})
store.record_error(operation_id, error, attempt_id=attempt_id)
store.finish_attempt(attempt_id, "SUCCEEDED", duration_ms=35)
store.finish_operation(operation_id, "SUCCEEDED", duration_ms=35)
history = store.get(operation_id)
stats = store.query_statistics(product_id="reference")
```

SQLite хранит `operations`, `attempts`, `events`, `errors`, квитанции
идемпотентного импорта и ограниченные служебные счётчики.
`schema_version=1` и `application_id` позволяют обнаружить чужую или более
новую БД. Чужая, повреждённая и более новая БД не удаляются и не заменяются.
Новая БД создаётся с приватными правами файловой системы. Полноценную NTFS ACL
для выбранного user/service профиля задаёт платформенная часть установщика.

Методы `start_operation` и `start_attempt` возвращают стабильные идентификаторы.
Методы записи/завершения возвращают `stored=sqlite|fallback|unavailable`.
`last_warning` и `diagnostic_state` показывают ограничения. Повторный event_id
не добавляет событие второй раз. Если event_id отсутствует, но имеется sequence,
ID детерминированно выводится из operation_id + sequence. Использование одного
ID для разных операций или разных ID для одной sequence отклоняется.

События принимаются по ограниченному списку полей. Полный stdout, stderr,
environment и произвольный вывод стороннего installer сохранять через этот
API нельзя. Данные операций/ошибок предварительно должны быть отобраны
вызывающим кодом как разрешённые технические факты.

## Аварийный журнал и продолжение

При недоступности SQLite запись поступает в соседний `*.fallback.ndjson`.
Можно явно указать отдельный `fallback_path`. По умолчанию максимум файла —
1 MiB, максимум отдельной записи — 64 KiB. Пределы проверяются до записи.
Обновление файла защищено отдельной кратковременной межпроцессной блокировкой;
запись использует flush/fsync и замену временного файла.

При переполнении сохраняется ограниченный хвост и явная запись о количестве
отброшенных диагностических записей. История/статистика после потери не
объявляются полными. Это допустимо для диагностической проекции, но было бы
недопустимо для обязательного recovery journal.

Если оба хранилища недоступны, возвращается `stored=unavailable`, увеличивается
счётчик несохранённых записей, исключается рекурсивное логирование ошибки
логгера. Такой счётчик в памяти не переживает аварийное завершение процесса,
если ни один носитель вообще не позволил сохранить запись.

`import_fallback()` применяет record и его квитанцию в одной SQLite-транзакции.
Сбой после commit до очистки файла допускает безопасный повтор. Записи
предыдущей аварийной очереди импортируются до новых переходов состояния.
Повреждённые строки сохраняются как непринятые, их наличие видно в результате.
Самопроизвольного удаления повреждённой БД или сброса продуктовых данных нет.

## Статистика

`query_statistics(product_id=None, target=None, since=None, until=None,
product_version=None, action=None, status=None)` использует согласованный
снимок SQLite. Временные фильтры — ISO 8601 с часовым поясом, выборка операций
определяется временем их начала. В ответе возвращаются сами фильтры.

Основные показатели:

- уникальные операции отдельно от попыток;
- статусы и виды действий, retries по execution attempts;
- ошибки по коду, этапу и компоненту, число затронутых операций;
- загрузки по явным `download.bytes` с `bytes_delta`, повторения
  `download.retry`, попадания `download.cache_hit`;
- измеренные длительности операций и событий `phase.completed`;
- число потерянных/удалённых по retention записей и признак полноты.

`SUCCEEDED` и `SUCCESS` означают успех. `FAILED_ROLLED_BACK` остаётся
неуспешным обновлением. CANCELED и CANCELLED считаются одной категорией отмены. Ожидание пользователя, перезагрузка и
незавершённость не превращаются в успешные установки.

Каждая доля имеет числитель и знаменатель. `success_rate_all_operations`
использует все отобранные операции. `success_rate_technical_outcomes`
учитывает только успешные и неуспешные технические исходы, исключая отмены,
ожидание и незавершённость. Пустой знаменатель даёт `ratio=null`.

Активная длительность операции передаётся контроллером, который знает
периоды ожидания. При её отсутствии остаётся `null`: время выключенного ПК
и ожидания не вычисляется как активная работа по разнице UTC timestamps.
Длительность локальной попытки может измеряться монотонным таймером процесса;
после нового запуска без исходного таймера она также остаётся неизвестной.

`prune(older_than_days=90, max_events=...)` удаляет только диагностические
данные завершённых операций. Активные операции сохраняются. После удаления
история прямо отмечает ограниченность покрытия. Это локальная статистика
конкретного хранилища, а не статистика всех клиентов.

## Приватность и экспорт

`redact(value, known_secrets=...)` выполняет дополнительную очистку:
секретные имена полей, Bearer/Basic, известные секреты, credentials и
чувствительные query-параметры URL, email и домашние пользовательские пути.
Ограничиваются длины и вложенность. Это защита в глубину, а не обещание
распознать любые персональные сведения в произвольном тексте.

Поэтому `export_preview()` применяет ещё более узкий allowlist: исключает
произвольные metadata, error details/evidence values, stdout/stderr,
environment, документы и содержимое продуктовой БД. Объяснение ошибки
восстанавливается из доверенного локального каталога. Preview показывает
состав и SHA-256 содержимого отчёта.

```python
preview = store.export_preview(operation_id)
# UI показывает preview пользователю и получает явное решение.
saved = store.export(
    "/private/support-report.json", operation_id=operation_id,
    confirmed=True, expected_digest=preview["sha256"],
)
```

Без `confirmed=True` экспорт отклоняется. Если после просмотра изменился
состав, `expected_digest` даёт PLAN_STALE. Существующий файл не перезаписывается.
Метод сохраняет локальный JSON; отправки на сервер или GitHub нет.

## Проверенные границы

Проверки `tests/test_i18n.py` и `tests/test_diagnostics.py` используют только
синтетические данные и временные каталоги. Проверяются перевод и поиск,
неизвестная/связанная ошибка, знаменатели, дедуп, повреждённая/чужая БД,
ограниченный fallback, конкурентные писатели, повтор импорта после commit,
отказ обоих хранилищ, очистка экспорта, stale preview и retention.

Это проверки Python-исходников на Linux. Они не являются испытанием Windows
NTFS ACL, установленного Setup, GUI или Docker. Для этих targets нужны отдельные
installed receipts с точными artifact hashes и реальными средами.
