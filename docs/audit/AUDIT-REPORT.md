### A-08 — Stat-кэши ошибочно подтверждают изменённые байты

- **Сценарий сбоя:** обычный файл заранее отображён writable `mmap`, страница уже стала dirty; файл успешно проверен и попал в кэш; та же отображённая страница меняется без изменения используемых stat-полей → повторная проверка возвращает старый успех → API может сообщить соответствие подписи/инвентарю для уже отличающихся байтов. - **Статус:** подтверждено настоящей Ed25519-подписью: изменённый ZIP принимается повторным `verify_signed_package`, а после очистки кэша отвергается. - **Граница вывода:** это доказательство ложного результата проверки, а не демонстрация запуска подменённого кода или нарушения изоляции между пользователями. Воспроизведение требует права изменять файл/сохранённое отображение. Приватный snapshot в `package_prepare` дополнительно проверяется; его обход здесь не установлен. Остановка писателей остаётся обязательной для согласованного архива. Комментарий `archive.py:44` упоминает mmap, но двухсекундный порог не решает показанный случай.
- **Предлагаемое исправление:** использовать кэш лишь для принадлежащих проверяющему неизменяемых snapshot либо вновь читать байты на границе подтверждения целостности. Возраст stat нельзя считать доказательством отсутствия сохранённого writable mapping.

- **Предлагаемое исправление:** ограничить чтение до выбранного максимума плюс один байт, отвергать специальные файлы без блокирующего открытия и возвращать безопасный `ManifestError`. Согласовать предел с другими входами манифеста.

### A-10 — Операционные ошибки новых API-команд классифицируются как ошибки контракта

- **Серьёзность:** низко.
- **Категория:** API/CLI-контракт, совместимость автоматизации.
- **Файл:строка:** `shared/api.py:1246`; обещание — `docs/API-DESIGN.md:465`.
- **Суть:** список операционных кодов в `main()` не включает новые `docker_*_failed`, `fresh_controller_failed`, `update_*_failed`, `uninstall_failed`.
- **Сценарий сбоя:** корректный запрос `check-docker-engine` указывает отсутствующий executable → API возвращает операционную ошибку `docker_preflight_failed`, но процесс завершается с 2 → вызывающая автоматизация может принять сбой среды за ошибку контракта/совместимости вместо документированного операционного кода 1. JSON-код ошибки при этом остаётся содержательным.
- **Статус:** подтверждено запуском настоящего `python -m shared.api`: `ok: false`, `error.code: docker_preflight_failed`, exit 2. Скрипт `api-manifest-repro.py`, независимый лог `api-independent.log`.
- **Предлагаемое исправление:** классифицировать ошибки централизованно и получать exit-код из той же классификации. Проверять каждый публичный код ошибки параметризованным тестом CLI.

## Что не удалось проверить и почему

- Полный pytest-прогон на несколько тысяч тестов не запускался: использовались точечные выборки по проверяемым областям. Успех прежнего полного прогона в WORK-PLAN не принимался за результат этого аудита.
- Настоящие Windows SCM/WinSW, ACL ProgramData, reparse points/junctions и длинные пути на NTFS не проверялись: текущий исполнитель — Linux, Windows-ВМ не запускалась. Для находок Windows известны точные границы подмены системных операций.
- Долгие Podman/systemd и Windows kit E2E, физическое выключение питания и реальные прерывания SIGKILL в полном жизненном цикле не выполнялись. Для выявленных окон применены воспроизводимые инъекции сбоев в точных точках; power-loss durability ФС этим не доказывается.
- Настоящий Docker daemon, контейнеры под нагрузкой и восстановление их данных не запускались. Проверка настоящим Compose ограничена offline-разбором конфигурации.
- Ротация ключей проверена по локальному исполнению существующих тестов/коду, но внешняя инфраструктура распространения/отзыва ключей, подлинность upstream и актуальные базы уязвимостей не аудировались. Сеть для этого не использовалась; отсутствие вредоносного кода/уязвимых зависимостей не утверждается.
- Реальная интеграция Rent и данные пользователя не запускались и не изменялись. Правильность конкретных продуктовых миграций, stopping всех внешних писателей и восстановление на другой физической системе требуют отдельных продуктовых проверок.

## Какие тесты стоит добавить

1. Windows update с неизменным общим inventory компонентов, но изменённым составом выбранного режима: отказ до эффектов и независимая проверка остановки всех прежних писателей перед любым архивом/миграцией.
2. Два разных product/component с одинаковой прежней конкатенацией и существующая чужая SCM-служба с правильным ID: install/start/stop/uninstall должны отказать без её изменения.
3. Полный kit install и консолидация с прерыванием на каждой файловой записи runtime/units и между записью результата порта и checkpoint контроллера; повтор должен завершать или предлагать реализованный безопасный путь восстановления.
4. Установка без `--root` в чистом HOME, где отсутствует `.local/share/homensai`; существующий E2E с заранее созданным родителем этого не заменяет.
5. Сбои ENOSPC/replace/kill при публикации сохранённого установщика до и после переноса `.installer.old`, включая возобновление тем же install/update на Linux и Windows.
6. Матрица wheel-тегов: отрицательные `cp313-none-any`, `cp313-none-win_amd64`, будущие cp-теги и несовместимые ABI; положительные `cp313-abi3-*`, `cp314-cp314-*`, `py3-none-any`.
7. Повторная проверка подписанного пакета и подготовленного выпуска после изменения через сохранённый `MAP_SHARED`, в том числе после двухсекундного settling; результат сравнивать со свежим SHA-256 реальных байтов.
8. Непустые Windows hooks: предварительный отказ в build/install/update до регистрации служб и миграций; тест обязан проверять использование реальной ветки установщика, а не только отказ отдельного `WindowsEffects`.
9. Манифест сверх лимита, FIFO и спецфайл: ограниченный по времени/памяти безопасный отказ без необработанного исключения.
10. Все публичные API-коды ошибок: соответствие коду завершения CLI, JSON-схеме и контракту. Сохранять реальные нижние порты в crash-тестах контроллера: нынешние тесты с полностью подменённым `api.handle` подтверждают порядок повторов, но не способность настоящего порта завершить `pending`.
