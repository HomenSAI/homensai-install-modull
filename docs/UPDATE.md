# Тексты служб и транзакция обновления — шаг 4

© 2026 Serhii Khomenko · HomenS.AI

`shared/services.py` и `shared/update_plan.py` используют только stdlib.
Это библиотечный механизм с внедряемыми портами и текстовые генераторы,
а не готовый установщик. Вызовов subprocess, sc/systemctl, сети, установки
служб, удаления старых выпусков или runtime в этих модулях нет.

## Службы

`component_order(manifest, modes)` требует явно выбранные режимы, проверяет
mutual_exclusion и возвращает топологический порядок `after`. Обратный порядок
используется для остановки. Несовместимые режимы одновременно не генерируются.

```python
from shared.services import render_services

# Только публичный манифест v2; install_root относится к целевой ОС.
units = render_services(manifest, platform="linux", modes=("autonomous",),
                        install_root="/opt/example")
# Получен dict filename -> text. Файлы и службы не создаются.
```

Для Windows манифест v2 может дополнительно содержать:

```json
"winsw": {"version": "2.12.0", "sha256": "<64 строчные hex-цифры проверенного x64 артефакта>"}
```

Поле необязательно для прежних v2 и Linux. Для Windows оно обязательно:
`render_services(..., platform="windows", install_root="C:\\Example",
winsw_payload=artifact_bytes)` сначала вызывает чистую
`verify_winsw(payload: bytes, sha256: str) -> bool`. Несовпадение, отсутствие
pin/байтов или неподдерживаемая версия запрещают выдачу XML. Нет скачивания,
чтения бинарника с диска или исполнения. Реального digest WinSW в репозитории
нет: его должен предоставить владелец проверенного x64 артефакта. Проверка
SHA-256 не определяет архитектуру/происхождение произвольного бинарника.
В v1 поле `winsw` запрещено; неизвестные поля секции также запрещены.

XML формируется ElementTree; argv кодируется по правилам Windows CRT,
зависимости — через `depend`, автозапуск — Automatic/delayedAutoStart.
В WinSW запрещены `%` в cmd/рабочем каталоге: это синтаксис подстановки wrapper,
а не безопасный literal. Недопустимые для XML Unicode-символы отвергаются.
systemd получает `After`/`Requires`, кавычки, экранирование backslash/quotes,
`%%` для specifiers и `$$` для argv environment expansion. Shell не используется.
Префиксы executable systemd и относительный executable с `/` отвергаются.
Рабочий каталог абсолютный, относительный app привязывается к install_root.

Restart delay/max/window переводятся в WinSW onfailure (max-1 restart,
затем none) и resetfailure; в systemd — RestartSec, StartLimitBurst,
StartLimitIntervalSec. Это штатные механизмы ОС: SCM сбрасывает счётчик после
интервала без отказов, systemd считает запуски, включая ручные. Они не заменяют
точный скользящий счётчик падений, heartbeat-надзор и часовой лимит уведомлений
Rent; такого надзора/сигнализации в шаге 4 нет.

В текстах присутствуют фиксированные публичные HOMENSAI_WEB_HOST=127.0.0.1
и HOMENSAI_WEB_PORT из манифеста; другой web.host отвергается валидатором.
Продукт обязан соблюдать эти настройки: генератор не анализирует поведение
произвольной программы и не доказывает фактический bind сокета.
Только имена secrets с контекстом service попадают в PassEnvironment (Linux)
или ссылки `%NAME%` (WinSW). Окружение процесса и файлы секретов не читаются,
значения не принимаются API. Значения должен безопасно предоставить адаптер
управляющей службе; admin-only дескрипторы в тексты не попадают. Строки cmd,
пути и идентификаторы должны быть публичными: распознавание произвольного
секрета в разрешённой строке невозможно. ACL, Credential Manager, DPAPI,
служебная учётная запись и доставка окружения не реализованы.

## Обновление и откат

```python
from shared.update_plan import UpdatePlan

plan = UpdatePlan(manifest, installation_root, ports, release="app-2.0",
                  modes=("autonomous",), migration_ids=("schema-1", "schema-2"))
result = plan.run()  # updated либо rolled_back; временная ошибка отката -> UpdateError
```

`installation_root` — абсолютный Path текущей ОС. Проверка DataHome шага 3
запрещает пересечения постоянных корней с app/releases, ссылки и reparse points.
Пути управления находятся в `paths.services`: manifest.update.state_file
(в примере `update.json`), manifest.update.pointer_file (active.json) и
`operation.lock`. Пересечение этих трёх путей запрещено. Указатель читает/пишет
порт: сам механизм не редактирует продуктовый active.json.

Последовательность:

1. stop всех писателей в обратном порядке after;
2. archive — полный проверенный зашифрованный снимок через backup-порт;
3. stage — подготовить и проверить полный неизменяемый выпуск;
4. для каждого migration_id: отдельный backup, затем migrate;
5. switch — атомарно переключить указатель;
6. pre_start и start в порядке after;
7. health — loopback URL и health_checks в пределах общего health_wait;
8. post_update.

В защищённом подписанном Linux-порту перед публикацией нового выпуска исходный
архив повторно проверяется вместе с привязанной отметкой, паролем и перечнем
корней. Он также проверяется перед переключением указателя и запуском нового
выпуска; перед каждой миграцией отдельно проверяется и соответствующая ей
копия. При неподтверждённом архиве действие не начинается, а состояние
остаётся неопределённым для отдельной проверки. Эта мера не является изоляцией
от другого процесса с теми же правами и не заменяет проверки на других
платформах; восстановление и остановка не блокируются новой проверкой запуска.

По умолчанию migration_ids содержит один элемент `manifest`: один вызов
manifest.migrations.cmd. Адаптер задаёт полный неизменяемый порядок отдельных
миграций и их соответствие этой команде. Нельзя прятать несколько миграций
за одним вызовом без собственной копии перед каждой. Пустой tuple означает
явное отсутствие миграций. Исключение new_db_no_backup здесь не используется:
копия выполняется даже для новой БД.

При обычном исключении шага записываются направление rollback и имя ошибочной
фазы, затем выполняются rollback_stop → **before_rollback** → restore исходного
archive → pointer_back → pre_start/start → health. Дополнительный stop нужен
и после частичного start/неуспешного health. Before-rollback — отдельный ключ
копии текущих данных; архив начала обновления или копия перед миграцией его
не заменяют. Ошибка этой копии оставляет фазу незавершённой: restore, pointer_back
и запуск не вызываются. Когда ошибка случилась до подтверждённого archive,
миграции ещё не начинались: отдельная before-rollback всё равно обязательна,
а restore пропускается, поскольку подтверждённого исходного архива нет.
Ошибка любого шага отката даёт обобщённый UpdateError; следующий run повторяет
этот шаг. Успешный откат возвращает outcome=rolled_back, а не успех обновления.

## Порты и восстановление после аварии

`shared.update_assembly.assemble_prepared_linux_update` связывает подготовку
с защищённым `UpdatePlan`, файловыми портами, проверкой подписанных старого и
нового выпусков, группой user-systemd, портом миграции и локальной проверкой
готовности. Функция принимает параметры `prepare_signed_linux_update` и
дополнительно `group`, `password_provider`, `interpreter`,
`interpreter_sha256`, `timeout`; возвращает объект плана. Сборка может создать
подготовленный payload и отметку, но не вызывает `plan.run()`, не запускает и
не останавливает процессы, не делает архив и не меняет указатель выпуска.

Это программный интерфейс для доверенного интегратора, не готовая команда
обновления. Он не проверяет доверие к группе и ключам, пригодность runtime,
доступность служб и отсутствие сторонних писателей. Аргументы и ссылки на
объекты должны оставаться доверенными и неизменными в течение операции.
Поддерживаются только манифесты без `pre_start`, `health_checks` и
`post_update` hooks. Для повторной сборки начатой транзакции передаётся
`reopen=True` с теми же пакетами, ключами, путями и идентификатором подготовки.
Проверяются checkpoint, обе подписи, старый выпуск, подготовленный payload,
новый выпуск (если уже опубликован) и отметка подготовки. Указатель может
ссылаться на старый или новый выпуск. Результат — объект плана, а не запуск;
он не доказывает, что неопределённый эффект завершился или что службы безопасны.
После отдельной проверки оператором вызов `plan.run(resume_indeterminate=True)`
может продолжить план, но порты по-прежнему отклоняют неподтверждённые pending.
Для сверки именно остановленных служб допускается `reconcile_stop_key` текущего
checkpoint: порт проверяет состояние без повторной команды stop. Это не
разрешение неопределённых миграций, запусков или архивов. Непосредственный
вызов `plan.run()` выполняет реальные эффекты и требует соблюдения остальных
условий из этого документа.

`shared.update_prepare.prepare_signed_linux_update` подготавливает новый
подписанный payload для Linux x86-64 до запуска плана. Требуются старый и новый
пакеты, их подписи и независимо доверенные открытые ключи, идентификаторы
продукта/версий, режимы, миграции, существующий отдельный рабочий каталог с
владельцем текущего пользователя и правами 0700, а также 32-символьный ключ
операции. Старый пакет сверяется с текущим подготовленным выпуском и указателем;
оба манифеста проверяются на совместимость и поддержку текущей среды.
Родительские каталоги рабочего каталога также должны быть защищены вызывающей
стороной. Под общей блокировкой lifecycle и `operation.lock` новый пакет
извлекается в `work_dir/payload-<ключ>`, проверяется и получает устойчивую
отметку `prepare-<ключ>.json`. Повтор точно того же завершённого запроса заново
проверяет состав, не перезаписывая файлы. При `pending`, изменённом запросе или
каталоге без отметки автоматический повтор запрещён; частичные файлы сохраняются
для разбора. Внешние процессы, не соблюдающие блокировки, не изолированы.

Результат содержит `payload_name`, `plan_sha256`, количество файлов и
`update_started: false`, `runtime_verified: false`, `services_verified: false`.
Эта операция не проверяет доступность зависимостей runtime, происхождение и
полномочия ключа, все процессы-писатели, состояние служб и безопасность кода;
она не запускает установку, миграции или обновление. Следующему контроллеру
нужно заново проверить актуальность условий и использовать подготовленный
каталог вместе с проверенным составом подписанного пакета. Полный публичный
контроллер обновления пока не реализован. Локальный API 1.29 предоставляет
`prepare-signed-linux-update` с тем же ограниченным результатом.

`UpdatePorts` — Protocol. Он передаёт публичные команды/hooks и устойчивые ключи
`<transaction UUID>/<phase>`; содержимое БД/секреты/тексты ошибок в state не
передаются. Каждый успешный возврат подтверждает **проверенный, durable** результат.
Backup-порт обязан сохранить отдельную зашифрованную копию под своим ключом,
stage — проверить полноту, SHA-256 и offline runtime, stop — остановить всех
писателей, health — проверять HTTP 200 без proxy/redirect и hooks до дедлайна.
Restore обязан сохранять актуальные update.json/operation.lock и не восстанавливать
их историческую версию поверх управляющего процесса. Pointer-порт отвечает за
атомарность и durability active.json. Портам известны публичный манифест и
конкретная установка; stage/backup получают идентификаторы, а не secret payload.

`LocalUpdateHealthPort` предоставляет ограниченный health-порт для активного
`UpdatePlan` с `guard_effects=True` и пустым списком health hooks. Он проверяет
JSON-контракт продукта на loopback, при прямом обновлении ожидает новый выпуск,
при откате — прежний. Указатель и checkpoint сверяются до и после запроса;
при их изменении результат остаётся неопределённым. Ответ не подтверждает
принадлежность сокета процессу или здоровье всех компонентов. Порт опрашивает
до истечения `health_wait`; таймаут сетевого чтения не является жёсткой общей
границей времени при медленном ответе. Подключение порта само по себе не
создаёт законченный контроллер обновления и не исполняет health hooks.

`LinuxSignedUpdateEffects` связывает уже настроенные `SystemdLifecyclePort`,
`SignedMigrationPort` и `LocalUpdateHealthPort` одного плана и одной установки.
Он отклоняет произвольные post-update hooks и подтверждает пустой шаг только
в активном checkpoint. Создание связки не проверяет, что выбранные службы
охватывают всех писателей, что их unit-файлы указывают на правильный выпуск,
или что runtime и издатель заслуживают доверия. Вызывающая сторона обязана
обеспечить эти условия и защищённые каталоги; это ещё не публичный контроллер.
Переносимый рецепт user-systemd v1 раскрывает `@release` в конкретный каталог
старой версии. Простое переключение `active.json` не меняет такой unit: после
запуска он продолжил бы использовать старый путь. Сборщик нового плана теперь
распознаёт такие точно совпадающие units из подписанного рецепта и отказывает
до подготовки payload. Возобновление прямого направления также отклоняется;
сборка плана в направлении отката остаётся доступной для восстановления.
Другие варианты unit-файлов эта проверка не подтверждает; переносимой интеграции
fresh → update с переключением служебных команд пока нет. Тест обновления с
systemd использует отдельный синтетический launcher, читающий указатель.

`shared/portable_launcher.py` — экспериментальная самостоятельная основа для
такого launcher на Linux. Она читает `{"release":"..."}`, проверяет формат
указателя и пути, подставляет целые аргументы `@app`, `@data`, `@runtime` и
`@release`, затем запускает выбранный исполняемый файл через `execv` без shell.
Загрузчик и его аргументы должны находиться в доверенном стабильном месте;
его нужно запускать доверенным Python. Исполняемый файл должен быть внутри
runtime или выбранного выпуска. Есть проверки повторных ключей, ссылок,
разрешений, выхода из каталога и изменения указателя при чтении. Аргументы
видны в списке процессов и не предназначены для передачи секретов.

Эта основа пока не устанавливается и не подключена к публикации units или
API. Она не проверяет подпись, хэши, достоверность активного выпуска или
runtime и не изолирует процессы с теми же правами. Запускать её в реальной
установке до реализации и проверки полного доверенного пути нельзя. Тесты
проверяют процессы и переключение 1 → 2 → 1 на синтетических данных; реальная
интеграция с установкой, обновлением, аварией и откатом ещё не подтверждена.

Экспериментальная чистая функция `render_pointer_user_services_v2` формирует
units с запуском `runtime/bin/python -I -B` и стабильного файла
`runtime/lib/homensai/portable_launcher.py`; текущая версия в них не зашита.
На одноразовом user-systemd в контейнере одна тестовая служба действительно
запустила версии 1 → 2 → 1 при изменении указателя. Это проверка генератора и
launcher, а не транзакции обновления: публикация и доверенная доставка самого
launcher, проверка его хэша, API и сценарии аварии ещё не интегрированы.
При прямом подключении этой связки файловый порт перед подготовкой и после неё,
а также до и после переключения и запуска нового выпуска сверяет состав и
хэши дерева с пакетом, проверенным по переданному доверенному ключу, продукту,
версии, манифесту и целевой среде. Эта проверка выполняется и при пустом
списке миграций. Если используется обёртка над связкой, она обязана передавать
все методы, в том числе `guarded_stage_release`, `guarded_switch_pointer` и
`guarded_restore`; обычный файловый порт сам подпись не проверяет.
Связке нужен отдельный `PreviousSignedRelease`: путь к прежнему пакету, его
подпись и независимо доверенный открытый ключ. Перед остановкой и до и после
восстановления данных, переключения назад и запуска старой версии проверяются
подпись, версия из checkpoint, продукт, среда и точный состав старого каталога.
Манифесты могут отличаться названием продукта, командами миграций, декларацией
поддерживаемых целей и составом закреплённых lock-файлов/wheels. При этом оба
выпуска должны поддерживать текущую цель, а версия Python, offline-политика,
пути, службы, режимы, параметры здоровья и остальные поля должны совпадать.
Проверка подписанных pin-файлов не подтверждает, что зависимости установлены в
runtime или что старый и новый выпуск с ним работают; это отдельная задача.
Другие переходы между манифестами пока отклоняются. При отсутствии подтверждения
остановка прямого обновления или соответствующий шаг отката не выполняется;
если проверка не прошла после действия, результат остаётся неопределённым.
Доверие к ключу, подлинность процесса
службы, runtime и безопасность подписанного кода проверкой не устанавливаются;
каталоги должны быть защищены от параллельной подмены.
При подключении связки к `FilesystemPorts` каждый архив и копия перед миграцией
или откатом дополнительно требуют отметку соответствующей остановки и проверяют
состояние выбранных units до и после создания снимка. Перед записью сохраняется
отметка `pending`; после прерывания или неуспешной повторной проверки такой
снимок автоматически не используется. Для продолжения нужен отдельный разбор;
автоматического восстановления этой отметки пока нет. Проверка двух состояний
не исключает кратковременного запуска между ними и не охватывает других
писателей. Обычные `FilesystemPorts` без связки такую проверку не выполняют.
`LinuxSignedUpdateEffects` дополнительно удерживает общую блокировку управления
службами от входа в `UpdatePlan.run()` до завершения или ошибки всей операции;
она берётся перед `operation.lock`. Те же блокировки используются ограниченными
операциями fresh start/stop и циклами systemd, поэтому они не могут запускаться
параллельно с таким обновлением. Если блокировка занята или защищённый каталог
`.homensai-control` не подготовлен, обновление не начинается. Обёртка над
эффектами должна передавать `operation_guard`; обходящие этот протокол прямые
вызовы systemctl и посторонние процессы не блокируются. Блокировка не доказывает
остановку всех писателей и не является песочницей.
Для экспериментальной проверки systemd-сценариев предназначен одноразовый
rootless-контейнер: `python3 tests/run_isolated_systemd_test.py --run --update`.
Сценарий устанавливает тестовые зависимости по сети и не является приёмкой
готового инсталлятора или проверкой физической потери питания.
Для проверки именно `assemble_prepared_linux_update` предусмотрен сокращённый
запуск `python3 tests/run_isolated_systemd_test.py --run --assembled`: он
проверяет обновление, откат и повторную сборку после прерывания остановки
синтетического SQLite-продукта с временными
user-systemd службами и зашифрованными копиями. Тестовый мост делегирует
защищённым портам и внедряет ошибку проверки готовности для сценария отката;
он не подтверждает установку runtime, развёртывание units или безопасность
произвольных продуктовых процессов.

Между эффектом и checkpoint процесс может умереть. После перезапуска механизм
повторяет **тот же ключ**; порт обязан хранить результат и дедупликацию вне
памяти процесса, включая частично исполненную миграцию/restore. Терминальную
ошибку прямого шага тоже нужно воспроизводить по ключу, если направление
rollback ещё не записано. Ошибки шага rollback допускают retry после исправления.

Если результат эффекта неизвестен, порт должен явно выбросить
`EffectIndeterminate`. Тогда `run()` сохраняет в checkpoint признак
`indeterminate`, выбрасывает `UpdateIndeterminate` и не начинает откат.
Обычный повтор `run()` останавливается без вызова портов. Сообщение порта не
раскрывается. После проверки вызывающий явно передаёт
`run(resume_indeterminate=True)`, а порт обязан безопасно обработать тот же key:
одной записи checkpoint недостаточно для дедупликации внешней операции.
Если запись checkpoint не удалась или процесс погиб до неё, признак может не
сохраниться; устойчивость к такому сбою по-прежнему требует durable-порта.
Автоматическая классификация произвольных исключений не реализована: если
порт ошибочно выбросит обычное исключение, по-прежнему начнётся rollback.

Экспериментальный режим `UpdatePlan(..., guard_effects=True)` сохраняет признак
перед каждым вызовом порта и снимает его только в атомарном checkpoint
следующего шага. При прерывании обычный `run()` остановится до вызова портов;
после проверки требуется явный `resume_indeterminate=True`. Режим входит в
отпечаток плана, поэтому переключить его у незавершённой транзакции нельзя.
Возможна ложная остановка до начала эффекта: данные для решения должен дать
сам адаптер. Этот режим не доказывает состояние внешнего процесса и не делает
сам эффект идемпотентным; порт всё ещё обязан безопасно обработать тот же key.
Стандартное поведение остаётся совместимым с ранее созданными checkpoint.
CLI `update-plan-status --guard-effects` и локальный API 1.9
`update-plan-status` умеют читать состояние такого плана. Создание и
возобновление guarded-плана через CLI/API пока недоступны.
Одного in-memory флага для этого недостаточно. Exactly-once для произвольной
внешней команды без такого соглашения не гарантируется; готовых адаптеров нет.

State содержит только version, transaction, digest публичного плана,
old_release/release, direction, index следующего шага, failed_phase,
archive_ready и outcome. Идентификаторы ограничены безопасным форматом.
Команды, env, значения секретов, исключения портов и содержимое копий не
записываются. Неизвестные/повторяющиеся поля, неверные индексы, инварианты,
смена манифеста/режимов/списка миграций/целевого выпуска запрещают resume.
Это проверка целостности структуры, а не криптографическая защита от владельца,
способного подменить state. Публичные строки не должны содержать секреты.

Checkpoint пишется в уникальный соседний файл: flush/fsync → os.replace;
на POSIX дополнительно fsync родительского каталога. Windows fsync каталога
не выполняется: гарантия при потере питания зависит от ФС. При ошибке записи
checkpoint run прерывается без начала отката, сохраняя предыдущую полную
версию state для повтора того же ключа. После реального kill могут остаться
неподтверждённые `.update-*.tmp`; они не читаются как state.

`operation.lock` — advisory OS lock (msvcrt byte lock / POSIX flock), без PID
эвристик и удаления файла. Он освобождается при закрытии handle/смерти процесса;
постоянный файл устраняет гонку смены inode. Все процессы управления обязаны
использовать этот протокол. Поддержка сетевых ФС и злонамеренной смены путей
между stat/open не заявляется. Разные state-файлы одной установки используют
один lock. Механизм сохраняет финальный state; следующий выпуск требует явного
архивирования завершённого журнала вызывающей стороной под тем же lock.
Автоматической очистки старых releases, runtime, копий и журналов нет.

ZIP из шага 3 не зашифрован и восстанавливает только в пустой каталог;
его нельзя напрямую выдать за требуемый здесь backup/restore-порт живой БД.
Службы/миграции/шифрование/health не исполнялись, реальных адаптеров Rent и
JobPilot нет. Docker/native install/update/restore/rollback ещё не приняты.

## Проверки

Тесты используют pytest, tmp_path, вымышленные данные, текстовые проверки и
фейк с дисковым ledger. Проверяются обычные ошибки каждой прямой/обратной фазы,
симуляции crash через BaseException до/после эффекта и checkpoint, resume новым
экземпляром портов, обязательный before-rollback, атомарная замена, блокировка,
retention, режимы, pin/escaping и отсутствие синтетических секретов в выводе.
Дополнительно `tests/test_archive_crash_recovery.py` проверяет реальный SIGKILL
дочернего процесса после создания шифрованной копии и до записи её готовой
отметки. Следующий процесс подтверждает копию по заранее переданному хэшу и
завершает обновление вымышленного продукта. Службы и миграция в этом тесте —
фейки; выключение питания, реальный systemd и WinSW не проверяются. Отдельный
