# Удаление и переустановка Linux user-systemd

Модуль `shared/uninstall_linux.py` и операции API 1.67
`plan-portable-linux-uninstall` / `uninstall-portable-linux` удаляют установку,
созданную контроллером первой установки (`install-portable-linux`) с
подписанным рецептом `pointer-v2` или `portable-v1`. Windows и Docker этим
не охватываются.

## Что передаёт интегратор

- Подписанный пакет **первой установки** в этот корень, его конверт, доверенный
  открытый ключ, ID и версию. После pointer-обновлений units по-прежнему
  отрисованы из этого пакета; после переустановки — из пакета переустановки.
- `install_root`, `unit_dir` и `modes` — те же, что при установке.
- `operation_id` — 32 hex-символа; интегратор сохраняет его до завершения.
- `data_policy`: `keep` (по умолчанию в сценариях) или `purge`. Для `purge`
  обязателен `confirm_product_id`, равный ID продукта.

## Что проверяется до изменений

1. Подпись пакета, нативная цель Linux x86-64 и корень с правами 0700,
   принадлежащий текущему пользователю.
2. Журнал первой установки соответствует этому пакету — так подтверждается,
   что корень создан установщиком из этого выпуска.
3. Каждый существующий unit-файл побайтно совпадает с отрисованным из пакета.
   Изменённый, связанный жёсткой ссылкой или чужой файл блокирует удаление.
4. Нет незавершённого обновления (`update.json` с `running` или
   `indeterminate`) и не занята блокировка операций; после аварии чужой
   операции удаление не начинается.
5. Менеджер `systemctl --user` действительно читает `unit_dir`; у units нет
   drop-in файлов; загруженный unit указывает на ожидаемый файл.

`plan-portable-linux-uninstall` выполняет только пункты 1–3 и возвращает
список units, удаляемых и сохраняемых путей; systemctl не вызывается.

## Порядок удаления

1. Квитанция `.homensai-uninstall.json` (0600) со статусом `pending`,
   привязкой ко всем параметрам и активной версией из указателя.
2. Остановка units в обратном порядке зависимостей; `failed` сбрасывается
   через `reset-failed`; требуется подтверждённое `inactive`.
3. Удаление собственных unit-файлов, `daemon-reload`, проверка `not-found`.
4. Удаление `app`, `releases`, `runtime`, `services`, `.homensai-control`,
   журнала первой установки; при `purge` — также `data`, `backup`, `config`.
   Удаление не следует по символьным ссылкам.
5. Квитанция переводится в `done`.

После `keep` в корне остаются `.homensai-bootstrap.lock`, квитанция и
сохранённые каталоги; после `purge` — только блокировка и квитанция. Их
можно удалить вручную; модуль не удаляет файл блокировки, чтобы не создавать
гонку с другим процессом.

Повтор с тем же `operation_id` продолжает прерванное удаление; каждый шаг
идемпотентен. Другой `operation_id` при существующей квитанции даёт
`uninstall_conflict`. Повтор после `done` возвращает прежний результат без
вызовов systemctl.

## Переустановка на сохранённых данных

После удаления с `keep` тот же корень можно использовать для переустановки,
передав `reuse_preserved_data: true` в `install-portable-linux` (или
`prepare-native-release`). Условия:

- квитанция `done` с сохранёнными данными, тем же ID продукта и версией,
  которая была активна при удалении; другая версия отклоняется — переход на
  новую версию выполняется обновлением с миграциями;
- в корне нет ничего, кроме квитанции, блокировки и сохранённых каталогов;
- расположение `data`, `backup`, `config` в манифесте совпадает с квитанцией.

Сразу после записи журнала подготовки квитанция переносится в
`.homensai-control/previous-uninstall.json`; прерванная переустановка
продолжается тем же запросом. Флаг входит в привязку операции.

Переустановка не изменяет и не проверяет содержимое сохранённых данных и не
выполняет миграции. Перед удалением рекомендуется создать и проверить полный
зашифрованный архив (`archive-create --encrypt`).

## Ограничения

- Останавливаются только собственные units продукта. Процессы вне systemd,
  внешние писатели и другие установки — ответственность интегратора.
- Безопасное стирание носителя не выполняется (`secure_erase: false`).
- Секреты во внешнем EnvironmentFile и рабочие каталоги контроллера вне
  корня установки не удаляются.
- Проверено синтетическим менеджером в тестах и в одноразовом rootless
  Podman с реальным user-systemd (`tests/run_isolated_systemd_test.py
  --run --lifecycle`); это не приёмка на пользовательской системе.
