   Полезный существующий код проверяй и интегрируй, не переписывай автоматически.
   Старый PASS из handoff не является новым доказательством на текущем artifact.
3. Если в репозитории уже есть ToDo, перенеси туда эти задачи с их ID и укажи
   один канонический путь. Не веди два расходящихся списка. Поставляемый файл
   можно использовать как основу TODO.md; формат не важнее единства состояния.
4. ID HIM-001…HIM-106 постоянны. Не перенумеровывай и не переиспользуй их.
   Новые задачи получают следующие свободные ID; подзадачи ссылаются на родителя.

   и RESUME/state по разделу 31 PROMPT.
6. Работай по зависимостям. Недоступность remote блокирует его sync, но не создание ToDo/RESUME
   и доступное локальное сохранение. Независимые задачи можно выполнять параллельно
   в отдельных worktree. Общее ядро не должно содержать особые ветки JobPilot/Rent.

   Всю общую задачу закрывай только после её заявленного покрытия.

   независимую реализацию и проверки на доступных средах, сохраняя BLOCKED.
   Не обходи функциональную или защитную зависимость ради отметки прогресса.
9. Первый практический результат — reference app через настоящий GUI во всех
   четырёх режимах. Минимальные доверие, согласия, права и диагностика нужны
   до него; полный lifecycle и расширенная аналитика доводятся на этапе 3.
10. После КАЖДОГО задания выполняй сохранение по протоколу ниже. Не жди конца
    этапа. Согласованные изменения кода и запись ToDo входят в один checkpoint.

Статус задачи:
TODO — не начато / ещё не принято;
IN_PROGRESS — выполняется;
BLOCKED — конкретное препятствие записано;
DONE — выполнены критерии этой задачи и обязательные проверки.

Статус проверки:
NOT RUN / PENDING / PASS / FAIL / BLOCKED.
N/A допустимо для отдельного сценария только с обоснованной неприменимостью.
Оно не заменяет PASS и не позволяет убрать обязательную платформу из reference.

Сохранение ведётся независимо от готовности:
NOT_CHECKED / LOCAL_SAVED / SYNC_PENDING / SYNC_CONFIRMED /
SYNC_CONFLICT / SYNC_BLOCKED.
Для local commit, отдельного Docker Git remote и GitHub состояние раздельное.
Если Docker Git — та же рабочая копия, локальный commit выполняет локальное
сохранение; лишний remote не создаётся. DONE + SYNC_PENDING означает
выполненную локально задачу, ещё не сохранённую во всех обязательных местах.

Поле sync в отслеживаемом ToDo — последнее наблюдённое состояние с датой.
Успех будущего push заранее не записывай. Фактический SHA и квитанция push
определяются после commit и сохраняются вне отслеживаемого дерева на постоянном
диске; при восстановлении проверяются Git history и remotes.
Не создавай рекурсивные служебные commits ради записи SHA самого commit.

[ ] Критерий готовности сопоставлен с фактическим результатом.
[ ] Проверки записаны честно; незапущенное не помечено PASS.

[ ] Назначен checkpoint_id; код и описание результата включены в один commit.
[ ] Локальный commit подтверждён; остаточные dirty files объяснены.
[ ] Отдельный Docker Git remote синхронизирован, если он предусмотрен.
[ ] GitHub рабочая ветка синхронизирована.
[ ] Для каждого remote проверено наличие нужного commit в истории.
[ ] Sync receipt сохранён без рекурсивных «коммитов о коммите».
[ ] Указаны препятствия и следующий безопасный шаг.

Этот повторяемый протокол не увеличивает счётчик 106 проектных задач.
В норме он завершается до следующей задачи. При недоступной сети допустима
независимая работа с локальными checkpoint и явным SYNC_PENDING/BLOCKED.
Не выдавай недоступный Docker Git/GitHub за успешно проверенный.

========================================================================
ПОРЯДОК ПРОДОЛЖЕНИЯ ПОСЛЕ ОБРЫВА
========================================================================

1. Прочитать текущие инструкции, канонический ToDo, журнал и RESUME/state.
2. Проверить branch/HEAD, незакоммиченное, worktree и постоянное хранилище.
3. Сопоставить task_id/checkpoint_id с реальной историей локально и в remotes.
4. Сохранить найденную незавершённую работу до получения/интеграции изменений.
5. Проверить ещё работающие процессы/сборки и эффекты прерванной операции.
6. Завершить недостающую синхронизацию, не повторяя уже выполненную задачу.
7. Продолжить с первой реально незавершённой безопасной операции.

Никаких автоматических reset --hard, clean, force push, удаления worktree,
томов или пользовательских данных ради «восстановления».
Гарантируется продолжение с последней сохранённой точки; изменения после неё
сначала исследуются. WIP checkpoint допустим, но не означает DONE.

========================================================================
ФИНАЛЬНЫЙ КРИТЕРИЙ
========================================================================

Мастер установки и обслуживания работает на русском, английском и немецком.
Модуль подключается к другому продукту через документированный публичный API,
создаёт реальные Windows/Linux установщики с native/Docker, доводит установку
до работающего веб-приложения, сохраняет восстановимость данных, объясняет
ошибки и допускает повторное использование без форка ядра.

Готовность подтверждают реальные artifacts и receipts, полный ToDo, актуальный
handoff и проверенное сохранение разрешённых результатов в Git.
Этот план сам по себе не утверждает, что система уже реализована.
