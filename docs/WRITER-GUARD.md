# Совместная блокировка писателей и архива на Linux

`homensai_installer_client.CooperativeWriterLock` — необязательный
механизм для продуктов, в которых **каждый** процесс-писатель добровольно
использует один и тот же файл блокировки. Писатель держит общую блокировку на
всё время, когда может менять данные; архиватор берёт исключительную блокировку
до проверки остановки служб и удерживает её до завершения снимка и повторной
проверки. Если блокировка занята, архивирование отказывает без ожидания.

```python
from homensai_installer_client import CooperativeWriterLock

guard = CooperativeWriterLock('/absolute/private-control/writers.lock')
with guard.hold(exclusive=False):
    run_product_writer()
```

Для экспериментального подписанного Linux-обновления API 1.62 принимает
необязательный `writer_lock_path`; путь включается в идентичность плана.
При просмотре, восстановлении и последующем управлении той же транзакцией
нужно передать тот же путь. Состав запросов описан в [API-DESIGN.md](API-DESIGN.md)
и контрактных схемах. Интегратор внутреннего Python-интерфейса может также
передать объект как `writer_lock` в `assemble_prepared_linux_update`. Без
явного указания замка защита не включается. Класс доступен в экспериментальном
пакете клиента, а `shared.writer_guard` ссылается на ту же реализацию. Передача
пути или объекта не доказывает, что другие программы соблюдают протокол.

Каталог блокировки должен существовать, принадлежать текущему пользователю и
иметь права `0700`. Файл создаётся с правами `0600`, остаётся на месте между
запусками и не должен удаляться или заменяться. Путь выбирает доверенный
интегратор; он должен быть вне корней программы, данных, архивов и рабочего
каталога обновления. Файл, каталог и все их родители должны быть защищены от
неавторизованных изменений. Нельзя использовать разные пути или разные inode
для одного набора данных. Контейнерам потребовалась бы отдельная проверенная
передача того же inode; Docker-поддержка здесь не реализована.

В Linux используется неблокирующий `flock`: писатели берут `LOCK_SH`,
архиватор — `LOCK_EX`. Lock на другом API, например POSIX record lock, не
считается участием в этом протоколе. Дескриптор помечен close-on-exec: каждый
запущенный через `exec` писатель должен получить собственную блокировку.
Проверены отдельные локальные процессы, завершение писателя по SIGKILL,
конкуренция блокировок и реальный архив синтетических данных. Сетевые файловые
системы, Windows, питание и реальные продукты не проверялись.

Синтетический продукт поддерживает необязательный `--writer-lock /absolute/path`:
в этом режиме каждый из `serve`, `worker` и `migrate` получает общий lock до
работы с данными и требует установленный пакет клиента. Без параметра поведение
не меняется. Через изолированную установку wheel 0.3.0 проверено, что работающий
worker блокирует исключительный lock, а после его остановки тот доступен.
Отдельный тест запускает одновременно web и worker с одним lock: остановка
только worker не разрешает архив, после остановки обоих lock становится доступен.

В контекст записи результата включены SHA-256 пути и SHA-256 идентичности файла
(`device:inode`); это не подпись и не проверка происхождения. Если файл подменён
во время снимка, результат остаётся `pending`; при изменении `device:inode`
между повторами готовая отметка не принимается. Повторное использование inode
файловой системой или умышленная подмена с тем же идентификатором не исключены.
Подготовка, переключение и запуск нового выпуска повторно проверяют отметку
исходной копии; перед миграцией дополнительно проверяется отметка её копии.
При включённом замке сверяются путь и идентичность файла. При утрате отметки,
её неподтверждённом состоянии или замене файла продвижение останавливается;
откат не требует эту отметку для восстановления исходного архива.
Перемещение или восстановление на другой
файловой системе также потребует отдельной проверки. Старые отметки без
идентификатора файла не принимаются автоматически. Остановка выбранных user-units по-прежнему проверяется до и
после снимка. Полученная защита не охватывает процессы, которые игнорируют
`flock`, используют другой файл, работают с другими правами или обходят
протокол; не гарантирует отсутствие записи до/после удержания блокировки и не
доказывает, что архив согласован для произвольной базы. Шаг 53 плана остаётся
незавершённым.

На реальном синтетическом worker проверен отказ зашифрованного снимка, пока
писатель держит lock; после его остановки снимок создан и проверен. Повторный
запуск другого согласованного worker внутри операции архивирования был отклонён.
В этой проверке состояния systemd-группы моделировались тестовым адаптером.
В отдельном systemd-контейнере через API 1.62 проверены отказ с занятым замком
и успешное обновление с указанным свободным замком, включая миграцию и запуск
синтетического продукта. Реальные продукты и игнорирующие lock писатели этими
испытаниями не охвачены.
