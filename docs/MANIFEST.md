# Манифест продукта, версии 1 и 2

© 2026 Serhii Khomenko · HomenS.AI

Манифест отделяет параметры продукта от общего механизма установки. На шаге 1
реализованы проверка JSON и формирование Docker-заготовок v1. Шаг 2 добавляет
контракт v2 по сообщению Rent. На шаге 3 добавлены библиотечные DataHome,
ZIP/SHA-256 и восстановление в пустой каталог: [ARCHIVE.md](ARCHIVE.md).
Установка, миграции и транзакция обновления/отката пока **не реализованы**.

Контракт: [shared/manifest.schema.json](../shared/manifest.schema.json).
Примеры: [JobPilot v1](../examples/jobpilot.manifest.json),
[Rent v2](../examples/rent.manifest.json).
Происхождение: [PROVENANCE.md](PROVENANCE.md).

## Контракт v2 и миграция

Валидатор принимает v1 без изменений: пример JobPilot остаётся v1.
`schema_version: 2` включает отдельный набор обязательных полей. Простая замена
номера версии недостаточна; автоматического преобразования нет.

Для ручной миграции сохранить `product_name`, `product_id`,
`archive_before_replace: true`, поменять `schema_version` на `2`. Перенести
`port` в `web.port`, путь старого `healthcheck_url` в `web.healthz`, задать
`web.host: "127.0.0.1"`. `migration_command` перенести в `migrations.cmd`,
`docker.start_command` — в argv нужного компонента. Удалить из корня старые
`port`, `healthcheck_url`, `migration_command`, `data_home_env`, `docker`:
в v2 они запрещены. Явно заполнить все оставшиеся секции по таблице ниже;
готового эквивалента Docker/DataHome в v2 нет. Старый Docker-рендер принимает
только v1 и возвращает понятную ошибку для v2, чтобы не терять компоненты,
хуки и требования обновления при рендере.

| Поле v2 | Контракт |
|---|---|
| `runtime` | `python: "3.14"`; `lock_files.windows` и `.linux`, каждый `{file, sha256}`; непустой `vendor_wheels[]` с теми же полями и расширением `.whl`; `offline: true`. SHA-256 — ровно 64 строчные hex-цифры. Файлы задаются относительно будущего payload, без URL, абсолютных путей и `..`. Пути артефактов уникальны. |
| `paths` | Обязательные `app`, `releases`, `data`, `backup`, `services`, `config`, `runtime`. Все пути имеют один тип корня: относительные к единому корню установки, абсолютные POSIX либо абсолютные Windows (разные диски допустимы). Ни один из пяти постоянных каталогов не может совпадать с `app`/`releases` или находиться внутри них. |
| `components[]` | От 1 до 64 объектов `{name, cmd, after, heartbeat, restart}`. Уникальное `name`: `[a-z][a-z0-9_-]*`, до 63 символов. `cmd` — argv по ограничениям v1. `after` — уникальные имена существующих компонентов; циклы и ссылка на себя запрещены. Порядок массива не задаёт порядок запуска. |
| `heartbeat` | `{file, interval, timeout}`: файл относительно `paths.data`, интервалы в секундах, 1–86400; `timeout >= interval`. |
| `restart` | `{delay, max, window}`: задержка 0–86400 секунд; `max` 1–100 падений за окно 1–86400 секунд, `delay <= window`. После достижения лимита будущий надзор должен остановить компонент и выдать сигнал. |
| `web` | `{host, port, healthz}`. Единственный допустимый host — строка `127.0.0.1`; `localhost`, IPv6, другие loopback и публичные адреса отвергаются. Порт 1024–65535; `healthz` — путь с начальным `/`, без URL/query/fragment. |
| `secrets[]` | Только дескрипторы `{name, required, contexts, same_value}`. `name` — имя переменной `[A-Z][A-Z0-9_]*`, до 128 символов; имена уникальны. `required` и `same_value` — bool, `contexts` — непустой набор `service`/`admin`. Для `same_value: true` нужны оба контекста; пример — `BACKUP_PASSWORD`. Пустой список допустим. |
| `modes[]` | Уникальное `name` и непустой список имён `components`. Каждый компонент включён хотя бы в один режим, все его зависимости также входят в этот режим. |
| `mutual_exclusion` | Массив уникальных групп из двух или более существующих имён режимов; одновременно допускается не более одного режима каждой группы. Повтор одного набора в другом порядке запрещён; пустой список допустим. Для общего хранилища/токена Rent пример явно исключает совместный запуск `autonomous` и `platform`. |
| `migrations` | `{cmd, backup_before_each: true, new_db_no_backup: bool}`. Копия обязательна перед каждой миграцией существующей БД; `new_db_no_backup` разрешает исключение только для новой пустой БД. |
| `backup`, `restore` | `backup: {cmd, encrypted: true}`, `restore: {cmd}` — команды адаптера продукта, не код архивирования. |
| `update` | `staged_releases: true`, `pointer_file`, `state_file`, `health_wait` (1–600 секунд), `backup_before_rollback: true`, `retain_previous_release: true`, `retain_runtime: true`. Файлы указателя/состояния — разные относительные пути внутри `paths.services`. В примере это `active.json`/`update.json` и ожидание 60 секунд. |
| `hooks` | Обязательные `pre_start`, `health_checks`, `post_update`: массивы команд argv, в том числе пустые. Это точки вызова адаптера продукта. |

Все перечисленные секции v2 обязательны. Неизвестные поля запрещены на каждом
уровне. В частности, `value`, `values`, `default`, `password`, `token`, `api_key`,
`private_key`, `secret`, `secret_value`, произвольный `env` и другие поля для
передачи значений не допускаются, в том числе внутри `secrets[]`. Значения
секретов нельзя помещать и в команды/хуки/прочие строки: валидатор проверяет
структуру, но не умеет распознавать произвольный секрет в разрешённой строке.
Диагностика не выводит значения ошибочных полей. Сам валидатор не получает,
не сравнивает и не хранит значения секретов из окружения или файлов.

Пути проверяются **лексически**, без чтения каталогов продукта: разделители
`/` и `\` нормализуются, регистр сравнивается консервативно без различия даже
для POSIX (безопасный перенос на Windows); `..`, UNC, Windows-пути относительно
диска/текущего диска, потоки `:`, сегменты с конечным пробелом/точкой запрещены.
Равенство и вложенность сравниваются по сегментам: `app-data` не вложен в `app`.
Интерполяции переменных нет. Symlink/junction, mount, короткие имена Windows и
фактические права доступа не исследуются: будущий установщик обязан повторно
проверить реальные цели путей перед записью. Проверка SHA-256 сейчас проверяет
формат, но не содержимое файла; существование wheels/lock-файлов, хэши внутри
lock-файлов, полнота offline payload и совместимость Python/ОС ещё не проверяются.

Требуемая будущая последовательность Rent: stop в обратном порядке зависимостей →
проверенная зашифрованная копия → staging в `paths.releases/app-<version>` →
проверка полноты payload → копия перед каждой миграцией → миграции → атомарная
смена pointer → pre_start/start по зависимостям → web healthz и health_checks
в пределах health_wait → post_update. При сбое до restore обязательна отдельная
проверенная копия текущей БД **before-rollback**; без неё откат не начинается.
Затем restore → прежний pointer → start → health. Старые release/runtime
сохраняются. Операции должны сериализоваться; состояние не содержит секретов.
Флаги в JSON декларируют этот контракт, но не подтверждают выполнение шагов.
Выбор активных режимов, блокировка операций, сравнение секретов, надзор,
стадии обновления и исполнение хуков в шаге 2 отсутствуют.

Пример Rent целиком вымышленный: `demo-layout/*`, модули
`fictitious_rent_demo.*`, имена lock/wheel и повторяющиеся буквы SHA-256 —
публичные заглушки, не реальные пути, зависимости, хэши или рабочий адаптер Rent.
Основание дизайна — [сообщение Rent](REQUESTS-RENT-2026-10-24.md), а не его код.

```powershell
py -3.14 -B -m shared.manifest examples/rent.manifest.json
```

## Сохранённый контракт v1 и Docker-рендер шага 1

| Поле | Контракт v1 |
|---|---|
| `schema_version` | Целое число `1`; изменение несовместимого контракта требует новой версии. |
| `product_name` | Название, 1–128 символов, без управляющих символов и крайних ASCII-пробелов. |
| `product_id` | Стабильный ID, 1–63 символа: первая буква/цифра `a-z0-9`, далее также `_` и `-`. Используется для Compose project/image; не является идентификатором отдельной установки. |
| `port` | Целое число 1024–65535, одинаковое внутри контейнера и на хосте. Приложение должно само слушать этот порт на интерфейсе контейнера, доступном Docker. |
| `data_home_env` | Имя переменной окружения продукта: `[A-Z][A-Z0-9_]*`, до 128 символов. Значение в контейнере — `/data`. |
| `migration_command` | Непустой массив argv, до 64 непустых строк по 4096 символов, без управляющих символов. Проверка и рендер не исполняют эту команду. |
| `healthcheck_url` | `http://127.0.0.1:<port>/<path>` внутри контейнера. Путь содержит только ASCII-буквы, цифры и `/_.~-`; query, fragment, credentials, redirect и proxy не допускаются. Успех — HTTP 200. |
| `archive_before_replace` | Обязательное логическое `true`: отключение полного архива контрактом запрещено. Это декларация требования, не доказательство наличия архива. |
| `docker.base_image` | Ссылка на Linux Python-образ, обязательно с `@sha256:` и 64 шестнадцатеричными символами нижнего регистра. Зависимости продукта должны быть подготовлены в образе заранее. |
| `docker.start_command` | Массив argv по тем же ограничениям, что и миграция; попадает в Docker `CMD` без shell. |

Все поля v1 обязательны; неизвестные поля запрещены, в том числе внутри `docker`.
JSON должен быть UTF-8 (BOM допускается); повторяющиеся ключи, NaN и Infinity
отвергаются. CLI возвращает `0` при успехе и `2` при ошибке входных данных.

Проверяющий модуль использует только stdlib Python 3.14+ и читает локальную схему;
это реализация набора ключевых слов этой фиксированной схемы, а не универсальный
JSON Schema engine. Дополнительные семантические проверки: порт URL совпадает с
`port`; `data_home_env` не равен `PATH`, `HOME`, `TMPDIR`, `PYTHONHOME`, `PYTHONPATH`,
`PYTHONDONTWRITEBYTECODE`, `PYTHONUNBUFFERED`, `LD_PRELOAD`, `LD_LIBRARY_PATH`.
Они выполняются Python-валидатором сверх схемы. Целочисленные поля принимают только
JSON integer (`8765.0` и `true` отвергаются). Значения из ошибочного манифеста
не включаются в диагностические сообщения.

Проверка из корня репозитория:

```powershell
py -3.14 -B -m shared.manifest examples/jobpilot.manifest.json
```

Рендер в новый явно выбранный каталог:

```powershell
py -3.14 -B -m shared.render_docker examples/jobpilot.manifest.json --output-dir build/jobpilot
```

Появятся `Dockerfile` и `compose.yml`. Существующие файлы с такими именами
не перезаписываются. Сеть, Docker, архивы и команды продукта не вызываются.
API `validate_manifest()` возвращает независимую копию словаря;
`render_docker()` возвращает словарь с двумя текстами без записи файлов.

Dockerfile использует UID/GID `10001:10001`, `/app` для программы, `/data` для
постоянных данных и exec-form CMD/healthcheck. При сборке `/data` получает владельца
10001 и режим 0700. Compose задаёт `read_only: true`, один именованный том
`data:/data`, публикацию `127.0.0.1:<port>:<port>`, `restart: unless-stopped`,
`cap_drop: [ALL]`, `no-new-privileges` и HTTP healthcheck со стартовой паузой 60 с.
Нездоровое состояние само по себе не перезапускает контейнер: restart policy
применяется к завершению процесса. Read-only корень обеспечивается именно Compose;
отдельный `docker run` должен задать аналогичные ограничения.

В каталоге результата перед будущей сборкой потребуется подготовленный `payload/`
с кодом и публичными ресурсами продукта, без секретов и пользовательских данных.
`COPY` сохраняет владельца кода root; приложение не должно писать в `/app`.
Базовый образ должен содержать `python`, POSIX shell, `mkdir`, `chown`, `chmod`,
все рабочие зависимости, не объявлять дополнительные VOLUME и не требовать
root при старте. Унаследованный ENTRYPOINT сбрасывается. Digest в примере взят
из JobPilot Dockerfile; его существование, содержимое и пригодность здесь не
проверялись. Новых сетевых проверок или загрузок не было.

Единый том обобщает контракт DataHome JobPilot: будущий адаптер продукта должен
размещать в нём `data`, `documents`, `configuration`, `secrets`, `history`,
`installation`. Эти каталоги сейчас не создаются; legacy-пути `/backups`,
`/documents`, `/run/secrets`, bootstrap/runtime.env и ACL/DPAPI не адаптированы.
Значение `JOBPILOT_DATA_HOME` в примере обозначает **контейнерный** корень;
в исходном JobPilot это также настройка хостового bootstrap. Пример не является
совместимой заменой нынешнего установщика JobPilot.

Порт 8765 и команда `backend.cli migrate` в примере демонстрационные:
наличие такой команды не подтверждено шестью разрешёнными исходниками.
`backend.main` и `/health/ready` взяты из исходников. Зависимости JobPilot
не включены в базовый Python-образ; без их подготовки приложение не запустится.
Запись временных файлов при read-only корне потребует поддержки продукта
внутри `/data`; дополнительных томов/tmpfs этот шаг не добавляет.

Перед будущей заменой потребуется остановить всех писателей, создать и проверить
полный архив, затем выполнить миграцию и healthcheck; при сбое восстановить
согласованное состояние. Ни миграция в ENTRYPOINT, ни автоматическая замена данных
в данный шаг не входят. Архив в том же DataHome не заменяет внешнюю резервную копию.
Несколько экземпляров, владение процессами, блокировки, перенос данных, Windows,
Linux native и install/update/restore/rollback остаются следующими этапами.

Тесты pytest работают без сети; файлы сценариев создаются только через `tmp_path`.
Команда для имеющего pytest Python (кэш и bytecode отключены):

```powershell
$env:PYTEST_DISABLE_PLUGIN_AUTOLOAD = '1'
py -3.14 -B -m pytest -q -p no:cacheprovider --basetemp .test-tmp
```

Это локальная проверка контракта и текстов. Требуемые CLAUDE.md проверки в Docker
остаются отдельной приёмкой; разрешённый доступ к Docker Engine необходим для них.

В данной Windows-песочнице штатный tmpdir plugin pytest создал недоступный для
следующих операций `.test-tmp` (`WinError 5`). Полный набор был выполнен следующей
командой: временная fixture с тем же именем `tmp_path` создаёт каталоги с обычным
наследованием прав внутри worktree, не изменяя ACL и не отключая файловые тесты.
Для повторения этой проверки из PowerShell:

```powershell
$env:PYTEST_DISABLE_PLUGIN_AUTOLOAD = '1'
@'
from pathlib import Path
import uuid
import pytest

class WorkspaceTemps:
    @pytest.fixture
    def tmp_path(self):
        path = Path.cwd() / 'build' / 'manifest-pytest' / uuid.uuid4().hex
        path.mkdir(parents=True)
        return path

raise SystemExit(pytest.main(['-q', '-p', 'no:cacheprovider', '-p', 'no:tmpdir'], plugins=[WorkspaceTemps()]))
'@ | py -3.14 -B -
```

Историческая итоговая строка шага 1: `94 passed in 3.96s` (код 0).
Каталоги `build/` и `.test-tmp/` исключены из Git; недоступный `.test-tmp`
не удалялся и его права не исправлялись.

## Проверка шага 2, 24.10.2026

`py -3.14 -B -m pytest --version` вернул `pytest 9.1.1`. Полный набор с новой
fixture не изменялся: использована в точности команда `WorkspaceTemps` выше,
все тесты включены, все файлы сценариев создаются через `tmp_path` внутри
worktree; сеть блокирует autouse fixture в `tests/conftest.py`.
Точный stdout успешного запуска (код 0):

```text
........................................................................ [ 20%]
........................................................................ [ 41%]
........................................................................ [ 61%]
........................................................................ [ 82%]
.............................................................            [100%]
349 passed in 3.22s
```

До этого обычный полный запуск с `--basetemp build/step2-pytest` завершился
с кодом 1 (`331 passed, 14 errors in 6.66s`): родитель `build/` отсутствовал,
tmpdir fixture не могла создать basetemp (`WinError 3`). После создания `build/`
повторный штатный запуск с `--basetemp build/step2-stock-pytest` также вернул
код 1: `PermissionError: [WinError 5]` в tmpdir plugin, включая sessionfinish.
Эти два запуска не считаются успешными. ACL/настройки безопасности не менялись,
недоступный каталог не удалялся. Успешный обход использует обычный `Path.mkdir()`.
Промежуточный полный запуск до финальных двух сценариев дал
`347 passed in 3.70s`; итоговый запуск выше добавляет проверку разных дисков
Windows и отказ от пути файла с конечным `/.`.

Обе команды `py -3.14 -B -m shared.manifest examples/jobpilot.manifest.json`
и `py -3.14 -B -m shared.manifest examples/rent.manifest.json` завершились
с кодом 0, соответственно `Манифест корректен: homensai-jobpilot-pro` и
`Манифест корректен: homensai-rent-demo`.

Docker-проверки в этом шаге не выполнялись: задание ограничено кодом worktree
и запрещает воздействие на внешние службы. Успех pytest относится только к
схеме, валидатору, примерам и текстовому рендеру v1; это не приёмка
install/update/restore/rollback или offline-установки.
