# Контрольные точки разработки и восстановление

`tools/checkpoint.py` сохраняет одну проверенную порцию работы в локальный Git и независимо отправляет её в явно выбранные remotes. Инструмент работает с исходниками проекта. Он не запускается на компьютере конечного пользователя при установке, не отправляет пользовательские данные и не является системой телеметрии.

Требования первой версии: Python 3.12+, Git 2.36+, существующий рабочий репозиторий с начальным коммитом, настроенная личность автора Git и feature-ветка. Git hooks и подпись коммитов используют уже принятую конфигурацию репозитория. Зависимости Python не нужны. Для Windows необходимы Git for Windows и Python; проверка этой реализации на Windows остаётся отдельным пунктом матрицы.

## Порядок после каждого законченного задания

1. Выполнить работу и предусмотренную для неё проверку. Записать конкретное доказательство: команду, результат, ссылку на отчёт или тест. Если проверена только source-версия в Linux, это так и обозначить.
2. Получить стабильный ID до обновления ToDo:

   ```text
   python tools/checkpoint.py id
   ```

3. Обновить ToDo или журнал задач, указав ID задания, выданный `CP-…`, сделанное, проверку и оставшиеся ограничения. `DONE` означает выполнение всех критериев задачи. Локальный коммит или успешный push сами по себе не означают `DONE`. Инструмент не меняет статусы задач автоматически.
4. Проверить diff и явно перечислить файлы этой порции работы. ToDo должен входить в этот же список и содержать ID задания и контрольной точки. Данные для восстановления связаны стабильным ID; SHA собственного ещё не созданного коммита в ToDo не требуется.
5. Сохранить контрольную точку. Например, после подстановки реального ID:

   ```text
   python tools/checkpoint.py save --repo . --checkpoint-id CP-20261025T120000Z-012345abcdef --task-id HIM-009 --todo TODO_RU.txt --file TODO_RU.txt --file tools/checkpoint.py --file tests/test_checkpoint.py --file docs/CHECKPOINTS.md --remote origin --remote forgejo --message "Добавлены контрольные точки и проверено восстановление"
   ```

   `TODO_RU.txt` здесь — пример. Следует указать действительный файл ToDo/журнала в данном проекте. Каталоги, шаблоны и `git add .` не применяются. Для удаления файла нужно явно добавить его прежний путь в `--file`; переименование задаётся двумя путями.
6. Прочитать JSON-результат. Проверить `local_saved`, `commit_sha` и отдельное состояние каждого remote. Если сервер недоступен, локальная работа уже сохранена; продолжить синхронизацию тем же ID после восстановления доступа.

Если known remote HEAD уже проверен при планировании публикации, его можно зафиксировать дополнительно:

```text
python tools/checkpoint.py save --repo . --checkpoint-id CP-example-001 --task-id HIM-009 --todo TODO_RU.txt --file TODO_RU.txt --file example.py --remote origin --expect-remote origin=0123456789abcdef0123456789abcdef01234567
```

`--expect-remote origin=absent` означает, что ветки на сервере пока не должно быть. Если ожидание не передано, первая успешная проверка выбранной ветки фиксируется в квитанции. При повторном запуске это ожидание не заменяется новым молча.

## Что именно сохраняется

Инструмент строит отдельный Git index от исходного HEAD и добавляет в него только явно разрешённые пути. Выполняются `pre-commit`, `prepare-commit-msg` и `commit-msg`; после них повторно проверяются состав коммита, содержимое staged-файлов и обязательные ID. Hook, добавивший чужой файл, блокирует создание коммита. Настроенный `commit.gpgsign=true` выполняется; при невозможности подписать коммит сохранение останавливается, подпись не отключается.

Коммит создаётся из проверенного дерева, а feature-ветка переводится на него через `git update-ref` с ожидаемым прежним HEAD. При конкурентном продвижении ветки инструмент не перезаписывает её. После этого основной index обновляется только для выбранных файлов; чужие staged- и unstaged-изменения сохраняются. Содержимое рабочей копии инструмент не откатывает. `post-commit` вызывается после локального сохранения; его ошибка отражается в результате и не отменяет уже созданный коммит.

Указанные в allowlist файлы не должны заранее иметь staged-изменений: инструмент отказывается присваивать себе ранее подготовленные части файла. Следует отдельно решить, кому относятся такие изменения. Не нужно сбрасывать чужой index ради запуска checkpoint.

Ветка `main`, `master`, `release`, `production`, `prod`, ветки `release/*` и detached HEAD блокируются. Слияние, rebase, cherry-pick, revert и конфликтующий index также требуют предварительного завершения обычным рабочим процессом. Создание самого первого коммита в пустом репозитории остаётся явным отдельным действием.

## Квитанция и восстановление после обрыва

Квитанция находится в Git common directory:

```text
<git-common-dir>/hinstall-checkpoints/<checkpoint-id>.json
```

Это служебная область Git вне отслеживаемого дерева исходников. Для linked worktree используется общий Git directory, а операция дополнительно привязывается к своей рабочей копии. Квитанция содержит ID задачи и checkpoint, ветку, исходный и созданный SHA, список файлов, состояние локальной транзакции и отдельные подтверждения remotes. URL с учётными данными, содержимое файлов, Git stderr и вывод hooks в неё не записываются. Подпапка `<checkpoint-id>.work` содержит служебные индексы и сообщение коммита; её не следует удалять до окончания локального восстановления.

На POSIX создаются служебные каталоги `0700` и квитанции `0600`; чужой владелец, широкие права, symlink и неподходящий тип служебного файла отвергаются. Windows использует наследуемые ACL Git directory; POSIX-режимы не являются подтверждением проверки Windows ACL. Рабочая копия и `.git` должны находиться в каталоге, доступном только уполномоченным пользователям.

Посмотреть состояние и продолжить:

```text
python tools/checkpoint.py status --repo . --checkpoint-id CP-example-001
python tools/checkpoint.py resume --repo . --checkpoint-id CP-example-001
```

`resume` использует сохранённый ID и SHA. Повторного коммита уже сохранённой порции не происходит, а появившиеся позже изменения рабочей копии в неё не добавляются. Повторный `save` с теми же ID и параметрами имеет то же поведение. Использование того же ID с другим составом запроса блокируется.

Если обрыв произошёл до создания коммита, перед продолжением проверяются исходный HEAD, index и хеши выбранных файлов. Изменение этих файлов после обрыва требует повторного рассмотрения работы и новой контрольной точки. Если обрыв произошёл между обновлением ветки и заменой index, инструмент может завершить именно свою транзакцию: проверяет хеш, файловую идентичность своего `index.lock`, прежний index и сохранённый SHA. Неизвестный или чужой `index.lock` никогда не удаляется автоматически.

Квитанция — локальный журнал восстановления, а не подписанное доказательство против злонамеренного владельца компьютера. При потере всей рабочей копии нужно клонировать подтверждённый remote и найти `Checkpoint-ID`/`Task-ID` в сообщении коммита вместе с записанным ToDo. Автоматическая реконструкция удалённой квитанции из истории в первой версии не реализована. Следующую порцию следует сохранять с новым ID после проверки этой истории.

## Синхронизация GitHub и локального Git-сервера

Remotes задаются каждым `--remote` отдельно. Никакой remote не добавляется, не переименовывается и не включается автоматически. Имена `origin` и `forgejo` — обычная договорённость проекта, а не доказательство назначения сервера.

Для каждого выбранного remote инструмент:

1. Читает один настроенный push URL и фиксирует его хеш. Несколько push URL, неизвестный транспорт и встроенные в HTTP URL учётные данные отвергаются; для авторизации используется существующий credential helper/SSH.
2. Проверяет фактический HEAD нужной feature-ветки через `ls-remote`, сравнивает его с сохранённым ожиданием и проверяет историю. При необходимости загружает объект коммита без изменения веток или рабочей копии.
3. Выполняет обычный push одного конкретного SHA в одну feature-ветку. Force, mirror, публикация tags и рекурсивная отправка submodules не используются. `pre-push` не отключается.
4. Повторно читает remote HEAD независимо от кода завершения push. Если сервер принял данные, но ответ потерялся, подтверждает принятый SHA. Если проверка недоступна, оставляет состояние неподтверждённым.
5. Записывает результат этого remote в квитанцию и переходит к следующему. Отказ одного сервера не отменяет локальный коммит и не отменяет проверку другого.

Изменение remote URL после первой попытки требует отдельного решения владельца и не принимается молча. Удалённая ветка, уже содержащая checkpoint в своей истории, считается синхронизированной; более новые коммиты на сервере не откатываются. Divergence требует обычного review/merge/rebase в отдельном рабочем процессе. Инструмент не пытается исправить её force-push.

Проверка ожидаемого HEAD до push и обычное правило fast-forward защищают от перезаписи чужой истории. Между проверкой и push сервер может измениться; транзакции сразу над локальным Git и несколькими независимыми серверами нет. Результат сообщается отдельно по каждому серверу и подтверждается после отправки. Отмена успешной отправки на один сервер из-за отказа другого не выполняется.

Ранее встречавшийся адрес локального Forgejo/Gitea `http://127.0.0.1:8796/` служит только ориентиром для компьютера владельца. Его фактическая доступность, URL конкретного репозитория и права доступа должны быть проверены там, где запускается инструмент. В контейнере `127.0.0.1` означает сам контейнер, поэтому адрес хоста выбирается по реальной Docker-сети. Эта реализация не создаёт Docker-контейнеры, не заявляет доступность пользовательского Forgejo и не меняет сетевые настройки.

## Состояния и коды завершения

| Поле/состояние | Значение |
| --- | --- |
| `PREPARED` | Запрос и исходные условия сохранены; локального коммита ещё нет. |
| `COMMIT_PREPARED` / `INDEX_PREPARED` | Объект коммита создан; локальную транзакцию нужно завершить или проверить после обрыва. |
| `LOCAL_SAVED` | Коммит находится в локальной feature-ветке; remotes не запрошены или синхронизация ещё не началась. |
| `SYNCING` | Выполняются независимые попытки синхронизации. |
| `PARTIAL_SYNC` | Локальный коммит сохранён; как минимум один запрошенный remote не подтверждён. |
| `COMPLETE` | Все явно запрошенные remotes подтверждены. Это не статус готовности продукта и не автоматический `DONE` задачи. |
| remote `SYNCED` | Подтверждён SHA checkpoint или его наличие в истории более нового remote HEAD. |
| remote `PENDING` | Push выполнен, но его результат ещё не подтверждён. |
| remote `BLOCKED` | Сервер/конфигурация недоступны или неприемлемы; локальная работа сохранена. |
| remote `CONFLICT` | Изменился ожидаемый HEAD/сервер либо разошлась история; требуется отдельное решение. |

CLI выдаёт один JSON-объект `result` или `error`. Код `0` означает завершённое запрошенное действие, `2` — локальное сохранение с неподтверждённым remote, `1` — блокировку/ошибку самого действия. Команда `status` тоже возвращает `2` для сохранённого `PARTIAL_SYNC`. Ошибки аргументов возвращаются безопасным JSON без повторения неизвестных значений.

| Код | Что проверить |
| --- | --- |
| `ALLOWLIST_ALREADY_STAGED` | Выбранный файл уже содержит staged-работу; согласовать её принадлежность, не сбрасывать чужие изменения автоматически. |
| `TODO_CHECKPOINT_MARKER_REQUIRED` | В staged-версии ToDo нет ID задачи и checkpoint; исправить запись и начать новую проверенную порцию. |
| `WORKTREE_CHANGED` / `INDEX_CHANGED` | Содержимое изменилось с момента сохранения запроса. Рассмотреть новый diff и создать новый ID. |
| `LOCAL_HEAD_CHANGED` / `LOCAL_REF_UPDATE_FAILED` | Ветку продвинул другой процесс. Сохранённый объект не даёт права перезаписать новое состояние. |
| `INDEX_LOCK_EXISTS` / `INDEX_RECOVERY_CONFLICT` | Действует другая Git-операция либо транзакция не совпадает с квитанцией. Проверить владельца lock и состояние Git вручную. |
| `COMMIT_HOOK_FAILED` | Обязательный hook не прошёл. Выполнить принятую в репозитории проверку локально; checkpoint не публикует потенциально секретный вывод hook. |
| `SECRET_PATTERN_REJECTED` / `SENSITIVE_FILE_REJECTED` | Выбран секретный тип файла или найден известный токен/ключ; убрать секрет из исходников и при реальной утечке сменить его. |
| `REMOTE_UNAVAILABLE` / `PUSH_NOT_CONFIRMED` | Проверить сеть, credential helper и сервер, затем повторить `resume` с тем же ID. |
| `REMOTE_HEAD_CHANGED` / `REMOTE_DIVERGED` | Прочитать обе истории и принять решение в обычном Git-процессе. Force не применяется. |
| `REMOTE_IDENTITY_CHANGED` | Изменилось назначение remote. Проверить новое назначение до любой публикации. |

## Границы первой версии и доказательства

Allowlist ограничен обычными текстовыми UTF-8 файлами до 16 MiB каждый. Symlinks, private-key форматы, `.env` с реальными настройками, базы, архивы и бинарные файлы не включаются; `.env.example`/`.env.template`/`.env.sample` проверяются как обычный текст. Это осознанная граница инструмента исходников. Публикация собранных бинарных релизов выполняется отдельным процессом с inventory, подписями и проверкой лицензий.

Встроенный поиск ловит несколько известных форм ключей и токенов, но не доказывает отсутствие всех возможных секретов. Review diff и принятый в проекте scanner остаются обязательными. Hooks, filters, credential helpers и конфигурация локального Git являются доверенным исполняемым окружением владельца; инструмент не изолирует произвольный вредоносный Git hook. Git trace-переменные из окружения отключаются для дочерних процессов; содержимое stderr/вывода hooks не попадает в JSON/квитанцию.

Проверка:

```text
python -m pytest -q tests/test_checkpoint.py
```

Тесты создают настоящие временные рабочие и bare-репозитории. Проверяются сохранение чужого staged/unstaged-состояния, два remotes, недоступность одного и последующий resume, divergence, lost push response, expected HEAD, смена remote, hooks, точное staged-содержимое, linked worktree, обрыв после update-ref, посторонний index lock, конкурентное продвижение HEAD, идемпотентность, удаления и отсутствие секретов в ответах. Сетевые обращения и пользовательский Git/Docker/Forgejo в этих тестах не используются. Успешный тест в доступной Linux-среде не закрывает отдельную Docker/Windows-приёмку.

Основания используемых Git-примитивов: [git-commit-tree](https://git-scm.com/docs/git-commit-tree), [git-update-ref](https://git-scm.com/docs/git-update-ref), [git-hook](https://git-scm.com/docs/git-hook), [git-push](https://git-scm.com/docs/git-push), [git-ls-remote](https://git-scm.com/docs/git-ls-remote). Публичные материалы проверены 25 октября 2026 года; рабочие тесты выполнены с Git 2.51.1.
