# Генератор Windows PowerShell — шаг 8

© 2026 Serhii Khomenko · HomenS.AI

`shared/windows_ps.py` использует только stdlib и возвращает **тексты**.
PowerShell, WinSW, ACL, DPAPI и службы при генерации не исполняются.
**Готового Windows-установщика нет; приёмка на чистой Win11 отсутствует.**

## Контракт

```python
from shared.windows_ps import render_windows

texts = render_windows(public_manifest_v2,
    install_root=r"C:\Product", modes=("autonomous",),
    winsw_payload=verified_public_artifact_bytes,
    dpapi_scope="LocalMachine")  # либо CurrentUser
```

Результат — `dict[str, str]`: `install.ps1`, `start.ps1`, `stop.ps1`,
`status.ps1`, `uninstall.ps1`, `rollback.ps1`, `secrets.ps1` и XML выбранных
компонентов. Файлы не создаются библиотекой. Порядок фиксирован, значения
окружения и содержимое каталогов продукта не читаются. PS1 содержат UTF-8 BOM:
Windows PowerShell 5.1 корректно прочитает не-ASCII пути. В скриптах нет
операторов PowerShell 7 (`??`, `?.`, `&&`, `||`).

Нужны v2, явный допустимый набор режимов и
`winsw: {version: "2.12.0", sha256: "<64 строчные hex-цифры>"}`.
Перед выдачей текстов `render_services` проверяет SHA-256 предоставленных байтов.
Генератор не скачивает WinSW, не подтверждает его происхождение/архитектуру и
не включает бинарник в результат. При будущем исполнении рядом со скриптами
нужен `WinSW.exe` с этим pin. Реального WinSW в репозитории нет.

Исходный Rent v2 намеренно не содержит pin и отклоняется до его явного
добавления. JobPilot v1 отклоняется: в нём нет контрактов native-компонентов,
путей, режимов и дескрипторов секретов. Docker-команда не превращается
автоматически в native-команду. Для него нужна явная миграция по
[MANIFEST.md](MANIFEST.md). Оба неизменённых примера проверены на такой отказ.
Успешные тесты используют копию Rent с **синтетическими** pin/байтами.

## Смысл сформированных сценариев

| Текст | Будущее действие при отдельном запуске оператором |
|---|---|
| `install.ps1` | Создать app/releases/data/backup/services/config/runtime из манифеста и data/secrets; защитить data/secrets; проверить соседний WinSW.exe; отказать при существующих XML/exe/SCM names; записать XML/копии wrapper; зарегистрировать службы. Не запускает приложение и не заменяет payload. |
| `start.ps1` | Запустить выбранные службы в порядке `after`. |
| `stop.ps1` | Остановить выбранные службы в обратном порядке. |
| `status.ps1` | Прочитать SCM status либо вывести `absent`; это не HTTP health. |
| `uninstall.ps1` | Остановить и снять регистрацию; сохранить данные, секреты, копии, releases/runtime и файлы wrapper/XML/lock. |
| `secrets.ps1` | Запросить значения по именам через `Read-Host -AsSecureString`, записать только DPAPI ciphertext в data/secrets. Существующий файл не перезаписывается. |
| `rollback.ps1` | Проверить recovery → stop → отдельная before-rollback → restore → прежний выпуск → start → health через обязательные порты продукта. |

Все семь сценариев захватывают `services/operation.lock`: FileStream byte
lock на offset `2147483647`, length `1`, тот же диапазон, что у Python
`operation_lock`. Блокировка освобождается в `finally`, файл не удаляется.
Содержимое Python metadata не изменяется; PowerShell stale detection не
реализован. Lock сериализует только сотрудничающие управляющие процессы,
не SCM auto-start и не произвольных писателей. До lock только install может
создать каталог services. Остальные сценарии требуют существующий services;
status также создаёт/открывает файл блокировки, поэтому не является чистым read-only.

Пути — локальные Windows drive-absolute либо manifest-relative к явному корню;
все семь корней попарно не пересекаются. Запрещены UNC, ADS, drive-relative,
`..`, устройства Windows, wildcard, конечная точка/пробел, `%` и неоднозначные
разделители. Конфликты pointer/state с lock и XML/exe запрещены. Идентификаторы
имеют строгий алфавит; PowerShell-литералы удваивают ASCII `'`. Доллар, скобки,
`;`, `&` и backtick в допустимом пути остаются данными в одинарных кавычках.
Типографские кавычки и Unicode-разделители строк в путях отклоняются.
XML экранируется существующим генератором, в PS1 включается как base64 данных;
`Invoke-Expression` и shell-конкатенации нет. Команды манифеста — доверенный
публичный код продукта; произвольные команды не становятся безопасными от
одного экранирования XML. Секретам в этих строках места нет.

Скрипты проверяют существующих предков на reparse point перед операциями.
ACL-обход сначала проверяет каждый узел, затем перечисляет детей; junction
не обходится рекурсивно до проверки. Это не устраняет гонки злонамеренной
подмены между проверкой и I/O и не обнаруживает алиасы 8.3/hard links.

## ACL и секреты

Текст ACL создаёт новую защищённую DACL на data и всех его потомках, включая
secrets: только текущий владелец операции, SYSTEM (`S-1-5-18`) и Administrators
(`S-1-5-32-544`) с FullControl. Предыдущие explicit/inherited ACE удаляются
через новый FileSecurity/DirectorySecurity и Set-Acl. В тексте также есть
`icacls /inheritance:r /grant:r` с SID, без локализованных имён групп.
Одного `/grant:r` недостаточно для удаления чужих explicit grants, поэтому
сначала заменяется вся DACL. Другие корни не получают такую ACL.
Будущему запуску нужны соответствующие права; фактические ACL не проверялись.

`secrets.ps1` принимает только имена из дескрипторов и scope, выбранный при
генерации. Каждое имя, включая admin-only, запрашивается отдельно. BSTR
копируется в временный byte[] UTF-16, `ProtectedData.Protect` шифрует его
с выбранным `DataProtectionScope`, записывается только ciphertext в
`<NAME>.<CurrentUser|LocalMachine>.dpapi`. BSTR, plaintext byte[] и SecureString
очищаются в `finally`. Ошибки фиксированные, без исходного exception и значений;
транскрипция/логирование значений отсутствуют. Пустые значения не проверяются
на продуктовую допустимость; при сбое записи может остаться неполный ciphertext.

CurrentUser связан с профилем пользователя, LocalMachine — с машиной;
для LocalMachine конфиденциальность чтения дополнительно зависит от ACL.
Доставка/расшифровка секретов в окружение службы, выбор service account,
перенос ключей, ротация и проверка same_value между контекстами ещё не реализованы.
Один ciphertext на имя сам по себе не настраивает окружение SCM/WinSW.
В XML остаются только `%NAME%` ссылки существующего рендера.

## Rollback и границы готовности

`rollback.ps1` требует пять `[scriptblock]` параметров: `VerifyRecovery`,
`BackupBeforeRollback`, `RestoreRecovery`, `SwitchPreviousRelease`, `Health`.
Каждый доверенный порт возвращает **ровно один Boolean true**, без вывода
секретов. Массивы, строки, false, отсутствие результата и ошибки запрещают
следующий шаг. Без подтверждённой новой before-rollback restore не вызывается.
Неуспешный health вызывает stop. Проверка recovery должна подтвердить продукт,
полный состав и возможность восстановления; backup обязан создать и проверить
новую полную зашифрованную копию всех данных. Restore обязан сохранить текущие
lock/управляющее состояние; switch — атомарно и надёжно активировать прежний
проверенный выпуск. Health обязан соблюдать loopback и health_wait из манифеста.
Замыкания портов получают конкретную установку/манифест от доверенного адаптера.

Эти порты не поставляются: `backup.cmd`/`restore.cmd` не определяют протокол
проверки полного зашифрованного архива и не вызываются наугад. Сценарий не
заменяет durable checkpoints/resume из `UpdatePlan`, не идемпотентен после
аварии целиком и не выполняет автоматический rollback при сбое install/start.
Частичная регистрация/запуск требуют ручного восстановления. Установка здесь
означает только подготовку каталогов и регистрацию уже подготовленного приложения:
поставка/проверка offline runtime/payload, миграции, hooks, health startup,
надзор heartbeat и межрежимное исключение уже работающих служб не реализованы.
Выбор режимов проверяется при генерации, разные отдельно запущенные bundles
должен согласовывать адаптер. Uninstall сохраняет файлы; повторный install
без явной подготовки назначения завершится отказом.

**Сформировано и проверено как текст; ничего из сценариев не исполнялось.**
Не выполнялись ACL/DPAPI операции, регистрация/старт/стоп/удаление служб,
реальный restore/rollback, clean-Win11 install/update/restore/rollback или Docker.
Требование CLAUDE.md о Docker-приёмке остаётся открытым: прямое задание запрещает
внешние службы. Внешние MCP, сеть, commit/push/merge/deploy и изменения
Git metadata/конфигурации агентов/настроек безопасности отсутствуют.

## CLI

Для заранее подготовленного публичного v2-манифеста с pin:

```powershell
py -3.14 -B -m shared.ctl --manifest public-v2.json render-windows --install-root C:\Product --mode autonomous --winsw-file public-WinSW.exe --dpapi-scope LocalMachine --output-dir build/windows-text --json
```

CLI проверяет публичный артефакт и записывает только PS1/XML в новый каталог.
Флага исполнения нет. Существующие результаты не перезаписываются; возможен
частичный вывод при I/O ошибке. Общие коды `ctl`: 0 — тексты записаны,
2 — неверный контракт/аргументы/пути/pin, 1 — локальная I/O ошибка.
