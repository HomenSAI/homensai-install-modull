# Совместная блокировка писателей и архива на Linux

`shared.writer_guard.CooperativeWriterLock` — необязательный внутренний
механизм для продуктов, в которых **каждый** процесс-писатель добровольно
использует один и тот же файл блокировки. Писатель держит общую блокировку на
всё время, когда может менять данные; архиватор берёт исключительную блокировку
до проверки остановки служб и удерживает её до завершения снимка и повторной
проверки. Если блокировка занята, архивирование отказывает без ожидания.

```python
from shared.writer_guard import CooperativeWriterLock

guard = CooperativeWriterLock('/absolute/private-control/writers.lock')
with guard.hold(exclusive=False):
    run_product_writer()
```

Интегратор может передать тот же объект как `writer_lock` в
`assemble_prepared_linux_update`; по умолчанию эта блокировка не включена.
Это внутренний Python-интерфейс, не операция публичного API. Передача объекта
сама по себе не доказывает, что продукт или другие программы соблюдают протокол.

Каталог блокировки должен существовать, принадлежать текущему пользователю и
иметь права `0700`. Файл создаётся с правами `0600`, остаётся на месте между
запусками и не должен удаляться или заменяться. Путь выбирает доверенный
интегратор; он должен быть вне корней программы, данных, архивов и рабочего
каталога обновления. Файл, каталог и все их родители должны быть защищены от
неавторизованных изменений. Нельзя использовать разные пути или разные inode
для одного набора данных. Контейнерам потребовалась бы отдельная проверенная
передача того же inode; Docker-поддержка здесь не реализована.

В Linux используется неблокирующий `flock`: писатели берут `LOCK_SH`,
архиватор — `LOCK_EX`. Lock на другом API, например POSIX record lock, не
считается участием в этом протоколе. Дескриптор помечен close-on-exec: каждый
запущенный через `exec` писатель должен получить собственную блокировку.
Проверены отдельные локальные процессы, завершение писателя по SIGKILL,
конкуренция блокировок и реальный архив синтетических данных. Сетевые файловые
системы, Windows, питание и реальные продукты не проверялись.

Файл блокировки включён в контекст записи результата через SHA-256 его пути;
это не подпись и не проверка происхождения. Если файл подменён во время снимка,
результат остаётся `pending`. Старая отметка без блокировки не принимается как
результат с ней. Остановка выбранных user-units по-прежнему проверяется до и
после снимка. Полученная защита не охватывает процессы, которые игнорируют
`flock`, используют другой файл, работают с другими правами или обходят
протокол; не гарантирует отсутствие записи до/после удержания блокировки и не
доказывает, что архив согласован для произвольной базы. Шаг 53 плана остаётся
незавершённым.
