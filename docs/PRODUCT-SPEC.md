# Спецификация первой версии общего установочного модуля

Версия требований: 02.11.2026. Основа — `WORK-PLAN.md`, шаги 03–10.
Автор проекта: Serhii Khomenko · HomenS.AI.

## Назначение и границы

Общий модуль собирает установочные комплекты по манифесту продукта и
управляет их жизненным циклом. Сам установщик не требует ИИ. Первую приёмку
проводят на вымышленном продукте; каждый настоящий продукт позже получает
свой адаптер и отдельную приёмку. Наличие профиля в спецификации не является
заявлением текущей готовности.

Первая версия охватывает свежую установку, повтор после прерывания,
переустановку, обновление, откат, восстановление из копии, состояние,
диагностику и удаление. Поддерживаются отдельные и комбинированные пакеты.
Не входят автоматическое управление лицензиями продуктов, удалённая установка,
облачный сервис, macOS, ARM и миграция реальных продуктов. Их можно добавить
позже без объявления поддержки сейчас.

## Целевые профили

| Профиль | Хост и способ запуска тестового продукта | Состав комплекта |
|---|---|---|
| `windows-native` | Windows 11 x64, локальные процессы/службы | ядро, Windows-блок, Windows payload и runtime |
| `linux-native` | Linux x86_64, локальные процессы/службы | ядро, Linux-блок, Linux payload и runtime |
| `windows-docker` | Windows 11 x64, Docker Desktop и Linux-контейнеры | ядро, Windows-блок, Docker-блок и контейнерный payload |
| `linux-docker` | Linux x86_64, Docker Engine и Compose | ядро, Linux-блок, Docker-блок и контейнерный payload |

Это целевая матрица приёмки, а не обещание работы на произвольной системе.
Конкретный дистрибутив Linux, редакцию Windows, версии Docker/Compose и
необходимые права зафиксировать вместе с тестовым окружением до приёмки.
Windows в контейнере не подразумевается: Docker-профили выше используют
Linux-контейнеры. Совместимость продукта с профилем заявляет его адаптер.

Отдельный пакет содержит ядро, выбранный профиль и необходимые файлы продукта.
Комбинированный пакет содержит объединение выбранных совместимых профилей;
мастер предлагает только доступные на текущем хосте варианты. Наличие Docker
может проверяться установщиком; автоматическая установка Docker и способ
получения его дистрибутива пока не определены и не считаются готовой функцией.
Offline-пакет должен включать все требуемые артефакты; online-пакет может
скачивать только явно перечисленные проверяемые артефакты. Конкретный формат
и каналы распространения уточняются при проектировании сборщика.

## Функции и жизненный цикл

1. Проверить платформу, архитектуру, права, место, зависимости и конфликтующие
   операции; выдать объяснимую ошибку до изменения пользовательских данных.
2. Выбрать разрешённый профиль и пути установки и постоянных данных.
3. Проверить состав и целостность пакета и подготовить выпуск.
4. При замене остановить всех писателей, создать и проверить полный архив
   постоянных корней; обеспечить копию перед каждой миграцией.
5. Выполнить миграции, переключить выпуск, запустить компоненты по порядку
   зависимостей и проверить идентичность и здоровье установки.
6. При неудаче остановить новые компоненты, создать отдельную проверенную
   копию текущих данных перед откатом и восстановить прежнее состояние.
7. Сохранять состояние операции; после сбоя возобновлять только совместимую
   операцию, не повторяя опасные внешние действия без доказанной идемпотентности.
8. Предоставить состояние, диагностику, восстановление и удаление с явным
   выбором обращения с данными. По умолчанию данные и копии сохраняются.

Новый продукт должен объявить свои постоянные корни, процессы, компоненты,
зависимости, миграции, совместимость выпусков и проверки здоровья. Универсальный
модуль не может вывести эти сведения автоматически или гарантировать
корректность произвольных команд продукта.

## Данные, безопасность и зависимости

Данные, настройки, архивы и ключи располагаются вне заменяемого выпуска;
установка не должна молча удалять их или перезаписывать ключ. Проверки путей
должны запрещать опасные пересечения и неподдерживаемые ссылки. Установка
производится с минимальными необходимыми правами; секреты не попадают в Git,
командные строки, сообщения или журналы. Доставка секретов и защита прав
проверяются на каждой целевой ОС. Архив с секретами шифруется, его пароль и
процедура восстановления должны быть доступны владельцу независимо от
предыдущей машины. Аварийная очистка временного открытого содержимого требует
отдельного проектирования и проверки; гарантия безопасного стирания не заявлена.

Для каждого бинарного артефакта и зависимости фиксируются версия, источник,
лицензия и проверенный хэш. Сборка и установка отказывают при несовпадении.
Перечень лицензий и способ получения подтверждённых артефактов закрепляются
до выпуска; существующий `requirements-crypto.txt` ещё не является полным
offline hash-lock. Проверка хэша подтверждает совпадение с доверенным ожидаемым
значением, но сама по себе не доказывает происхождение файла.

## Критерии приёмки каждого профиля

На одной зафиксированной сборке тестового продукта и в задокументированной
чистой целевой среде должны пройти: свежая установка, повторная установка,
успешное обновление, отказ миграции, отказ health, восстановление и откат;
прерывание и повтор на важных фазах; проверка места, прав, повреждённого
пакета и архива; параллельные операции; пути с пробелами и кириллицей;
сохранение данных при удалении; восстановление на другой чистой системе.
Проверить реальное состояние служб/контейнеров и данных, а не только коды
выхода. Зафиксировать версии среды, состав пакета, результаты, пропуски и
открытые дефекты. Непроверенный или пропущенный сценарий не считается пройденным.

Подтверждение профиля требует реальной целевой ОС и исполнения соответствующих
служб/контейнеров. Фейки, генерация текстов и контейнер с тестами Python полезны
для разработки, но не заменяют приёмку. Финальная совместимость с JobPilot,
Rent или иным продуктом требует отдельной интеграции и тестов этого продукта.
