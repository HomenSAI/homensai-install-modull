# Подготовка зависимостей в мастере

Автор: Serhii Khomenko. Реализация CP-20261025-015; `production_ready=false`.

Мастер использует HTTP-контракт `PREREQUISITES_HTTP.md` и тот же явно
зарегистрированный coordinator, что SDK/CLI. JavaScript не выбирает adapter,
не запускает команды и не вычисляет совместимость версий самостоятельно.
`gui_auto_flow=true` в discovery означает наличие условного flow в исходном
коде. Capabilities сессии возвращают true только для настроенного target;
без coordinator и для другого режима — false.

## Просмотр и согласия

Раздел подготовки находится на первом шаге мастера. Для компонента показаны
обязательность, найденная версия, требуемый диапазон, scope, зависимости,
готовность и доступные use/auto/manual/skip. Обязательный компонент и зависимость
выбранного компонента нельзя пропустить. Auto доступен только для IDs из
проверенных capabilities. Артефакты показывают версию, источник, размер и SHA-256.

`requirements` соединяются с plan по component ID при равенстве product ID,
owner ID, catalog digest и полного target. Неверные или отсутствующие metadata
означают неизвестные сведения. Найденная версия показывается только для строки
допустимого формата со строгим концом строки; объекты, redaction markers и
завершающий newline не становятся версией. Readiness берётся из core.

Нужны просмотр условий продукта и лицензий компонентов, отдельные флажки
автоматического действия, повышения прав и дополнительных условий, если они
требуются, затем подтверждение общего плана. Неизвестное обязательное согласие
блокирует запуск. Флажки условий доступны после просмотра текста; текст можно
сохранить, страницу — распечатать. Смена выбора или языка аннулирует draft
review. Исполняемый план сохраняет исходные согласия; перевод экрана их не меняет.

## Операция и восстановление

Подготовка имеет отдельные operation ID, revision, event cursor и progress.
Они не заменяют продуктовую операцию и её экран результата. Выделенный сервером
ID сохраняется до POST start с точной публичной привязкой. Reload/list — только
GET. Потерянный ACK восстанавливается по тому же ID без нового start/resume.
Продолжение требует отдельного действия пользователя.

Управление и переход к продукту требуют `execution.active === false`.
Active=true/null продолжает ожидание даже при READY/finished. Старые revision,
GET из предыдущей мутации и запоздалые ответы смены языка/режима не возвращают
прежнее состояние. Потеря соединения блокирует новый запуск; успешное обновление
восстанавливает наблюдение. Ошибка старого запроса не отменяет новый poll.

Cancel доступен во время медленного recheck. Replace-plan сохраняет исходный
operation ID, требует новых согласий и отдельного resume. Reboot/relogin
записывают now/later; `host_action.performed=false` отображается как необходимость
выполнить системное действие самостоятельно.

Показаны подтверждённые состояния и число READY. Пока нет готовности, индикатор
неопределённый. Durable byte-progress и безопасный выбор локального артефакта
браузером ещё не реализованы; процентов из времени или числа событий нет.

## Возврат к приложению

Dependency READY подтверждает только подготовку. Оно сбрасывает старые product
plan и согласия. Отдельная кнопка получает свежие capabilities/discover и новые
условия, затем нужен новый review приложения. Product submit автоматически
не вызывается. Незавершённые операции и неизвестный controller блокируют переход.
Сессионная защита не закрывает промежуток между внешними product submit и
prerequisite start: общий атомарный межпроцессный lease остаётся задачей core.

## Проверка и границы доказательств

`tests/js/wizard_prerequisites.cjs` выполняет настоящий `app.js` через Node VM
с управляемыми DOM/fetch и читает фактические HTML/locales. Python launcher
`tests/test_wizard_prerequisite_ui.py` включает его в source suite. Прежние
capability cases сохранены в `tests/js/wizard_capabilities.cjs`.

Node contract не подтверждает браузерную вёрстку, accessibility, реальные
скачивания, OS installers, UAC, reboot/relogin или полную приёмку платформ.
Результаты, hashes, первоначальные FAIL и BLOCKED находятся в checkpoint
receipts и `verification-status.json`. Настоящий браузерный прогон нужно
выполнить в исправной среде; тестовый файл не заменяет выполненную проверку.
